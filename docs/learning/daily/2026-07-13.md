## 2. Payment Processing Concepts Learned

- A fraud action is part of payment lifecycle truth, not merely a score. The
  attempt and intent must enter the matching state before processor work.
- Only ALLOW crosses the processor boundary. Fraud step-up is not processor
  3DS evidence, and review cancellation is not an authorization void.
- Idempotency plus the PaymentIntent lock serializes attempt numbering and
  prevents two callers from creating divergent decisions or processor work.

## 3. Fraud Detection Concepts Learned

- Explainability requires retaining non-matches as well as matches; otherwise
  absence of evidence is indistinguishable from skipped evaluation.
- `BLOCK > REVIEW > REQUEST_3DS > ALLOW` is deterministic product policy.
  The fixed score is severity for sorting, not fraud probability.
- Review intake is the first durable analyst work item. Assignment, resolution,
  labels, and feedback remain Phase 4 because they need their own authorization
  and money-action promises.

## 4. Security Concepts Learned

- Application immutability is insufficient for decision evidence. Composite
  database keys must bind copied action/reason/priority and review reasons back
  to the immutable source record.
- Tenant and traffic-origin identity must cross every feature, decision, rule,
  payment, and review edge.
- Metrics and explanations use closed codes only; no card data, PII, IDs,
  feature values, credentials, or merchant prose becomes a dimension.

## 5. Architecture / Design Notes

- The engine accepts only `DecisionFeatureContext`, evaluates the full seeded
  catalogue, then returns one decision plus complete typed evaluations.
- Confirm persists and flushes local evidence before processor authorization.
  Non-allow branches finish locally; ALLOW alone invokes the adapter.
- V25 preserves webhook subscription intent for both partial and exact-full
  legacy event sets; without a durable wildcard bit, neither is consent to
  future fraud/review event types.
