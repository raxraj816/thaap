# Daily Deep Dive: 2026-06-09

This note is for end-to-end understanding of a Staff-level implementation slice.
It should make the code explainable, not merely documented.

## 1. System Goal

Chapter 6 makes `POST /payment_intents` production-shaped enough to be a safe base
for later confirm, authorization, fraud, and ledger work.

In payment terms, this slice creates the customer-visible payment container. It
does not move money. It records that a merchant intends to collect a specific
amount from one of its own customers, under a stable object ID that later
attempts and decisions can reference.

The production risk reduced here is duplicate or cross-tenant object creation.
If retries create multiple payment containers, merchants lose trust. If one
merchant can attach another merchant's customer to a PaymentIntent, tenant
isolation is broken before fraud scoring even begins.

## 2. Plain-English Design Brief

The simplest model is:

1. Authenticate the merchant through `X-Api-Key`.
2. Require an `Idempotency-Key`.
3. Validate the create request.
4. Prove the customer belongs to that merchant.
5. Create one PaymentIntent in `REQUIRES_CONFIRMATION`.
6. Create webhook delivery intent for active merchant endpoints.
7. Store and replay the response for safe retries.

Without this design, a network retry could create duplicate PaymentIntents or a
client could point at another merchant's customer ID. Both failures corrupt the
payment lifecycle and future fraud labels.

We built the create boundary and test proof. We intentionally deferred confirm,
PaymentAttempt creation, fraud decisions, processor authorization, ledgering,
and idempotency expired-key cleanup because those are separate side-effect or
operations boundaries in the master plan.

## 3. Code Map

- `PaymentIntentController` owns the HTTP contract, validation annotations,
  tenant-scoped customer check, PaymentIntent creation, and webhook delivery
  creation call.
- `PaymentIntent` owns the container state: ID, merchant, customer, amount,
  uppercase currency, capture method, status, and timestamps.
- `PaymentAttempt` owns the confirm lineage state: merchant, PaymentIntent,
  PaymentMethod, idempotency key, status, attempt number, nullable fraud
  decision, nullable processor authorization, nullable 3DS status, and
  timestamps.
- `IdempotencyService` owns required-key enforcement, operation and request
  binding, committed `IN_PROGRESS` reservation, merchant-scoped replay,
  changed-body conflict detection, in-progress duplicate rejection, completion,
  and failed-mutation cleanup.
- `WebhookDeliveryService` creates `payment_intent.created` delivery rows for
  active merchant endpoints and `payment_attempt.created` rows once confirm
  creates an attempt.
- `PaymentIntentCreateContractTests` proves the Chapter 6 contract directly.
- `PaymentIntentConfirmContractTests` proves the Chapter 9 attempt lineage
  contract directly.

The tables involved are `payment_intents`, `payment_attempts`,
`idempotency_records`, `customers`, `payment_methods`, `webhook_endpoints`, and
`webhook_deliveries`.

## 4. Request/Data Flow

1. `POST /payment_intents` enters `PaymentIntentController`.
2. `MerchantContext` resolves the tenant from `X-Api-Key`.
3. Bean validation checks `customerId`, positive `amount`, and three-letter
   `currency`.
4. `IdempotencyService.execute` rejects a missing key, computes the internal
   request hash, reserves an `IN_PROGRESS` record by `(merchant_id, key)`, and
   either replays, conflicts, or runs the create supplier.
5. `CustomerRepository.existsByIdAndMerchantId` proves the customer belongs to
   the merchant.
6. `PaymentIntentRepository.save` persists the new object with uppercase
   currency and status `REQUIRES_CONFIRMATION`.
7. `WebhookDeliveryService.createDeliveries` writes
   `payment_intent.created` delivery records for active endpoints.
8. The idempotency record is marked `COMPLETED` with response body and HTTP
   status for replay only after the mutation response is durable.
9. The API returns the public PaymentIntent response.

Chapter 9 confirm adds this flow:

1. `POST /payment_intents/{id}/confirm` enters `PaymentIntentController`.
2. `IdempotencyService` reserves the confirm key for
   `payment_intents.confirm:{id}`.
3. The PaymentIntent is loaded through `(id, merchant_id)`.
4. The PaymentMethod is loaded through `(id, merchant_id)`.
5. The controller verifies the PaymentMethod belongs to the same customer as
   the PaymentIntent.
6. The controller rejects non-confirmable PaymentIntent statuses.
7. `PaymentAttemptRepository.maxAttemptNumber` computes the next attempt number
   for that PaymentIntent.
8. `payment_attempts` receives the durable attempt row.
9. `WebhookDeliveryService` writes `payment_attempt.created` delivery records
   for active endpoints.
10. The idempotency record stores the attempt response for exact replay.

## 5. Database Invariants

- `payment_intents.merchant_id` is required and references `merchants`.
- `(merchant_id, id)` is unique for tenant-scoped object addressing.
- `(merchant_id, customer_id)` references `customers(merchant_id, id)`, so a
  PaymentIntent cannot point to another merchant's customer.
- `payment_attempts` reference PaymentIntents by `(merchant_id,
  payment_intent_id)` and PaymentMethods by `(merchant_id, payment_method_id)`.
- `(merchant_id, payment_intent_id, attempt_number)` is unique, so attempt
  numbers cannot collide inside a PaymentIntent lineage.
- `idempotency_records` are unique by `(merchant_id, idempotency_key)`.
- `idempotency_records.operation` and `request_hash` bind a key to exactly one
  mutation contract.
- `idempotency_records.status` separates `IN_PROGRESS` from `COMPLETED`.
- In-progress idempotency records have nullable response status/body so they do
  not pretend to have a replayable result.
- `idempotency_records.expires_at` gives future operations code a recovery hook
  for abandoned in-progress reservations.
- `webhook_deliveries` reference webhook endpoints by `(merchant_id,
  webhook_endpoint_id)`, preventing cross-merchant delivery rows.
- Hot lookup indexes exist for merchant, customer, and idempotency access.

If the tenant-scoped foreign keys disappeared, application bugs could silently
create cross-merchant payment lineage. If the idempotency unique key
disappeared, retries could diverge into duplicate objects.

## 6. Security And Privacy Invariants

The request contains a customer ID, amount, currency, optional capture method,
`X-Api-Key`, and `Idempotency-Key`. The API key is authenticated by hash/prefix
storage from prior days. The idempotency request hash is internal, keyed through
`SensitiveValueHasher`, and not returned.

The response returns public PaymentIntent state only. It does not return
idempotency hashes, stored response bodies, API-key hashes, webhook signing
secret hashes, customer PII hashes, or card fingerprints.

The payment-security principle is least exposure plus tenant isolation: the
merchant can see its payment container, not internal controls or another
merchant's graph.

## 7. Fraud/ML Relevance

PaymentIntent create provides stable context for future PaymentAttempts,
fraud decisions, feature snapshots, review cases, and processor outcomes. It
also establishes customer linkage, amount, currency, and capture method as
payment facts that later features can reference.

Chapter 9 adds the missing lineage target: PaymentAttempt. We still avoided
adding fraud rules, model scores, feature snapshots, graph signals, and analyst
explanations because those outcomes need their own owner chapters. Scoring a
PaymentIntent directly would collapse the planned distinction between payment
container and scoring/audit unit.

## 8. Tests As Proof

`PaymentIntentCreateContractTests` proves:

- successful create returns the public response and persists normalized state
- `Idempotency-Key` is required and errors use the standard shape
- replay returns the original response
- replay does not create duplicate PaymentIntent or webhook delivery rows
- changed-body reuse returns `409`
- invalid request fields return validation errors
- missing `captureMethod` defaults to `AUTOMATIC`
- another merchant's customer is rejected

Existing migration tests also prove the schema-level tenant constraints and
indexes exist. Existing tenant tests still cover broad cross-merchant payment
read and mutation behavior.

`IdempotencyServiceTests` now proves the Chapter 8 hardening slice directly:

- completed reservations replay the original response
- operation mismatch conflicts even when the request body matches
- in-progress duplicates are rejected before the mutation supplier runs
- failed mutations release reservations and can be retried
- same idempotency key can be reused by different merchants
- in-progress records store operation, request hash, status, and expiration
  without fake response payloads

`PaymentIntentConfirmContractTests` now proves the Chapter 9 slice:

- confirm creates a durable attempt with fraud/processor/3DS fields still null
- `GET /payment_attempts/{id}` fetches through tenant scope
- confirm replay does not create duplicate attempts or webhook deliveries
- separate confirm keys produce attempt numbers `1` and `2`
- concurrent confirm keys also produce distinct attempt numbers because confirm
  locks the PaymentIntent row before reading the current max attempt number
- invalid status creates no attempt
- cross-merchant PaymentIntent and PaymentMethod inputs create no attempt
- wrong-customer PaymentMethod input creates no attempt

The missing test a Staff engineer would ask for next belongs to Chapter 10:
prove confirm orchestration updates attempt and PaymentIntent state consistently
once fraud/processor behavior exists.

## 9. Staff Engineer Review Notes

The tradeoff was to harden object creation, idempotency, and attempt lineage
before pulling in authorization behavior. That keeps each side effect auditable:
creation creates a container, idempotency creates a retry-safe mutation
boundary, confirm creates an attempt, fraud creates a decision, and processor
authorization creates a result.

The risk reduced was accidental duplicate or cross-tenant PaymentIntent and
PaymentAttempt creation. The design stays reversible because no actual fraud,
ML, ledger, or processor outcome rows are created yet.

It would be dangerous to overbuild by adding synthetic fraud scores here. The
platform needs lineage before intelligence; otherwise explanations become
storytelling instead of evidence.

## 13. Interview Narrative

Practice saying this out loud:

- The tradeoff I made was keeping Chapter 6 limited to object creation.
- The invariant I enforced was that a merchant can create exactly one
  PaymentIntent per idempotent create request for its own customer, and Chapter
  8 makes that boundary safe under in-progress duplicate requests. Chapter 9
  adds the invariant that confirm creates a tenant-scoped PaymentAttempt before
  future fraud or processor work can attach outcomes.
- The production risk I reduced was duplicate payment containers and
  cross-tenant object linkage.
- I deferred confirm, attempts, fraud decisions, processor authorization, and
  ledgering at Chapter 6 because each is a separate side-effect boundary. After
  Chapter 9, attempts are no longer deferred, but fraud decisions, processor
  authorization, final status mapping, and ledgering still are.
- The tests prove request validation, idempotent replay, changed-body conflict,
  tenant isolation, persisted normalized state, webhook non-duplication,
  in-progress duplicate rejection, operation binding, failed-mutation cleanup,
  and merchant-scoped key reuse.
