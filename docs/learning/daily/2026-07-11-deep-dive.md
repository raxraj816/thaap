# Daily Deep Dive: 2026-07-11

This note is for end-to-end understanding of a Staff-level implementation slice.
It should make the code explainable, not merely documented.

## 1. System Goal

- Re-close Chapter 21 only after merchant replay and webhook secret/lease
  protocols survive their full time-and-concurrency transition grammars.
- Payments platforms fail at boundaries between individually valid states;
  this slice prevents duplicate credentials, expired signatures, lost webhook
  events, late runtime key failures, and stolen live reservations.

## 2. Plain-English Design Brief

- A replay window is one durable epoch: calls inside it return the same result;
  calls after it create a new epoch and therefore a new credential.
- A webhook generation is authorized only if its validity is checked at the
  same locked instant used to mint its signature timestamp.
- A stale claim should retry against current durable state; integrity failures
  remain terminal.
- No defect affecting the frozen promise is deferred.

## 3. Code Map

- `MerchantCreationService`: reservation ownership, expired-epoch replacement,
  deterministic credential derivation, and completion.
- `WebhookEndpointService`: endpoint creation and rotation transaction order.
- `WebhookEndpointSecretService`: tenant-scoped endpoint lock, exact-time
  generation validation, decryption, lazy KEK re-encryption, and signing.
- `WebhookDeliveryExecutor`: target preparation, recovery classification,
  transport, and attempt finalization.
- `WebhookExecutionConfiguration`: persisted KEK readiness independent of
  worker mode.
- Contract tests prove API/storage behavior; PostgreSQL tests force the two
  lock orderings that an H2 or mock test cannot certify.

## 4. Request/Data Flow

Merchant creation: the admin request is canonicalized and HMACed; an existing
live alias replays its record, while an expired record and aliases are deleted
and flushed. A new UUID record becomes the lifecycle epoch. The API key is
derived from original key version + record UUID + request identities, the
merchant and completed reservation commit together, and only the response
reveals the raw key.

Webhook delivery: the claim already names a secret generation. After target
preparation, the executor supplies a time lower bound. The signing transaction
locks the tenant endpoint, captures exact use time, validates current or
strictly-unexpired previous generation, decrypts, signs under the lock, and
returns the header. A concurrent rotation waits. A stale generation normally
records retryable known-no-send evidence; at the retry ceiling, current state
is rebound before the first socket opportunity.

Endpoint creation: the operation transaction locks and validates the durable
reservation before secret generation or persistence. Even after wall-clock
lease expiry, a contender cannot reclaim until the owning transaction releases
the row, at which point it observes completed truth and replays it.

## 5. Database Invariants

- One live merchant-creation alias maps to one creation record; a record UUID
  distinguishes successive expired epochs without storing the external key.
- One tenant/url endpoint row and one tenant/idempotency alias binding prevent
  duplicate delivery streams.
- Endpoint current/previous generations and expiry are read under the same row
  lock used by rotation and signing.
- Reservation owner token and status are validated before mutation. Without
  that ordering, a lease timeout could admit two secret generations or audit
  histories even if one transaction later rolled back.

## 6. Security And Privacy Invariants

- Merchant API keys and webhook signing secrets are revealed raw only in
  bounded responses. Merchant credentials persist as prefix/hash; webhook
  material persists as prefix/hash plus tenant-bound AES-GCM ciphertext.
- External idempotency keys and canonical requests persist as HMAC outputs with
  explicit key versions. The record UUID is non-secret domain separation.
- KEK startup inventory fails closed across current, unexpired previous, and
  live replay ciphertext even in observe/admin-only mode.

## 7. Fraud/ML Relevance

- Reliable merchant and webhook identity keeps duplicate retries from creating
  duplicate fraud events or misleading analyst timelines.
- Stable correlation keys remain unchanged, so velocity, graph, and future ML
  features do not split during replay-key rotation.
- No scoring or label behavior was added; Chapter 21 repairs infrastructure
  truth and does not invent Phase 3 fraud promises.

## 9. Staff Engineer Review Notes

- Signing under a database row lock intentionally lengthens a short transaction
  by local HMAC work. That small bounded cost buys an atomic authorization/use
  boundary without holding the lock over network I/O.
- Stale generation is retryable, but ciphertext integrity/key-configuration
  defects are not silently reclassified; this preserves diagnosability.
- No migration was required: existing UUIDs, locks, and attempt state already
  represented the needed truth. The correction is reversible at code level.
- Building a distributed signing service or queue would add protocol surface
  without improving this bounded local product wedge.

## 13. Interview Narrative

Practice saying this out loud:

- The tradeoff I made was holding an endpoint row lock during bounded local
  cryptographic work to make generation authorization and use atomic.
- The invariant I enforced was that replay is stable inside one lifecycle epoch
  and distinct after expiry, while signatures use only exact-time-valid state.
- The production risk I reduced was duplicate merchant credentials, invalid
  webhook signatures, silently lost deliveries, late KEK failures, and stolen
  live endpoint reservations.
- I deferred new fraud behavior because this slice repairs substrate truth and
  Phase 3 needs its own frozen decision promises.
- The tests prove exact epoch, time, recovery, operating-mode, and lock-order
  partitions at their real enforcement boundaries.
