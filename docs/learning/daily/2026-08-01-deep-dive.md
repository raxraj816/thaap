# Daily Deep Dive: 2026-08-01 — Durable Facts To Rebuildable Risk Truth

Phase 5 implementation status: COMPLETE

## 1. System Goal

THAAP now turns committed payment/risk facts into explainable analytics that
survive broker failure, duplicate delivery, restart, corruption attempts, and
projection replacement without changing source payment, fraud, or ledger truth.

## 2. Plain-English Design Brief

The mental model is a chain of receipts. The source transaction writes an
immutable canonical receipt and an outbox pointer. Kafka transports the exact
receipt. A PostgreSQL inbox makes repeats harmless. Projections are disposable
views with explicit generation/freshness/coverage. Rebuilds create a hidden new
view, prove equivalence, then swap one pointer. Datasets bind a point in time.

Without those receipts, a broker outage can lose truth, a duplicate can double
money, a stale table can mislead an analyst, and a rebuild can silently rewrite
history. We intentionally did not add model training/serving, CDC, a schema
registry, ClickHouse, hosted multi-merchant scope, or network effects.

## 3. Code Map

- `event/` owns catalogue, canonical bytes, stream versions, writer, and outbox.
- `eventpublication/` owns leased Kafka publication and recovery.
- `projection/` owns inbox/quarantine, generation-local handlers, health, and
  consumer recovery; `analytics/` shapes tenant-scoped reads.
- `projection/rebuild/` owns cutoffs, bootstrap facts, Spring Batch shadow build,
  reconciliation, activation, and rollback.
- `replay/` owns immutable point-in-time dataset manifests/results.
- V65–V85 enforce durable database truth; the analyst UI and public demo expose
  the product loop.

## 4. Request/Data Flow

1. Merchant/risk APIs authenticate, resolve tenant/actor, and lock/idempotently
   mutate authoritative rows.
2. The same transaction allocates the tenant-qualified stream version, encodes
   exact bytes, and writes event plus pending publication.
3. A fenced publisher sends stored bytes to `thaap.domain-events.v1`.
4. The consumer validates key/bytes/schema/tenant/order, writes inbox plus both
   projections atomically, then acknowledges Kafka.
5. Analytics resolve active generations and return lineage/freshness/coverage.
6. Rebuild/dataset operators create isolated, immutable, bounded work and public
   readers never see an unreconciled generation.

## 5. Database Invariants

- Composite tenant/stream uniqueness and locked heads make versions gap-free.
- Exact byte/digest fields and immutable triggers prevent historical rewrite.
- Inbox uniqueness binds consumer/event identity to one full-record digest.
- Projection rows, checkpoints, and positions are generation-qualified.
- Rebuild lease token+epoch fences stale workers; chunk and catch-up evidence is
  append-only, and each cycle applies no more than 100 inputs.
- Activation locks the definition before changing the active pointer.
- Dataset cutoff/generation/tenant lineage is immutable.
- `domain_event_source_lineage` makes a fraud event's decision and feature
  snapshot explicit. PostgreSQL validates the event type and walks the decision
  through its payment attempt to require the event's exact payment stream;
  update/delete and cross-payment substitution fail.

## 6. Security And Privacy Invariants

Credentials are reveal-once and stored hashed. Canonical payloads are explicit
allowlists, never entity serialization. Recovery returns safe codes/counts, not
payloads. Tenant identity is independently matched at every representation
boundary. Human audit and domain events stay separate so automation cannot
impersonate a person.

## 7. Fraud/ML Relevance

The payment projection preserves decision-time ruleset/feature catalogue,
reason codes, outcome, review, label value/source/availability, origin, and money
lifecycle. Merchant aggregates expose honest cohort coverage. Offline manifests
create reproducible training/evaluation inputs later, but Phase 5 makes no model
quality or serving claim.

## 8. Tests As Proof

H2 contracts prove fast state partitions. PostgreSQL proves constraints,
timestamps, lock order, triggers, retained migration, and query plans. Kafka
tests prove broker configuration, exact bytes, duplicate/restart behavior, and
ack boundaries. Browser tests prove what an analyst actually sees. The strongest
new hostile test changes a positive bootstrap amount without changing row count;
reconciliation rejects it, restoration passes, and source rows remain unchanged.
The final regression ran 854 backend tests and 166 repository Python tests with
zero failures or skips, plus 22 analyst UI tests and a production build.

The second hostile pass added the partitions that the first closure missed:
same-microsecond decisions, copied same-tenant payment lineage, integer overflow,
microsecond timestamp precision, noncanonical UUIDs, missing source links, every
analytics collection's terminal cursor, UTC interval alignment/defaults, and
the human-visible basis-point conversion.

## 9. Staff Engineer Review Notes

The key tradeoff is PostgreSQL-first transparency over early distributed scale.
That reduces dual-write, replay, and observability risk and keeps every claim
inspectable. Generations and immutable manifests make the design reversible.
It would be dangerous to add ML/warehouse/network breadth before dataset and
merchant-product evidence justifies it.

## 13. Interview Narrative

The tradeoff was a PostgreSQL-first event/projection backbone instead of early
distributed breadth. The invariant was that every downstream artifact is a
tenant-qualified, immutable derivation of committed source truth. This reduced
lost-event, duplicate-effect, stale-analytics, and unsafe-rebuild risk. Scale and
ML serving were deferred because their evidence triggers do not yet exist. Real
PostgreSQL/Kafka, browser, failure-sequence, migration, and source-fingerprint
tests prove the important boundaries.

The final live journey changed the proof discipline materially. H2 plus a
PostgreSQL `EXPLAIN` did not certify JDBC timestamp conversion, an intent-only
rebuild did not certify the canonical basis-point score, and client safety unit
tests did not certify the public demo's response/status/schema names. The
resolved `ER-0074`–`ER-0082` family therefore added value-bearing PostgreSQL API
execution, a production-shaped score-bearing rebuild, V82, complete-stream
waiting, exact end-to-end durable counts, V83–V85 relational source identity,
semantic protocol bounds, collection-wide pagination, aligned ranges, explicit
human score units, and architecture-gate reconciliation before restoring the
merge claim.
