## 2. First-Principles Mental Model

A recovery protocol needs two truths: who owns unfinished work now, and what
safe identity remains if the secret-bearing work record is erased. A
time-bounded credential also needs authorization at the instant of use, not
merely when it was loaded. Security review follows the effective destination
and every decryptable ciphertext, not only the obvious URL or primary column.
For a remote mutation, local journaling starts too late: only a stable
server-side idempotency identity can reconcile a server commit that precedes
every client-side write. Workflow classification is also durable protocol
state, not a hint a newer caller may reinterpret.

## 3. Payment, Fraud, And ML Relevance

The fixes do not change money state or fraud decisions. They protect the
surrounding control plane from duplicate merchants/customers and webhook
streams, expired signatures, credential exfiltration, and loss of synthetic-run
cleanup lineage. Duplicate customer or merchant truth would corrupt tenant and
future fraud-label lineage before the first payment existed, so onboarding
idempotency is a data-quality control as well as an API reliability feature.

## 4. Schema, API, And Transaction Boundaries

- V14 adds `lease_token` and `lease_expires_at`; `IN_PROGRESS` records require
  both, `COMPLETED` records require neither, and historical unfinished rows are
  immediately reclaimable.
- V15 applies the same fenced state machine to general idempotency and adds
  `merchant_creation_records`. Merchant reservation and merchant creation
  complete atomically after an independently committed reservation; customer
  mutation, safe response, and idempotency completion share one transaction.
- Reservation reclaim and completion lock the creation record and validate the
  lease token, fencing stale owners.
- Endpoint-secret authorization returns a bounded use window; the executor
  validates its exact signature timestamp before calling the signer.
- KEK startup inventory unions current, unexpired previous, and unexpired
  generation-matching creation-replay ciphertext.

## 5. Security And Privacy

Both credentialed Python clients explicitly disable environment proxies and
reject redirects. Generator checkpoint erasure still removes API keys; only
sanitized merchant/resource identifiers survive in `generator_resources`.
Merchant creation stores HMACed idempotency/request identities and a merchant
ID, never the raw idempotency key or raw API key. Exact API-key replay is
derived under the server pepper and verified against the merchant's stored
hash. Customer idempotency responses contain IDs rather than email or phone.

## 6. Failure Modes And Operational Signals

The hostile sequences are: proxy-configured credential forwarding, waiting
across secret expiry, removing a KEK still required by replay/overlap state,
process death after `REQUIRES_NEW` reservation commit, and abandoning a run
without cleanup identity. The final sequences add caller retry-classification
drift and client death after merchant/customer response but before all local
persistence. Active leases conflict or serialize; expired leases reclaim;
changed/malformed keys fail before mutation. Each has deterministic regression
or migration proof. No new secret-bearing output was introduced.

## 9. Stripe/Mastercard-Style Review Narrative

The important correction is boundary completeness. “Loopback-only” includes
proxy routing; “valid before expiry” means valid at signature time; “KEK
ready” covers every decryptable product path; independently committed unfinished
work requires a fenced lease; and a client cannot close a remote commit gap
with local persistence alone. The implementation proves these claims at real
HTTP, clock, SQLite, H2, PostgreSQL-lock, and migration boundaries.

## 12. Post-Closure Staff Review: ER-0031 Through ER-0033

The completion claim reopened again. Three green-looking boundaries were still
too weak:

- a mutation lease could expire before `IdempotencyService` locked its row,
  allowing a second supplier and therefore a future duplicate processor call
- merchant idempotency identity changed when the HMAC pepper rotated
- generator verification reads could cumulatively outlive the run lease

The first-principles rule is that a fence protects only work that happens after
the fence is owned. The operation transaction now locks and validates the
idempotency row before invoking any supplier. The PostgreSQL proof expires a
100-millisecond lease while the supplier is deliberately blocked and observes
the contender waiting rather than running.

Secret-derived identity needs a rotation protocol, not merely a key version.
V16 adds unique identity aliases for every configured current/previous pepper;
all aliases point to one creation record, while API-key replay uses that
record's original derivation version. Missing still-required versions stop
startup. This protects tenant truth without persisting raw idempotency or API
keys.

Workflow ownership must cover reads as well as writes. The generator now
heartbeats immediately before and after every HTTP request and rejects a lease
shorter than one request timeout. A real delayed server keeps three requests
running longer than the original lease while a second process remains unable
to acquire ownership.

No work is deferred: all three affect frozen payment, security, and operations
promises. In a Stripe/Mastercard-style review, the defense is the exact forced
sequence: expire during supplier execution, rotate between commit and replay,
remove a required old key at startup, and exceed the original workflow lease
with successful network calls.

## 13. Boundary-Family Recovery: ER-0034 And ER-0035

The next review found that ER-0032 had repaired one observed HMAC consumer
instead of the entire persisted-digest family. The same rotatable pepper still
fed general request hashes, webhook endpoint idempotency identities, card
fingerprints, and customer pseudonyms. That creates three different failures:
a valid mutation replay can conflict after rotation, a webhook key can appear
new and bind another request, and routine replay-key rotation can split fraud
and ML correlation.

V17 now records the original request-hash version for general idempotency and
adds tenant-scoped current/previous aliases for webhook creation. Startup
inventories every key version still required by a live replay window; expired
records can restart or be retired without retaining a dead key forever. PAN,
email, and phone pseudonyms moved to the separately configured stable
`THAAP_CORRELATION_PEPPER`, so routine replay-key rotation cannot rewrite fraud
identity.

Generator resource lineage now persists explicit immutable `resource_type`
metadata with each step. Existing SQLite journals receive an additive column
and deterministic backfill before resume, including interrupted steps and the
tenant-isolation verifier merchant. Runtime resource recording no longer
guesses from a step-name suffix.

The design-review lesson is blunt: a key-rotation review starts from every
persisted output and downstream consumer, not from the class where one defect
was observed. A cleanup-lineage review reconciles every resource-producing plan
step against durable inventory, not a sample of familiar names.

Final proof resolves `ER-0034` and `ER-0035`: the hostile subset passes 68
Java tests, the complete backend passes 265 tests, and the repository Python
suite passes 67 tests, all with zero failures, errors, or skips. V17 clean and
V16-to-V17 migration proof, rolling-version PostgreSQL contention, live versus
expired key retention, stable correlation digests, typed legacy-journal
backfill, and verifier-merchant cleanup lineage are all executable.
