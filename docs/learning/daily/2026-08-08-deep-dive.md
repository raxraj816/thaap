# Daily Deep Dive: 2026-08-08

Subject: clock precision as a persistence invariant, and why ten weeks of green tests proved
nothing about it.

## 1. System Goal

- **What did we build?** A single definition of the precision a persisted instant may carry
  (`DatabaseInstant`), a `Clock` bean that cannot produce a finer one, and a build-time gate that
  fails on any call site minting time outside it.
- **Why does this matter in a payments/fraud platform?** Every payment, authorization, refund,
  ledger entry, fraud decision and domain event is ordered and audited by timestamp. A field whose
  value changes between the create response and the next read is a field an auditor cannot
  reconcile and a consumer cannot cache.
- **What production risk does this address?** A live public-contract violation on Linux: the
  create response and every subsequent read disagreed on `createdAt` for the same immutable record.

## 2. Plain-English Design Brief

- **Simplest mental model.** The database can hold six decimal places of a second. The JVM on Linux
  hands you nine. If you keep all nine, you are holding a number your database will never agree
  with. Round it off once, at the place time enters the system, and the disagreement cannot start.
- **What would go wrong without this design?** What did go wrong: 53 production sites each decided
  independently whether to truncate, roughly thirty of them added the truncation defensively after
  the fact, and the ones that did not were invisible on the only hardware anyone tested on.
- **What did we choose to build now?** Source-level truncation plus a source-scanning regression
  gate, because the defect class cannot be caught at runtime on a developer machine.
- **What did we intentionally defer?** Removing the ~30 now-redundant scattered
  `.truncatedTo(ChronoUnit.MICROS)` calls. They are harmless and removing 30 lines during an
  incident fix mixes concerns. Recorded as an open question instead.

## 3. Code Map

- `com.thaap.payments.time.DatabaseInstant` — owns the rule. `now()`, `of(Instant)`,
  `tick(Clock)`. The only place `ChronoUnit.MICROS` should need to appear for this purpose.
- `com.thaap.payments.event.EventTimePrecision` — retained for its existing callers, now a thin
  delegate, so the codec's enforcement and the application's minting share one definition.
- `com.thaap.payments.config.JacksonConfiguration#clock` — the injected clock, now ticked. This is
  the highest-leverage line in the change: it fixes every `Clock`-injecting service at once.
- `webhook.WebhookExecutionConfiguration`, `webhook.WebhookEndpointSecretService` — the two
  production classes that constructed their own `Clock.systemUTC()` and therefore did not benefit
  from the bean.
- Entities (`PaymentIntent`, `PaymentAttempt`, `Refund`, `LedgerEntry`, `FraudDecision`,
  `AuthenticationChallenge`, `WebhookEndpoint`, `AuditLog`, others) — set `createdAt`/`updatedAt`
  at construction and cannot inject a bean, which is why they need the static helper.
- `time.DatabaseInstantTests` — behavioural pins plus `noSourceFileMintsTimeOutsideThisClass`.

## 4. Request/Data Flow

1. A request enters a controller; the service reads time from the injected `Clock`, which now ticks
   at microseconds.
2. Tenant, validation and idempotency checks run. `GovernedControlService.exactInstant()` rejects
   any caller-supplied instant finer than microseconds with `400` — unchanged, and correct.
3. A domain object is constructed. Entity constructors stamp `createdAt` via
   `DatabaseInstant.now()` rather than `Instant.now()`.
4. The row is written. PostgreSQL `timestamp(6)` stores it exactly, because there is nothing left
   to round.
5. A domain event is encoded. `CanonicalEventCodec.validateInstant()` refuses a payload timestamp
   carrying sub-microsecond digits — unchanged, and correct. The response is shaped from the same
   in-memory value that the database now holds byte-for-byte.

## 5. Database Invariants

- **What must always be true?** For any persisted instant, the value the application returned when
  it wrote the row equals the value a later read of that row returns.
- **What enforces it?** The column type `timestamp(6)` defines the ceiling; `DatabaseInstant`
  makes the application respect it; `CanonicalEventCodec.validateInstant()` enforces it at the
  event boundary; the source scan prevents regression.
- **What breaks if it disappears?** Nothing throws. Ordering stays correct, money stays balanced.
  What is lost is the ability to compare a returned timestamp with a stored one — which is exactly
  what idempotent replay, digest equality and lineage reconciliation do.

## 6. Security And Privacy Invariants

- No secrets are involved. One adjacent point: `WebhookEndpointSecretService` was among the classes
  holding an untruncated clock, and secret rotation timestamps participate in ordering decisions.
  Nothing was exploitable, but rotation windows should be reasoned about in a unit the datastore
  can represent.

## 7. Fraud/ML Relevance

- Fraud labels, review resolutions and decision events are reconstructed from the domain event
  stream and compared by canonical bytes. A timestamp that serialises differently in memory than in
  storage breaks digest equality between a live projection and a rebuilt one — which is precisely
  what `RiskOperationsEventPostgreSqlConcurrencyTests` and the Phase 5 rebuild suites assert.
- Nothing was added to the feature surface. The lineage that already existed simply became sound on
  the platform that runs it.

## 8. Tests As Proof

- **Riskiest invariant:** `noSourceFileMintsTimeOutsideThisClass`, because it is the only check
  that can fail on a developer machine. Verified by planting a violation and watching it fail.
- **Behavioural proof:** truncation-not-rounding; a ticked clock truncating a nanosecond source;
  5,000 consecutive readings free of sub-microsecond digits.
- **Environment proof:** the full suite executed on Linux against a confirmed nanosecond clock —
  1384 tests, 0 failures — and on macOS for regression — 1384 tests, 0 failures.
- **Happy-path only:** none of the swept call sites gained new assertions; they inherit the
  existing suites, which is the point.
- **Missing test a Staff engineer would ask for next:** one that asserts a create response and an
  immediately subsequent read return byte-identical timestamps for the same record, at the HTTP
  boundary. Today that is proven indirectly, by 48 tests that happened to compare the two.

## 9. Staff Engineer Review Notes

- **Tradeoff:** coarser time. Two rapid calls can now share a microsecond. Accepted because macOS
  has always behaved this way and the suite is green there, so Linux is converging on the
  already-tested behaviour rather than entering new territory.
- **Risk reduced:** a public-contract inconsistency on every Linux deployment, and an entire class
  of future defect made visible at build time.
- **Kept reversible:** `DatabaseInstant` is one small class; the sweep is mechanical and revertible;
  the input guards were not touched, so no contract was loosened to make tests pass.
- **Dangerous to overbuild now:** replacing the ~30 redundant truncations, or introducing a
  repository-wide time abstraction beyond `now`/`of`/`tick`. The invariant is narrow; the fix
  should stay narrow.

## 10. Explain-Back Questions

1. **What problem did this slice solve?** The application minted timestamps finer than PostgreSQL
   can store, so a returned instant stopped matching its own row on Linux.
2. **Why did we solve it this way?** Because truncating at 315 call sites is a rule enforced by
   memory, and on macOS a forgotten one is undetectable.
3. **What production risk did this reduce?** `createdAt` disagreeing between the create response
   and every later read of the same record.
4. **What did we defer and why?** Removing the redundant scattered truncations — harmless, and
   mixing cleanup into an incident fix obscures both.
5. **What tests prove the important invariants?** `DatabaseInstantTests`, and the full suite
   executed on Linux where the defect can actually exist.
6. **Design-review framing?** "Our persistence layer has a resolution ceiling. We were minting
   values above it in 53 places and could not observe the consequence, because our development
   platform truncates in the kernel. We moved the rule to the source and added a build-time gate,
   then verified on the target platform rather than the development one."

## 13. Interview Narrative

- The tradeoff I made was coarser timestamps — microsecond rather than nanosecond — in exchange for
  the application and its database never disagreeing about a stored instant.
- The invariant I enforced was that a persisted instant read back equals the instant returned when
  it was written.
- The production risk I reduced was a public-contract violation on every Linux deployment, where
  `createdAt` differed between the create response and every later read.
- I deferred removing roughly thirty now-redundant truncation calls, because cleanup mixed into an
  incident fix hides both.
- The tests prove it on the platform where the defect can exist: the full suite on Linux against a
  confirmed nanosecond clock, plus a source scan that fails the build on any reintroduction and was
  itself verified by watching it fail.

## 14. Second Subject: The Registry Thirty-One Test Classes Share

The rest of this deep dive is about time. This section is about a different mechanism found the
same day, and recorded here because the daily note left its cause open and the cause turned out to
matter more than the symptom.

### 14.1 The mental model

Starting a Spring application context is expensive — beans, Flyway migrations, a connection pool,
a web layer. Running that once per test class would make a 200-class suite unusable, so Spring's
test framework caches contexts and reuses them. The cache key is the *merged context
configuration*: the test class's `@SpringBootTest` attributes, inlined properties, active profiles,
initializers, and any mock-bean definitions. Two classes whose configuration matches receive the
**same context object**, and therefore the same singleton beans.

That is a good trade, and it has one consequence nobody writes down: a singleton bean in a cached
context is shared mutable state across test classes, and the sharing is invisible at the call site.
Nothing in `PaymentInvestigationObservabilityTests` says "you also hold the registry belonging to
thirty other classes". You learn it by noticing that its two annotations happen to match another
file's, character for character.

### 14.2 Why a metrics registry is the worst place for this to bite

Micrometer's `MeterRegistry` is a map from meter id to meter. Most application code registers
meters lazily on use — `registry.counter(name, tags).increment()` both creates and increments — so
a removed counter silently reappears the next time anything touches it. Self-healing state hides
its own corruption.

A gauge is the exception. A gauge observes a value that already exists, so it is naturally
registered once, at construction, and never again. In `DecisionIntelligenceMetrics` every meter but
two was a counter or timer; the two exceptions were the bulk-backlog gauges. When a neighbouring
test emptied the shared registry, everything grew back except the two meters that matter most —
the only signal that reports a bulk run whose worker died.

So the same event produced 319 healthy meters and two missing ones, which is exactly the shape that
makes a bug look supernatural.

### 14.3 The failure sequence, in order

1. Surefire picks a class order. Its default is `filesystem`: roughly sorted on APFS, arbitrary on
   ext4.
2. `PaymentInvestigationObservabilityTests` runs. Its `@BeforeEach` deletes every
   `thaap.decision_intelligence.*` meter so its cardinality assertions see a clean slate.
3. The two backlog gauges go with them. They are never re-registered, because the constructor that
   registers them runs once per context and that context is already built.
4. `ReviewBulkBacklogReadinessTests` runs later against the same context. `registry.find(name)`
   returns null; the helper reports its `-1.0` sentinel; four assertions fail.
5. On a Mac, step 2 happens *after* step 4, and the suite is green.

Nothing throws. Nothing logs. The only difference between the green run and the red one is which
file the operating system listed first.

### 14.4 Why the first investigation went wrong, and what to do instead

Three hypotheses were tested and killed, all of them about Micrometer: `clear()` elsewhere, context
cache eviction, weak-reference collection. Each experiment was sound. The search space was wrong.

The generalisable mistake is a scope error in ruling something out. `meterRegistry.clear()` at
`PaymentIntentConfirmContractTests:89` was correctly excluded, because that class's context key
genuinely differs — but the conclusion recorded was "no test removes these meters" rather than
"that test does not". One `grep -rn 'registry::remove' src/test` distinguishes the two and names
the file.

The second lesson is about instrumentation. The earlier probe identified registries by
`System.identityHashCode`, which cannot tell *one registry lost two meters* from *these are two
registries*. A diagnostic that cannot separate the two possible answers cannot settle the question,
however much output it produces. The replacement stamped each registry with a monotonic sequence
number the program assigns, and added two canary meters registered once in the same constructor as
the gauges — a counter and a strongly referenced gauge. Their survival, in the same registry, in
the same run, eliminated identity confusion, general removal, and weak-reference collection in a
single observation.

### 14.5 The enforcement boundary

The fix is isolation, not repair. `@ExclusiveMeterRegistry` contributes a `ContextCustomizer`
whose identity is the annotated class; a context's cache key includes its customizers, so that class
gets a context — and a registry — nobody else shares. This is the same extension point Spring uses
for bean overrides, which is exactly why `PaymentIntentConfirmContractTests` already had accidental
isolation from its `@MockitoSpyBean`. It is applied to both classes in the suite that mutate a
registry.

An earlier revision used an inert property with an identical effect on the cache key. It worked and
it was still wrong: a magic string names nothing, gets copied without its reason, and can only be
enforced by text matching. The annotation carries its intent in its name, and the gate checks a type
rather than a substring.

Isolation is a property of a file that a future author will not know to copy, so it is enforced
rather than remembered. The scan in `MeterRegistryIsolationTests` fails the build when a `@SpringBootTest` class prunes a
registry without declaring ownership. Following `ER-0098`, the gate was verified by watching it
fail: the property was removed, the scan failed and named the file, the property was restored, the
scan passed.

The suite's ordering is the other half. `surefire.runOrder` is now pinned to `alphabetical`, which
makes a local result and a CI result comparable for the first time. Pinning alone would have
re-hidden this defect — an arbitrary order is what exposed it — so a separate CI job runs the same
suite at `-Dsurefire.runOrder=random` and republishes the seed that replays any failing ordering.
Determinism where you need comparability, shuffle where you need discovery.

### 14.6 Tests as proof

- `MeterRegistryIsolationTests.noSharedSpringContextTestRemovesMetersFromTheRegistryItShares` —
  the invariant that review could not see, verified by watching it fail.
- `MeterRegistryIsolationTests.theBacklogGaugesComeBackAfterSomethingRemovesThemFromTheRegistry` —
  the self-healing behaviour of the gauges, pinned as behaviour rather than as commit history.
- The full suite at `-Dsurefire.runOrder=reversealphabetical`, which is the ordering that failed
  4/4 before this change.

### 14.7 How to defend this in a design review

The claim is not "we fixed a flaky test". It is that a test suite had an undeclared shared-state
boundary, that boundary was written through, and the only signal reporting a stalled bulk run
disappeared as a result — visibly in CI, and only in half of the possible run orders. The response
was to identify the mechanism by experiment rather than ship against an unexplained one, to remove
the sharing rather than to repair the damage, to make the ordering that concealed it comparable
across machines while keeping a deliberate shuffle that can still find its successors, and to
enforce all of it with a gate that has been observed failing.

### 14.8 What is deliberately not done

The isolation gate covers the `MeterRegistry`, because that is the boundary that broke. The same
invisible sharing applies to every other mutable singleton in a cached context, and no gate covers
those. That is recorded as an open question in the daily note rather than solved speculatively:
the honest scope of this change is one proven boundary, not a claim about all of them.

### 14.9 The gate's first two runs, and the claim it disproved

The randomized-order job failed on its first execution and again on its second, both times on
classes unrelated to meters, and both times on the same sentence written two ways:

- `PaymentInvestigationScopeBoundaryTests` proved its fixture was not vacuous with
  `SELECT DISTINCT card_fingerprint FROM payment_methods` — unscoped, so it counted the previous
  class's rows and read 2.
- `PaymentInvestigationNavigationScopeBoundaryTests` failed in setup, because
  `RiskWorkspaceScenario.drainProjection` replays every event in the database and a leftover event
  whose subject a later class deleted returns `QUARANTINED` rather than `APPLIED`.

The audit that followed is the part worth keeping: 15 of the 41 classes using `RiskWorkspaceScenario`
never cleaned the database, and 26 did. The 13 that had not yet failed were the same defect waiting
for the right ordering. All 15 now clean, and the fingerprint assertion is scoped to its own
merchants, because an assertion should measure the thing it claims about. §14.8 predicted that the
`MeterRegistry` was one instance of a wider sharing problem; this is the database instance of it,
found within an hour by the mechanism built for it rather than by inspection.

The same job also disproved something written in its own comment. The claim was that a failure is
reproducible from the printed seed with one flag. It is not, across platforms: surefire shuffles the
list the directory scanner produced, and that input order is filesystem order, so one seed is two
different permutations on ext4 and APFS. Replaying CI's seed on macOS gave an entirely different
ordering and a different failure. `runOrder=alphabetical,random` does not compose either — surefire
honours only the first entry, which was checked rather than assumed. The workflow now states the
limitation and carries a `workflow_dispatch` seed input, so a failing ordering is replayed on a
runner of the same platform, where it genuinely is reproducible.

Both corrections point the same way as the rest of this day: **the claim and its proof have to be
the same object.** A precision rule enforced by memory, a diagnostic keyed on an identity hash, an
assertion scoped to the wrong table, a reproducibility promise written from how a flag reads — each
looked right and none of them had been executed.

## 15. Third Subject: Making An Artifact Say What It Is, And Refuse What It Cannot Do

Chapters 61 and 62 are two halves of one idea. An artifact must be able to state
its own identity, and a runtime must refuse to pretend it has capabilities it
does not have. Both are about a system telling the truth about itself when
nobody is watching closely.

### 15.1 The mental model: provenance is answered by the process, not by the pipeline

During an incident, the question is "what is running?" There are three places to
look and only one of them is trustworthy.

The **deployment record** — a task definition, a pipeline log, a commit message —
says what somebody intended to deploy. It is correct until a rollback, a manual
override, or a failed deploy that half-succeeded.

The **image digest** says what was pulled. It is unambiguous and it is a hash:
to turn it into a commit you need a lookup table that lives somewhere else and
is itself a thing that can be wrong.

The **running process** knows. It is executing specific bytes, and if those
bytes were stamped at build time with the commit that produced them, the process
can be asked directly, over HTTP, by someone with no shell access.

Spring Boot supports the third one out of the box: the `build-info` goal writes
`META-INF/build-info.properties` into the jar, and the actuator's
`BuildInfoContributor` serves it at `/actuator/info`. What is not out of the box
is *where the commit comes from*, and that is where this became interesting.

### 15.2 The constraint that shaped the design

`apps/payments-api/.dockerignore` excludes `.git/`. That exclusion is a security
control from Chapter 60 — a broad `COPY . .` with a working tree behind it is how
a live token ends up in a published layer — and it means the image build has no
git repository to read.

So the usual answer, a git-reading Maven plugin, produces exactly nothing in the
only build whose provenance matters. The commit has to arrive the way every other
deployment input arrives: passed in.

```text
git rev-parse HEAD
  -> docker build --build-arg THAAP_BUILD_COMMIT=<sha>
       -> ARG in the build stage
            -> mvn -Dthaap.build.commit=<sha> package
                 -> build-info.properties  ->  /actuator/info
       -> ARG in the runtime stage
            -> org.opencontainers.image.revision  ->  registry metadata
```

Two outputs from one input, which is the property that makes them checkable
against each other. `scripts/release-identity-check.sh` builds the image and then
asserts the label and the in-image `build-info` agree, because an image whose
metadata and whose application disagree is worse than one that reports nothing:
it answers the incident question confidently and wrongly.

### 15.3 Why the build timestamp was removed

`build-info` records a timestamp by default, and excluding it looks like
throwing away information. It is the one recorded property that is not a function
of the source. Keep it, and building the same commit twice produces two different
artifacts — which quietly retires the reproducibility promise Chapter 60 had just
spent a whole chapter establishing. The commit is the timestamp that matters;
when it was compiled is a fact about the build machine, not about the software.

### 15.4 The second half: a system that appears correct while protecting nothing

`application.yml` gives eight security-relevant values an empty-string default.
That is deliberate and right: a stack that cannot start without a secrets
ceremony is a stack nobody runs, and Chapter 60's whole claim is that a stranger
with only Docker can start THAAP.

Now deploy that same default. With an empty `THAAP_REVIEW_NOTE_ENCRYPTION_KEY`
the application starts, passes all sixteen readiness indicators, serves traffic,
and writes analyst notes about named customers in a way the product's own
documentation calls encrypted. Nothing throws. Nothing logs. The damage is
discovered later, by someone else, in a form that cannot be undone, because the
notes were already written.

This is the failure shape the repository has already taken a position on.
`DomainEventProducerGate` refuses to start on a catalogue version it cannot serve
rather than dropping events, and the reasoning generalises: **a component that
cannot do its job must fail loudly rather than serve a weaker promise than the
one it advertises.**

### 15.5 Where the refusal runs, and why that is not a detail

A `@PostConstruct` check on a bean would also stop the application. It would stop
it *after* Hikari had opened a connection pool to the production database and
after Flyway had taken the migration lock.

An `EnvironmentPostProcessor` runs while the environment is being prepared, before
the application context exists. Nothing has been constructed, nothing has been
dialled, nothing has been locked. When the answer is "this instance must not run",
the cheapest possible moment to say so is before it has done anything at all.

`RuntimeSecretContractStartupTests.refusesBeforeItOpensADatabaseConnection` proves
this the only way it can be proven: it points the datasource at
`jdbc:postgresql://127.0.0.1:1/...`, which nothing can reach, blanks one secret,
and requires the failure to still be the secret contract. If the gate were a bean,
that test would fail with a connection error — and the error message would be the
evidence that the instance had already touched the database.

### 15.6 The rules, and the reasoning behind the three that were not asked for

The plan required absent, empty, and below-minimum-entropy. Three more were added.

**Distinctness.** Every reused value is individually strong, so this is not a
shape problem. Sharing the hash pepper with the correlation pepper ties credential
rotation to fraud identity: a routine key roll silently splits every customer's
PAN, email and phone history in two. Sharing one KEK across the three ciphers
means a single disclosure decrypts analyst notes, webhook signing secrets and
authentication replays together. Independent rotation and independent compromise
are the properties being bought.

**No value this repository publishes.** The strongest argument for this rule is
that it contradicts the instinct behind the first two: the published KEKs are
genuinely random 32-byte keys and pass every entropy test that could be written.
They are still unusable, because they are printed in a file anyone can read. A
rule about strength cannot see that. Only a list can.

**No placeholder markers.** The list catches what was published; this catches what
someone will publish next. It is scoped honestly: every marker contains a hyphen
or a letter outside the hexadecimal alphabet, so `openssl rand -hex 32` and
`openssl rand -base64 32` cannot trip it, and it therefore cannot reach a Base64
KEK at all. The test says so by only covering opaque tokens, rather than quietly
passing on three of eight.

### 15.7 Holding a hand-written list honest

`RequiredRuntimeSecret` is a hand-written enumeration of what matters, which is
the classic way this control decays: a ninth secret is added, nobody updates the
enum, and the gate goes on passing while enforcing seven eighths of a promise.

Three drift locks, each closing a different route:

| Drift | Lock |
|---|---|
| A secret-shaped property exists that the contract does not enforce | `RuntimeSecretContractDriftTests` walks `application.yml`, collects every `${THAAP_*}` placeholder whose leaf ends in `token`, `pepper` or `encryption-key`, and requires that set to equal the enum |
| The error message names an environment variable the application does not read | The same class asserts each property resolves from exactly the variable the contract names |
| A newly committed default becomes an accepted production secret | The same class scrapes the compose file, both READMEs and the test fixtures, and requires every value it finds to be refused |
| The reference document and the application disagree | `scripts/runtime-configuration-reference-check.py`, in the readiness gate: undocumented variables, phantom variables, stale defaults, and any secret marked `Required` that the gate does not enforce |

The singular/plural distinction in the leaf pattern is load-bearing:
`previous-hash-peppers` and `secret-decryption-keys` are rotation *sets*, and an
empty rotation set is what every deployment that has never rotated looks like.
Requiring them would make an ordinary state look broken.

### 15.8 The defect this work produced, and what caught it

The gate was first registered at
`META-INF/spring/org.springframework.boot.env.EnvironmentPostProcessor.imports`.
That is the correct path in Spring Boot 3. Spring Boot 4 moved the interface to
`org.springframework.boot.EnvironmentPostProcessor` and loads implementations
through `SpringFactoriesEnvironmentPostProcessorsFactory` — `spring.factories`,
with no imports-file path for this extension point at all.

The file was therefore a registration that registered nothing. It produced no
warning, because an unread resource is indistinguishable from an absent one.
Fifty-five unit tests passed against rules that were wired to no application.

`RuntimeSecretContractStartupTests` caught it on its first run, by starting a real
`SpringApplication` with a secret removed and finding that it started perfectly
happily. That is the whole argument for the class: **a validator's rules and a
validator's reachability are two different claims, and only one of them can be
proven without starting the thing.** It is the same lesson as the rest of this
day — `CanonicalEventCodec.validateInstant()` was right for a week and silent for
a week — arriving through a different door.

### 15.9 Explain-back questions

1. Three places record which commit is deployed. Why is the running process the
   only one worth trusting during an incident?
2. `.dockerignore` excludes `.git/`. Explain the chain that gets a commit SHA into
   `/actuator/info` anyway, and why a git-reading Maven plugin cannot.
3. Why is the build timestamp excluded from `build-info`, when recording it is
   free and it is obviously useful?
4. An empty `THAAP_REVIEW_NOTE_ENCRYPTION_KEY` produces a system where nothing
   throws and every health check is green. Describe what has actually gone wrong,
   and why it cannot be repaired afterwards.
5. Why does the refusal run as an `EnvironmentPostProcessor` rather than in a
   bean? Name the two things a bean-based check would have already done.
6. The published webhook KEK in `compose.yml` is a genuinely random 32-byte key.
   Explain why no entropy rule can reject it, and what does.
7. `THAAP_HASH_PEPPER` and `THAAP_CORRELATION_PEPPER` are both 32-character
   opaque tokens. Why does the gate refuse to let them be the same string?
8. Fifty-five tests passed against a gate wired to nothing. What class of claim
   were they proving, and what class were they not?
