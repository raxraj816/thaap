## 2. Payment Processing Concepts Learned

- A webhook URL is part of the merchant delivery contract. Sending a correctly
  signed payment event to the wrong path is still incorrect payment-system
  behavior.
- Migration rejection must happen before schema mutation when the old database
  cannot provide authoritative lineage.
- At-least-once delivery requires exactly-once merchant effects to come from a
  durable consumer uniqueness transaction, never from receiver memory.
- A processor authorization answers what the issuer/network simulator did; it
  does not answer what THAAP's fraud engine decided.
- Phase closure is a product contract, not a chapter count: capture, void,
  refund, accounting, webhook, and processor evidence must agree end to end.

## 3. Fraud Detection Concepts Learned

- Webhook payload and destination stability protect downstream fraud operations:
  analyst or merchant automation must receive the same event at the intended
  route across retries.
- No fraud feature, model, score, or label semantics changed in this recovery.
- The `SUSPECTED_FRAUD` processor fixture remains independent from the current
  `ALLOW` / `RULES_NOT_ENABLED` FraudDecision. Treating one as the other would
  poison future labels and decision-quality evaluation.

## 4. Security Concepts Learned

- Java `US_ASCII` encoding replaces unrepresentable characters; it does not
  automatically produce URI percent escapes.
- `URI.toASCIIString()` is the representation boundary that preserves Unicode
  path/query meaning as UTF-8 percent-encoded wire text.
- Existing percent escapes must remain stable or a security fix can accidentally
  double-encode the merchant's route.
- Demo reports are security-sensitive product artifacts. Chapter 20 scans raw
  test-card values, buyer PII, API keys, signing secrets, and every generated
  idempotency key before atomically publishing evidence.
- A loopback URL check constrains only the first request. Redirect handling is a
  second destination boundary because a default client may copy authentication
  headers to the next origin.

## 7. Bugs, Surprises, Or Tradeoffs

- A response-parser boundary-family review did not automatically cover the
  request-line encoder; custom protocols require bidirectional grammar review.
- PostgreSQL would roll back the late migration failure, but H2 retained partial
  DDL. Preflight order therefore matters even when production uses PostgreSQL.
- A script that contains test commands is not proof that its canonical
  invocation executes them.
- A parser that identifies the right deduplication key is not a replay-safe
  consumer until the key and business effect share durable transaction state.
- A green active-worker metric test says nothing about the worker-disabled
  operating mode.
- The roadmap still called webhook execution “remaining” after Chapter 19 and
  grouped fees, payouts, and disputes into Phase 2 despite their actual owner
  boundaries. Phase closure required correcting the source of truth, not
  expanding V1 into unrelated accounting.
- The first hostile Chapter 20 report review found that the sanitizer checked
  only confirm idempotency keys and did not explicitly scan the one-time
  signing secret. The boundary family was expanded before closure to all three
  per-fixture keys plus the returned signing secret.
- The post-closure merge review found that `urllib` followed redirects and
  preserved custom credential headers. That escaped because origin tests
  validated input syntax but never exercised the HTTP client's effective
  destination; it is now recorded and resolved as `ER-0021`.
