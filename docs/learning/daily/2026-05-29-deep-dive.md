# Daily Deep Dive: 2026-05-29

## 1. System Goal

We created the THAAP foundation: product scope, architecture source of truth,
ADRs, glossary, diagrams, repository layout, and the learning-note system.

This mattered because THAAP is not a single feature. It is a long-running
payments, fraud, ML, and operations simulator. Without a clear architecture
contract, later implementation would drift into isolated demos instead of a
coherent platform.

## 2. Plain-English Design Brief

The simplest mental model:

- `docs/IMPLEMENTATION_MASTER_PLAN.md` says what we are building.
- Architecture docs explain why the system is shaped that way.
- ADRs record durable choices.
- The repo layout separates current deployables from later services.
- Learning notes turn implementation into an apprenticeship track.

What would go wrong without this:

- Fraud code could be built without real payment lifecycle context.
- ML work could start before labels, features, and replay exist.
- LLM agents could accidentally enter real-time authorization.
- Service boundaries could be split too early, slowing learning and increasing
  coordination cost.
- Future code could use inconsistent terms such as `STEP_UP` versus
  `REQUEST_3DS`.

## 3. Code And Documentation Map

- `README.md` introduces THAAP and points to the authoritative master plan.
- `docs/IMPLEMENTATION_MASTER_PLAN.md` defines scope, roadmap, API surface,

- `docs/VISION.md` captures product intent.

## 5. Database Invariants

No database schema existed yet. The important future invariants were identified:

- `merchant_id` must become the tenant discriminator.
- mutating payment APIs need idempotency.
- money movement must eventually use balanced double-entry ledger groups.
- fraud decisions need persisted audit trails.
- features and model predictions need lineage back to payment attempts.

The key design decision was to avoid inventing schema before the domain model
had enough behavior to prove it.

## 6. Security And Privacy Invariants

The first security boundary was architectural:

- no raw PAN persistence
- no CVV persistence
- tokenized simulator boundary for card data
- no LLMs in real-time authorization
- GenAI agents can recommend offline but cannot mutate live payment, rule, or
  model state

This protected the project from building an impressive but unsafe fraud demo.

## 7. Fraud/ML Relevance

Day 1 was crucial for ML because it prevented premature modeling.

The plan established:

- one training row per future `PaymentAttempt`
- delayed labels from reviews and chargebacks
- feature snapshots for decision-time truth
- time-based splits instead of random primary splits
- ReplayEngine before serious rule/model threshold changes
- advanced models only after EDA and baseline analysis justify them

The Staff-level lesson: fraud ML architecture starts with payment event
lineage, not model selection.

## 9. Staff Engineer Review Notes

Tradeoff:

- We chose modular monolith first instead of splitting services immediately.

Risk reduced:

- Early microservice boundaries would create operational complexity before the
  domain was understood.

Kept reversible:

- Later service folders exist for model serving, analytics, and agents, but
  they do not force premature runtime separation.

Dangerous overbuild:

- Starting with GNNs, agents, or dashboards before payment attempts, labels,
  and replay would create architecture theater instead of usable platform
  capability.

## 13. Interview Narrative

Practice saying this out loud:

- The tradeoff I made was to start with a modular monolith and strong domain
  contracts, while deferring service decomposition until latency, scale,
  ownership, or operational risk requires it.
- The invariant I established was that payments, fraud decisions, ML features,
  and future agent workflows must share consistent lineage and tenant scope.
- The production risk I reduced was premature complexity: real-time LLM calls,
  speculative ML, and service splitting before the core payment lifecycle is
  stable.
- I deferred real PSP integration, graph ML, and agents because the simulator
  must first prove payment lifecycle, auditability, and fraud labels.
- The proof for Day 1 was not code tests; it was coherent source-of-truth
  documentation, ADRs, canonical terms, and a roadmap that future code can be
  reviewed against.
