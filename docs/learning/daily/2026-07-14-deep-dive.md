# Daily Deep Dive: 2026-07-14

This note is for end-to-end understanding of a Staff-level implementation slice.
It should make the code explainable, not merely documented.

## 1. System Goal

- We built Chapter 30's confirm-time velocity and typed negative-control loop.
  It detects repeated identities and governed known-bad identities before a
  processor call, while preserving exact evidence for analysts and replay.
- The production risks addressed are self-counting/retry inflation, Redis
  ambiguity becoming false zero, raw identity leakage, cross-tenant controls,
  mutable historical explanations, and weak controls suppressing safety rules.

## 2. Plain-English Design Brief

- Velocity is a bounded attendance register: Redis records a stable pseudonymous
  logical-attempt member and returns how many *other* members are inside a window.
- A fraud list is an append-only, typed set of negative candidates. Configuration
  is PostgreSQL truth; evaluation produces a candidate, not an override.
- Without stable members, retries inflate counts. Without explicit UNAVAILABLE,
  an outage looks like safe traffic. Without immutable versions/evaluations, a
  later list edit rewrites why an old payment was blocked.
- We built four velocity dimensions and all eight promised list identity families.
  We then built Chapter 31 merchant policy as constrained versioned data rather
  than a programmable rule language. Historical replay impact and later ML
  scoring remain outside this slice because they require separate truth.

## 4. Request/Data Flow

Describe the flow step by step:

1. `POST /payment_intents/{id}/confirm` authenticates a merchant and reserves the
   idempotency key before locking the PaymentIntent.
2. The transaction creates one PaymentAttempt and optional immutable RiskContext.
3. Velocity evaluates four applicable HMAC dimensions through exact Lua; typed
   lists evaluate every active immutable version at one timestamp.
4. Base rules, velocity, and list candidates aggregate with
   `BLOCK > REVIEW > REQUEST_3DS > ALLOW`; no evaluation short-circuits.
5. FraudDecision, snapshot, typed features, rule results, velocity observations,
   and list evaluations flush before any processor call.
6. The winning action creates processor, review, or authentication truth, and
  idempotency stores the exact committed response. Any later failure rolls the
  database work back; Redis compensation removes exact reserved members.
7. When an active merchant policy exists, every finite threshold is evaluated
   against the same immutable snapshot before aggregation. The copied evaluation
   evidence survives future activation or retirement without historical lookup.

## 5. Database Invariants

- One velocity row exists per merchant/attempt/dimension, with an exact AVAILABLE
  or UNAVAILABLE shape and optional one-time null→FraudDecision attachment.
- One list code is tenant-unique; versions, entries, lifecycle actors, matched
  entries, attempts, and decisions share the same merchant through composite FKs.
- HMAC and canonical entry shapes are mutually exclusive; ALLOW is rejected by
  both API logic and SQL checks; intervals are ordered; lifecycle targets are
  semantically validated.
- PostgreSQL rejects UPDATE/DELETE for lists, versions, entries, events, and
  evaluations. Removing these protections would let current configuration alter
  historical decision explanations.
- A merchant configuration guard serializes profile/policy lifecycle. Activation
  atomically retires the prior active version or rolls back with it still active;
  confirm shares the same merchant ordering boundary.

## 6. Security And Privacy Invariants

- PAN/card fingerprint, email, email domain, IP, customer, device, and session
  inputs are normalized then transformed through purpose-separated correlation
  and/or versioned HMAC domains. Management responses expose only safe IDs,
  type, action, reason, and time.
- Redis keys/members and durable list rows contain no raw high-cardinality identity.
  The principle is data minimization with unlinkable purpose domains: compromise
  of one control surface should not create a universal identity join key.

## 7. Fraud/ML Relevance

- These immutable observations/evaluations become replay inputs, analyst
  explanations, rule/model features, and later list-effectiveness labels.
- We did not call a velocity count a probability, infer labels from a block, or
  claim replay impact analysis before the Phase 4.5 ReplayEngine exists.
- `merchant.risk_tier` is a governed categorical feature with explicit STANDARD
  default provenance. Policy severity is still not fraud probability or model
  output, and activation is not a training label.

## 9. Staff Engineer Review Notes

- We accepted bounded synchronous Redis work under the PaymentIntent transaction
  to keep one decision/attempt/compensation boundary. Tight timeouts and explicit
  REVIEW degradation bound the risk; a future outbox/coordination redesign stays
  reversible behind the coordinator.
- Lists use constrained types/actions rather than executable rules. This reduces
  injection, accidental safety overrides, and review complexity.
- The hostile pass changed two boundaries. Confirm and lifecycle mutation now
  coordinate through shared/exclusive merchant locks, and management/evaluation
  metrics emit only after commit or rollback is known. These changes prevent a
  mixed point-in-time decision and false committed telemetry.
- Building policy DSLs, distributed streams, or ML inference here would blur the
  narrow confirm-time truth and weaken proof quality.
- Policy uses two-person governance because configuration can systematically
  block or add friction to every future payment. Approval and activation are
  separate so review of immutable bytes cannot silently become deployment.
- The live demo caught a locking read inside read-only preview. Splitting pure
  preview lookup from mutation locking preserved both PostgreSQL correctness and
  the promise that preview is bounded evaluation, not serialized production truth.

## 14. Integrated Phase 4 Closure Mental Model

Phase 4 is one feedback/control loop, not nine unrelated APIs:

1. Confirm freezes safe context, velocity, list, policy, rule, and action
   lineage before processor behavior.
2. Authentication or review can continue the same attempt without rewriting
   its fraud decision.
3. Analyst resolution appends an action and label; post-authorization evidence
   can open a later case and invoke the same PaymentIntent-first refund boundary.
4. Chargebacks allocate only remaining captured value and preserve fraud versus
   non-fraud label semantics.
5. Suspected card-testing incidents aggregate committed evidence. Redis limits
   request pressure, but never becomes incident, payment, or fraud-label truth.

The important composed failure rule is ordering by authority. A Redis outage at
the Chapter 34 request guard returns 503 before confirm creates payment/fraud
truth. If the request passes that guard and the narrower velocity observation is
ambiguous, Chapter 30 records UNAVAILABLE lineage and raises the fraud action to
REVIEW. These outcomes are intentionally different because they occur at
different enforcement boundaries.

In a Stripe/Mastercard-style review, defend this design by separating:

- durable PostgreSQL facts from ephemeral Redis coordination;
- recommendation from operator authorization and money movement;
- original point-in-time decision from later evidence/labels;
- definite rate-limit exceedance (429) from dependency ambiguity (503);
- simulator/merchant-ingested evidence from network-confirmed truth.
