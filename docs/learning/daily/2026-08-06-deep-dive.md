# Deep Dive: 2026-08-06 — Two Credentials, One Header, And The Contract That Lied

Phase 6 implementation status: COMPLETE

This dive is about a single HTTP header, `X-Thaap-Scenario-Runner-Token`, and how
publishing it slightly wrong in a machine-readable contract produces a silent
data-integrity failure that no test in the repository would have caught.

## The domain problem first

A payments sandbox has to solve something real: a merchant needs to generate
test payments that exercise the fraud engine, and those payments must not
contaminate the merchant's live fraud statistics. If synthetic volume lands in the
same denominator as real traffic, every rate an analyst reads — confirmed-fraud
rate, review yield, false-positive proxy — is wrong, and wrong in a direction
nobody notices, because the synthetic payments are designed to look plausible.

THAAP solves it with a second credential that is not an authority. The merchant
API key answers *who are you*. The scenario runner token answers *is this traffic
real*. In `MerchantContextArgumentResolver`:

```java
private TrafficOrigin resolveTrafficOrigin(HttpServletRequest request) {
    String suppliedToken = request.getHeader(SCENARIO_RUNNER_TOKEN_HEADER);
    if (suppliedToken == null || suppliedToken.isBlank()) {
        return TrafficOrigin.MERCHANT_API;
    }
    if (scenarioRunnerToken.isBlank() || !MessageDigest.isEqual(...)) {
        throw new PublicApiException(SCENARIO_RUNNER_CREDENTIAL_INVALID, ...);
    }
    return TrafficOrigin.SYNTHETIC_SCENARIO;
}
```

Read the three branches carefully, because the entire failure follows from them:

1. **Absent** → `MERCHANT_API`. Silent. This is the correct behaviour for an
   ordinary merchant call, and it is also what happens when a client that *meant*
   to send the token fails to.
2. **Present and wrong** → hard failure. Loud.
3. **Present and right** → `SYNTHETIC_SCENARIO`.

Branch 1 is where the bug lives. A missing qualifier is indistinguishable from a
genuine live payment.

## How OpenAPI models "two credentials"

OpenAPI has exactly two ways to describe a credential-bearing header, and they
mean different things.

**As a security scheme** referenced in an operation's `security`:

```yaml
security:
  - merchantApi: []
    scenarioRunner: []
```

Entries *within* one list item are ANDed. This says: both are required. A
generated client injects both automatically from its configured `api_key` map,
without the caller passing anything.

**As an explicit header parameter**:

```yaml
parameters:
  - in: header
    name: X-Thaap-Scenario-Runner-Token
    required: false
```

This says: optional, and the caller supplies it per call. The generated client
exposes it as a keyword argument and sends nothing unless the caller passes it.

Both are legal. Both generate working code. They produce completely different
clients.

## What the committed contract actually said

At the start of the session the contract used the *parameter* form on all 42
merchant operations — including the six scenario operations. The wrapper,
meanwhile, had been written against an older contract that used the *scheme*
form, and configured `api_key={"scenarioRunner": token}`.

So: the caller passed `Credentials(scenario_runner_token=...)`. The wrapper stored
it under a security scheme no operation referenced. The generated operations
expected a keyword argument nobody passed. The header never left the process.

The server took branch 1. Every sandbox payment the published quickstart created
was recorded as `MERCHANT_API`.

Nothing threw. The quickstart printed `THAAP quickstart complete`.

## Why every existing test passed

This is the part worth internalising. The repository had, at that moment:

- 1250 backend tests, including `DeveloperScenarioContractTests`, which drives the
  scenario API with `trustedHeaders(merchant)` — building the header **by hand** in
  the test, not through the SDK.
- 14 SDK tests, including one asserting exactly one credential and one version
  header per request — which passed because it asserted the header the client
  *did* send on each path, and had been written against the old behaviour.
- A regeneration gate that would have caught the drift in one command, and had
  never been run.

Every layer was individually tested. The failure lived in the seam between the
published contract and the shipped client, and the only artifact that spanned that
seam was the gate nobody executed.

## The correction, and the mistake inside the correction

The obvious fix is to publish the scheme form for the operations that require the
token. So: which operations require it?

I read `DeveloperScenarioController`, found `requireScenarioRunner(context)` in
three of six handlers, and concluded the answer was three. I changed the contract
generator, the contract check, and the Java assertions to encode a three/three
split, complete with a confident comment explaining why the split was correct.

It was wrong. `DeveloperScenarioService.requireSynthetic` guards all six service
methods. `create`, `get` and `report` reject a token-less merchant just as firmly
as `claim`, `completeStep` and `fail` do — the guard simply lives one layer down.

Two things about this are worth keeping:

**The evidence was already in the repository.** An existing test asserts that
`POST /developer/scenario-runs` returns 403 for an ordinary merchant. I had read
that file. I generalised from the controller anyway.

**It is the same error as the original defect.** The original contract
generalised over the path prefix and got it wrong in one direction; the original
check generalised over the path prefix and got it wrong in the other; I
generalised over one layer of the call stack and got it wrong in a third. Three
independent attempts, one shared method: infer the rule from a convenient
surface rather than from the enforcement point.

## The structural fix

The durable answer is not more careful reading. It is putting the declaration
where the enforcement is, and having every consumer derive from it:

```java
@PostMapping("/scenario-runs")
@RequiresScenarioRunner
public ResponseEntity<RunView> create(MerchantContext context, ...)
```

`PublicOpenApiConfiguration` reads the annotation off the handler mapping to
decide which operations publish `scenarioRunner` as a required scheme.
`OpenApiSecurityContractTests` reads the same annotation to derive the enforced
boundary it compares the contract against. Neither holds a list. Neither
generalises over a path.

There is a subtlety in that test worth flagging: it now derives *expected* from
the annotation and *actual* from the contract, which are two different artifacts,
so the comparison still has content. If I had instead hardcoded the same list in
both the generator and the test, the test would have been circular — it would have
proven the list equals itself.

## What "correct" looks like now

- Six scenario operations: `security: [{merchantApi: [], scenarioRunner: []}]`,
  and the contract check rejects any that additionally publish the bare header,
  because a client could then send the header and believe it had satisfied the
  scheme.
- Thirty-nine other merchant operations: the optional header parameter, which is
  the honest description of branch 1 — the token is accepted and changes traffic
  origin, but the call succeeds without it.
- The generated client injects the token automatically for the six, and the
  wrapper additionally sets it as a default header for a scenario-configured
  client, because a per-call qualifier that is forgotten fails silently.
- `Credentials` refuses to hold merchant and risk-operator authority at once, and
  refuses a scenario token without a merchant key, so the invalid combinations
  cannot be constructed rather than merely being discouraged.

## The test that would have caught it

```python
def test_scenario_traffic_is_tagged_synthetic_and_live_traffic_is_not() -> None:
    ...
    assert live_intent.traffic_origin == "MERCHANT_API"
    assert synthetic_intent.traffic_origin == "SYNTHETIC_SCENARIO"
```

Two clients, same endpoint, different traffic origin, asserted on the response the
server actually produced. It is three lines and it directly encodes the product
promise. It did not exist because every test that touched scenario traffic built
its headers by hand, and so could never observe the client failing to send one.

The general form: when a client is supposed to *cause* a server-side
classification, assert the classification, not the header. Asserting the header
tests the test's own fixture.

## How I would defend this in a design review

The strongest thing to say is not that the bug was found. It is that the bug was
found by executing a gate that had been written, reviewed, and never run — and
that the process correction is mechanical rather than aspirational. Both OpenAPI
gates are now invoked by `commit-readiness-check.sh`, and
`commit_readiness_check_tests.py` fails if either is deleted. A future engineer
cannot quietly return to the state that produced `ER-0096` and `ER-0098`.

The weakest thing to say is that a matrix row said `PENDING` with an honest note
about what was missing, and that honesty was not enough. The row read as *nearly
done*. It was, in fact, hiding a P1 defect that would have corrupted a merchant's
fraud metrics. "Asserted by the script but not demonstrated by a recorded run" is
not a caveat. It is a red build nobody has looked at yet.
