## 2. Payment Processing Concepts Learned

- Payment processing must be first-class scope, not just a wrapper around fraud detection.
- Fraud systems only make sense when connected to the payment lifecycle.
- V1 should be a full card-payment simulator, not a real PSP integration.
- `PaymentIntent` is the merchant-facing payment container.
- `PaymentAttempt` is the concrete scoring, authorization, and audit unit.
- Authorization and capture are different lifecycle stages.
- Cancel/void applies before capture; refund applies after capture.
- Chargebacks/disputes are post-capture customer claims and can become fraud labels.
- Idempotency is mandatory for mutating payment APIs to prevent duplicate captures, refunds, and confirmations.
- Webhooks are part of the merchant integration contract, not an optional later detail.
- Even simulated money movement should use double-entry ledgering.

## 3. Fraud Detection Concepts Learned

- Real-time fraud decisions must be deterministic, bounded, observable, and auditable.
- LLMs must not run inside the real-time authorization path.
- Canonical fraud actions are `ALLOW`, `BLOCK`, `REQUEST_3DS`, and `REVIEW`.
- `REQUEST_3DS` is the canonical step-up action; we should not introduce `STEP_UP` as a separate enum.
- Fraud decisions should persist feature snapshots, rule execution results, reason codes, model version, ruleset version, risk score, risk level, and latency.
- Rules need explicit ordering: `REQUEST_3DS`, `ALLOW`, `BLOCK`, then `REVIEW`.
- Velocity counters must exclude the current payment being evaluated.
- Manual review is both an operations workflow and a fraud-label feedback source.
- Chargebacks are delayed labels and must be treated carefully in ML training.
- Blocked or abandoned payments may have unknown true outcomes, which matters for evaluation.

## 4. Security Concepts Learned

- Raw PAN must never be persisted.
- CVV must never be persisted.
- Test card data can enter API memory only long enough to produce token, fingerprint, BIN, last4, card country, funding type, and simulator behavior.
- Sensitive request bodies must not be logged.
- Email, phone, IP, and similar identity fields should be hashed or masked where practical.
- GenAI agents can inspect and recommend, but cannot mutate live payment, rule, or model production state.
- Rule activation, refunds, chargebacks, review decisions, and future model promotions are high-risk actions that require audit logs.

## 5. Architecture / Design Notes

- Chose modular monolith first with `payments-api` as the core backend.
- Initial backend stack: Java 25, Spring Boot 4.0.6, PostgreSQL, Redis, Flyway, Actuator.
- PostgreSQL is the transactional source of truth.
- Redis is for velocity counters, temporary cache, and idempotency acceleration, not durable truth.
- Kafka, ClickHouse, Neo4j, object storage, MLflow, model serving, and GenAI agents come in later phases.
- The processor simulator should sit behind a `ProcessorAdapter` so a real PSP adapter can be added later.
- The master plan is authoritative; research docs are reference only.
- Detailed architecture was split into:
  - system context and components
  - payment processing flows
  - fraud decisioning and ML
  - data, events, ledger, and storage
  - security, observability, and operations
- Day 1 repository structure keeps runnable V1 work in `apps/payments-api` while preserving later service boundaries for model serving, analytics, and fraud intelligence agents.
- Initial ADRs now capture modular monolith, simulator-first, no LLM in authorization, card-only V1, double-entry ledger, tokenized card-data boundary, and Docker Compose first with AWS as reference cloud.

## 7. Bugs, Surprises, Or Tradeoffs

- The first master plan was too compressed compared with the research plan, so we expanded it with missing implementation-critical details.
- We decided the master plan should not copy all research prose, but it must contain every implementation-critical decision.
- We avoided early microservices to keep the learning loop fast.
- We intentionally deferred real PSP integration to avoid compliance and integration complexity before the domain model is solid.
- We kept `.DS_Store` untouched because it is macOS metadata and not relevant to docs structure.
- Important architecture feedback surfaced missing detail around PCI DSS scope, deployment target, rate limiting, V1 feature store abstraction, synthetic data priority, offline replay, and threshold calibration.
- We agreed synthetic data is critical path and should begin in Phase 1, not wait until ML.
- We agreed ReplayEngine is required for safe rule/model/threshold changes.
- Important ML feedback corrected the plan: advanced fraud modeling should be data-first and evidence-driven. GNNs, embeddings, and graph features should emerge from EDA/error analysis, not be prescribed before data exists.
- Day 1 intentionally created placeholders instead of fake scaffolds for services that are later-phase deployables.
