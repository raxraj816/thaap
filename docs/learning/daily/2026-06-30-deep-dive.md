# Daily Deep Dive: 2026-06-30

This deep dive records the reopened Chapter 19 review and the correction to the
review process itself.

## 1. System Goal

- Make Chapter 19 webhook delivery defensible under payments-grade review.
- Preserve truthful merchant-facing delivery evidence across crashes, retries,
  endpoint disable, DNS stalls, resolver saturation, malformed HTTP responses,
  weak key configuration, and legacy migration.
- Replace repeated reactive fixes with a proof loop that starts from failure
  sequences rather than from the implementation.

## 2. Plain-English Design Brief

A webhook worker has three kinds of truth:

- It definitely did not start HTTP.
- It definitely completed writing the request.
- It crossed the dispatch boundary, but the final outcome is unknowable.

The old shape blurred those cases. That is dangerous in payments because
merchants may fulfill orders, update risk workflows, or deduplicate side effects
from webhook evidence. The corrected design records a durable dispatch marker
and tri-state send evidence, then lets lease recovery close the attempt
honestly.

The second correction is methodological. A green test suite is only useful when
the tests came from the product promises and hostile failure sequences. If tests
are selected after reading the code, they mostly prove the code’s current
imagination.

## 3. Code Map

- `WebhookDeliveryClaimService` owns due claiming, final pre-dispatch endpoint
  validation, expired lease recovery, and disabled-expired in-flight
  convergence. Attempt mutation paths use an explicit pessimistic attempt lookup
  after the delivery row is owned.
- `WebhookDeliveryAttempt` owns durable attempt evidence:
  `dispatchStartedAt` plus nullable `httpRequestSent`.
- `WebhookDeliveryExecutor` signs and validates target policy before marking
  dispatch, then marks dispatch immediately before HTTP.
- `WebhookDeliveryFinalizationService` maps nullable request-sent evidence to
  retryable, terminal, success, or `OUTCOME_UNKNOWN` attempt outcomes.
  Finalization locks the attempt row before mutating it, in addition to the
  delivery-owned claim-token validation.
- `SocketWebhookHttpTransport` owns exact outbound protocol behavior: bounded
  request deadline, partial-write ambiguity, informational response handling,
  and status range validation.
- `WebhookHostResolver` wraps platform DNS with an application deadline and
  bounded worker/queue capacity.
- `WebhookTargetResolutionException` separates transient resolver
  infrastructure failures from terminal target-policy violations.
- `WebhookEventEnvelopeFactory` owns serializer-backed runtime payload
  construction, UTF-8 payload-size enforcement, and representation-boundary
  hashing before signing.
- `JacksonConfiguration` now uses explicit module registration for stable
  Java-time behavior instead of classpath-wide module discovery.
- `V9__harden_webhook_delivery_execution` owns legacy delivery normalization
  and serializer-backed payload backfill before installing stronger
  constraints.
- `CHAPTER_19_INVARIANT_PROOF_MATRIX.md` is the proof ledger: 19 invariants,
  all PASS after the fresh hostile review.

## 4. Request/Data Flow

1. A due delivery is claimed in a short transaction and an attempt is appended.
2. The worker loads signing material, signs the immutable payload, and validates
   target policy before dispatch.
3. Immediately before HTTP, `prepareForDispatch` locks the endpoint then the
   delivery, validates the endpoint is still `ACTIVE`, validates the claim
   token, marks `dispatchStartedAt`, sets `httpRequestSent = null`, and renews
   the lease.
4. The socket transport sets request-sent evidence to:
   - `false` before writing starts,
   - `null` while a partial write is possible,
   - `true` only after the request flush completes.
5. Finalization persists success, retryable failure, terminal failure, or
   outcome unknown only if the claim token and attempt number still match.
6. Lease recovery closes expired pre-dispatch attempts as known no-send and
   expired post-dispatch attempts as unknown.
7. Endpoint disable prevents new claimable work and any claimed work that has
   not reached the durable dispatch-started marker; it does not prevent
   recovery from closing an already in-flight expired attempt.

## 5. Database Invariants

- `webhook_delivery_attempts.http_request_sent = false` means known no-send.
- `http_request_sent = true` means the request write completed.
- `http_request_sent = null` is allowed only for post-dispatch in-progress or
  `OUTCOME_UNKNOWN` attempts.
- `dispatch_started_at` must exist before true or unknown send evidence.
- Legacy `PENDING` rows with `next_attempt_at` become `RETRY_SCHEDULED` before
  V9 retry constraints are installed.
- Expired `DELIVERING` rows remain selectable for recovery even if the endpoint
  has been disabled.
- A disabled pre-dispatch claim closes as terminal `ENDPOINT_DISABLED` with
  `http_request_sent=false` and no `dispatch_started_at`.

## 6. Security And Privacy Invariants

- DNS cannot consume unbounded worker or memory resources because resolution has
  an application deadline and bounded pool/queue.
- Resolver deadline and capacity failures are retryable known-no-send attempt
  evidence; they are not proof that the merchant configured an unsafe target.
- A configured webhook encryption key must decode to 32 bytes and must not be
  the known-bad all-zero value.
- Numeric HTTP statuses outside `100..599` are transport failures, not
  persisted protocol truth.
- Informational `1xx` responses are consumed only as interim protocol messages;
  the final status decides delivery outcome.
- Attempt evidence, logs, metrics, and APIs do not expose secrets, signatures,
  URLs, payload internals, PAN, CVV, buyer PII, or idempotency material.
- Signed payload JSON is produced through a JSON serializer rather than string
  concatenation. This matters because the payload bytes are not cosmetic
  formatting; they are the exact merchant-verifiable contract signed by HMAC.
- Local/test HTTP is accepted only on loopback for simulator fixtures. The
  payload and signature header are plaintext on that local socket, so the mode
  cannot be treated as shared-environment merchant transport.
- `TD-0003` owns old/new signing-secret rotation windows. A claimed worker may
  have already loaded the previous secret before a concurrent rotation commits;
  production-grade merchant operations need an explicit overlap and expiry
  contract before shared onboarding.

## 7. Fraud/ML Relevance

Future fraud and analyst loops will rely on replayable event identity and
delivery evidence. A false “not sent” attempt can hide duplicate merchant side
effects. A false “sent” attempt can create an audit trail that merchants cannot
reconcile. Explicit unknown truth is the only safe state for model/label lineage
later.

### Final hostile recovery evidence

- `socketTransportRejectsTruncatedFinalResponseHead` proves a `204` status line
  without the terminating response-head boundary cannot become false success.
- `socketTransportBoundsFinalResponseHeaders` proves the same parser bound
  applies to the final response, not only informational responses.
- `unknownHostAndResolverFailuresRemainRetryableKnownNoSendOutcomes` and

  the DNS outcome taxonomy beyond timeout and resolver-capacity cases.
- Four PostgreSQL endpoint-order tests establish rotation-before-disable,
  disable-before-rotation, routing-before-disable, and disable-before-routing.
  Each records the competing backend PID and observes a real PostgreSQL lock
  wait before releasing the owning transaction.
- The endpoint-disable API response now preserves its durable subscription
  set while continuing to omit the raw signing secret.
- A fresh PostgreSQL 16 schema migrated through V9 and passed live application
  startup plus the public `503 -> 204` signed webhook demo. The stable event,
  exact payload, payment status, and ledger reconciliation all passed.
- An older local volume with a pre-final uncommitted V9 draft failed Hibernate
  validation because it lacked `dispatch_started_at`. That fail-closed behavior
  was preserved; verification moved to an isolated fresh database instead of
  deleting or mutating local developer data.

## 9. Staff Engineer Review Notes

- The tradeoff is a slightly richer attempt state machine in exchange for
  honest merchant-facing evidence.
- The architectural correction is endpoint status gating new work and
  pre-dispatch claimed work, while still allowing recovery of already
  dispatch-started expired work; resolver infrastructure failures are a
  retryable worker condition, not merchant target truth.
- The process correction is stronger than “be more careful”: completion now
  requires a frozen matrix with honest provenance, explicit hostile failure
  sequences, all PASS statuses, escaped-review root causes, a closure dossier,
  and a readiness command that names both current artifacts.
- Severity closure is executable: unresolved P0/P1 and frozen-promise P2
  escaped findings block the chapter. Future-scale P2 work needs canonical
  `TD-NNNN` ownership instead of a vague “later.”
- ADR-0009 makes mature infrastructure the default. The Chapter 19 socket
  transport remains only because validated-address pinning with original
  HTTP/TLS identity is the required SSRF boundary; the ADR limits its protocol
  surface and names the replacement trigger.
- `ER-0001` through `ER-0005` make the earlier misses measurable. The dominant
  categories were weak proof and missing failure sequences, so the process now
  changes proof selection before the next chapter rather than merely adding
  more Chapter 19 tests.
- The dangerous overbuild would be adding a new distributed queue or replay
  console before the core V1 truth model is correct.

## 10. Explain-Back Questions

Answer these without looking at the code:

1. Why is `OUTCOME_UNKNOWN` safer than pretending a crashed post-dispatch
   attempt was not sent?
2. Why should endpoint disable stop new work but still allow expired in-flight
   recovery?
3. Why is a claimed delivery still stoppable until `dispatch_started_at` is
   persisted?
