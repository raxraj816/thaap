## 2. Payment Processing Concepts Learned

- A PaymentIntent is the merchant-facing payment container. It represents the customer's intent to pay before confirm, authorization, capture, settlement, refund, dispute, or fraud-label workflows exist.
- Idempotency belongs at object creation, not only at money movement, because merchants retry create requests after network failures and must not accidentally create duplicate payment containers.
- Idempotency is a mutation state machine, not merely a response cache. The
  important states are `IN_PROGRESS` while the first mutation is running and
  `COMPLETED` once the response is safe to replay.
- `REQUIRES_CONFIRMATION` is the correct initial status because no PaymentAttempt, fraud decision, processor authorization, or ledger effect has happened yet.

## 3. Fraud Detection Concepts Learned

- PaymentIntent alone is not the fraud scoring unit. It gives future fraud flows stable context, but fraud lineage begins when a PaymentAttempt exists.
- PaymentAttempt is the correct fraud/ML row grain because it binds the
  merchant, PaymentIntent, PaymentMethod, attempt number, future processor
  result, future FraudDecision, and future labels.
- Tenant-scoped customer linkage is already fraud-relevant because future velocity, identity, card, and graph signals depend on connecting the right merchant's objects without cross-tenant leakage.
- The Chapter 6 webhook record is operational lineage, not fraud evidence yet; it proves downstream delivery intent without pretending that fraud scoring has run.

## 4. Security Concepts Learned

- Cross-object lookups must be tenant-scoped in the repository/database boundary, not trusted from client-supplied IDs.
- Public PaymentIntent responses should expose only payment-container state, not idempotency request hashes, stored response bodies, API-key hashes, signing-secret hashes, or unrelated merchant state.
- The idempotency request hash is an internal control, keyed with `SensitiveValueHasher`, and should be used only to detect changed replay bodies.
- Operation binding is a security and correctness control: same-body mutations
  such as future empty capture and cancel requests must not replay each other's
  responses just because the idempotency key matches.

## 5. Architecture / Design Notes

- Chapter 6 did not require a schema migration because Chapter 4 already created the PaymentIntent, idempotency, and webhook-delivery storage needed by the slice.
- `IdempotencyService` wraps the create path, scopes records by merchant and key, binds the key to the operation and serialized request hash, and replays the stored response for matching completed requests.
- Chapter 8 split idempotency into three transaction moments: committed
  reservation, mutation plus completion, and rollback cleanup for failed
  mutations.
- Chapter 9 intentionally creates lineage but not outcomes: fraud decision,
  processor authorization, 3DS result, and final status mapping remain nullable
  until their owner chapters populate them.
- `PaymentIntentController` remains the boundary for request validation, tenant-scoped customer ownership checks, domain object creation, and webhook-delivery scheduling.
- The create path stays intentionally before money movement. PaymentAttempt now
  exists for confirm lineage, while fraud decision, processor authorization,
  final status mapping, and ledger writes are still separate later-chapter
  concerns.
- Deferral is now treated as an engineering decision, not a default pace limiter: defer only when a missing invariant, boundary, lineage source, side-effect review, or correctness guarantee makes the work unsafe.
- Chapters are now product-building units, not time boxes. Daily notes remain dated work journals and do not limit throughput.

## 7. Bugs, Surprises, Or Tradeoffs

- Most Chapter 6 runtime behavior was already present from earlier scaffolding; the real gap was proving it with direct contract tests.
- We resolved the Chapter 8 design question by choosing a committed reservation
  plus mutation/completion transaction. That makes in-progress duplicates
  visible without caching failed mutation responses.
- We also did not add fraud decision or processor side effects. Creating those from PaymentIntent create would blur the boundary between create and confirm.
- The user correctly challenged a too-conservative daily pattern: safe sequencing should not become slow execution. The new rule keeps correctness-based deferrals while encouraging dependency-ready pull-forward.
- We intentionally did not implement expired in-progress cleanup. The row now
  stores `expires_at`, but cleanup/takeover after process crash needs an
  operations policy and likely a reliability worker.
- We intentionally left PaymentIntent status as `REQUIRES_CONFIRMATION` after
  Chapter 9 confirm. That lets Chapter 9 prove attempt lineage and attempt
  numbering without pretending processor/fraud outcomes exist.
