## 2. Payment Processing Concepts Learned

- Payment truth must commit before external HTTP. A slow or broken merchant
  callback cannot hold open or roll back confirm, capture, cancel, refund,
  ledger, audit, or idempotency work.
- A webhook event is historical integration truth. Retrying must reuse the exact
  event ID and payload rather than reading the payment's latest mutable state.
- HTTP delivery is at least once. A sender can crash after the merchant receives
  the callback but before THAAP records success.

## 3. Fraud Detection Concepts Learned

- Webhook events will later carry review, chargeback, dispute, policy, and
  incident signals to merchant systems, so immutable event identity is part of
  fraud-operations lineage.
- Chapter 19 deliberately limits payloads to safe event/resource identifiers.
  Richer fraud context should not leak buyer PII, card fingerprints, rules, or
  model internals through a generic callback.

## 4. Security Concepts Learned

- The existing endpoint stores only a signing-secret prefix and SHA-256 hash.
  A one-way hash cannot recover the original HMAC key.
- Treating the stored hash as the signing key would let a database-only attacker
  forge callbacks. Chapter 19 therefore uses AES-256-GCM encryption under a
  separately configured key-encryption key while retaining prefix/hash metadata.
- Calling merchant-controlled URLs creates SSRF and egress risk. The plan now
  requires redirect denial, scheme/allowlist policy, validated DNS targets,
  private/metadata-address rejection, timeouts, and safe local-loopback rules.
- `InetAddress.isSiteLocalAddress()` is not a global-routability oracle: it
  misses IPv6 ULA and special IPv4 ranges such as CGNAT. Security policy must
  classify the actual address bytes against explicit ranges.
- Payloads, responses, logs, metrics, and attempts all have explicit sensitive
  data exclusions.

## 5. Architecture / Design Notes

- `WebhookEvent` owns stable event identity and exact canonical payload bytes.
- `WebhookDelivery` owns routing, aggregate state, retry time, and claim lease.
- `WebhookDeliveryAttempt` owns numbered HTTP evidence and safe outcome data.
- Delivery states are now unambiguous: `PENDING`, `DELIVERING`,
  `RETRY_SCHEDULED`, `SUCCEEDED`, and `EXHAUSTED`.
- The worker claims in one short transaction, performs HTTP outside a
  transaction, and finalizes under a claim token in another transaction.
- A batch is a processing budget, not a lease bundle. Each attempt is now
  claimed immediately before dispatch, and unknown runtime failures remain
  available for lease recovery rather than becoming false terminal truth.
- Key/DNS preparation can itself outlive a lease, so ownership is renewed under
  a delivery row lock immediately before HTTP. Finalization performs the same
  locked token check, removing a stale check-then-write race.
- A kill switch is a concurrency protocol, not just a status field. Rotation
  and disable require exclusive endpoint locks, while event routing requires a
  shared lock until its delivery rows commit.
- Retry schedule is immediate, then 1 minute, 5 minutes, 30 minutes, and 2
  hours, with exhaustion after the fifth failed attempt.
- Phase 5 still owns the general domain outbox/Kafka boundary; Chapter 19's
  webhook event envelope does not pretend to be that outbox.

## 7. Bugs, Surprises, Or Tradeoffs

- The original Chapter 19 sentence "sign with stored webhook signing secrets"
  was not implementable because only irreversible hashes are stored.
- Architecture documents disagreed on `FAILED` versus `EXHAUSTED` and treated a
  delivery as if it were also an attempt. The updated plan separates those
  concepts.
- Existing endpoints cannot be silently upgraded to encrypted secrets. The
  honest migration state is `REQUIRES_SECRET_ROTATION`.
- Exactly-once HTTP receipt is impossible without cooperation from the merchant.
  Stable event IDs and merchant deduplication are the defensible contract.
- Disabling during an in-flight failing request initially allowed a misleading
  retry-scheduled state. Finalization now rechecks endpoint status and records a
  terminal `ENDPOINT_DISABLED` outcome, so no stranded retry remains.
- The first concurrency test proved one-row lock exclusion but not batch lease
  safety. With 20 claims, a 30-second lease, and serial five-second requests,
  later rows could expire before dispatch. Just-in-time claiming removes that
  state instead of tuning around it.
- Socket `SO_TIMEOUT` is an inactivity timeout per read, not a total request
  deadline. A watchdog now closes the active socket when the attempt's
  wall-clock budget expires.
- Green delivery tests initially hid two operational gaps: rotation could
  reactivate a disabled endpoint, and metrics observed only normal
  finalization. The closure tests now exercise the state races and recovery
  paths directly.
