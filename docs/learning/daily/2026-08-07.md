## Three things worth remembering

### 1. A proof field is a promise that something exists, and nothing checked it

The gate validated the *shape* of a row — required fields present, `Status: PASS`, no
unfinished-work marker. That is exactly the check a well-formed obsolete claim passes.
Every Phase 5 matrix is `PRE_IMPLEMENTATION`, so its `Proof` fields are written in future
tense as obligations. Implementation then consolidated each domain into one contract
class plus a `*PostgreSqlTests` subclass, and `Status` flipped to `PASS` without anyone
rewriting `Proof`. Chapter 50 planned eleven suites and shipped seven test methods.
Chapter 46 planned ten and shipped 302 lines across two classes.

The consolidation was sound engineering. The defect was that the durable traceability
artifact was never updated to say so, so it points at names that resolve to nothing.

### 2. `ER-0098`'s own correction was never enforced

`ER-0098` states that removing `openapi-contract-check.py` from the readiness run would
fail a test. It would not have. The readiness tests stubbed each checker and asserted
only the exit code — an unreferenced stub is simply never executed, and the run still
exits zero. The correction was recorded, believed, and inert for a chapter.

The fix is a marker-file test that asserts *invocation*, verified by deleting a gate line
and watching it fail, then restoring it and watching it pass. The wider lesson: when a
process correction is written, its enforcement must be executed against the failure it
claims to prevent. Nobody had ever deleted the line to check.

### 3. A matrix with only one status cannot describe reality

Every gap row was `PASS` while naming a suite that did not exist, because `PASS` was the
only value the gate accepted. A reviewer who noticed a thin row had nowhere to record it
short of blocking a merged phase — which is not a move anyone makes at the end of a
closure pass. The vocabulary shortage was not cosmetic; it was the reason the condition
survived review.

Adding `PARTIAL` cost about thirty lines because only one line in the whole repository
enforced row status. The absence was never load-bearing, only unexamined.

## Where production turned out to be short

Writing the tests is how we learned production did not keep three promises:

- `ProjectionRebuildMetrics` emitted no duration and no lease-recovery signal, though
  `ProjectionRebuildStore` had recorded `LEASED` versus `LEASE_RECOVERED` as durable
  events all along. Added both, plus a `recovered` flag on `ProjectionRebuildLease` so
  the distinction is carried rather than inferred from the fencing epoch — the epoch
  increments on every claim, so inferring it would have been wrong.
- `TransactionalDomainEventWriter` emitted nothing at all. Added
  `DomainEventWriterMetrics`. Its rejection counter fires immediately rather than after
  commit, because the rejecting transaction is about to roll back and a deferred counter
  would make an integrity failure indistinguishable from an ordinary rollback.

## Two things that looked like findings and were not

- Merchant events publish the API key prefix as the actor id, and `SecretHasher.prefix`
  is literally `rawApiKey.substring(0, 12)`. Keys are `"thaap_test_"` — eleven characters
  — plus a UUID, so the published prefix is a fixed namespace plus **one hex character**.
  Not a leak. But the margin is one character, so the fragility is now held by
  `thePublishedMerchantActorPrefixCannotGrowIntoSecretMaterial` rather than by
  coincidence.
- I reported the replay execution probe as having zero call sites. Wrong: my grep was
  `probe\.` and the field is `executionProbe`. Both methods are wired at exactly the two
  documented points.
