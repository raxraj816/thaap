# Weekly Architecture Review: 2026-W26

## 1. Scope Reviewed

- Chapter 15: capture with balanced ledger entries.
- Chapter 16: local synthetic payment-risk scenarios and Staff-review hardening.
- Important diffs: ledger migration, ledger domain/service/API, capture
  authorization proof, capture audit log, capture rollback tests, README and
  learning trail updates.

## 2. What Changed Architecturally

- Capture is now a real money-truth mutation instead of only a PaymentIntent
  state transition.
- Approved authorization is required before capture.
- Capture writes a two-entry balanced ledger group before moving the
  PaymentIntent to `CAPTURED`.
- Merchant-scoped ledger reads now exist through `GET /ledger/entries`.
- Synthetic scenarios now traverse public payment APIs, assert durable
  authorization/fraud lineage, and fail closed on false ledger truth.

## 3. Risks That Decreased

- A captured payment can now be defended with durable accounting evidence.
- Idempotent replay no longer risks duplicate capture ledger, webhook, or audit
  truth.
- Ledger rows are tenant-scoped from the first Phase 2 money-movement chapter.
- Ledger persistence failure rolls back capture state and idempotency
  completion.
- Synthetic generation is restricted to loopback targets so test traffic cannot
  silently contaminate shared risk or ML data.

## 4. Risks That Remain

- Refunds do not yet write ledger reversal entries.
- Cancel/void after authorization is not yet processor/accounting complete.
- Fees, disputes, reserves, payout settlement, and partial capture/refund are
  still deferred.
- `TD-0001` authoritative server-side synthetic-origin classification is owned by Phase
  4.5, **Developer Scenario Runner And Traffic-Origin Governance**. Payments
  Core is the schema/API DRI and Risk Operations owns runner policy and
  analytics exclusion; resolution is required before a shared scenario runner.
- `TD-0002` resumable interrupted runs are owned by Phase 7, **Synthetic Generator V2 Run
  Orchestration**. ML/Data Platform is the run-state/retry DRI and Payments Core
  owns idempotent mutation dependencies; resolution is required before
  scheduled or dataset-scale generation.
- The canonical technical debt register and automated readiness validator now
  preserve debt IDs, ownership, triggers, done criteria, and closure evidence
  independently of agent memory.
- Debt governance tests reject missing owners, vague destination phases,
  evidence-free resolution, and master-plan IDs that are absent from the
  register. Open debt also becomes commit-blocking when it has not been reviewed
  within 35 days.
- Debt lifecycle is intentionally limited to `OPEN`, `IN_PROGRESS`, and
  `RESOLVED`; accepted risk is a review disposition, and P0 findings are
  explicitly rejected from deferral.

## 5. Test Review

- Strongest tests: balanced capture ledger entries, idempotent capture replay,
  double-capture rejection, invalid declined/3DS states, cross-merchant ledger
  isolation, and rollback when ledger persistence fails.
- Missing next tests: refund ledger balancing and cancel/void semantics once
  those chapters are implemented.
- Chapter 16 proof includes deterministic plan/phone data, local-target
  enforcement, collision-resistant run identity, atomic output, sensitive-data
  scanning, tenant isolation, processor-neutral authorization reads, and
  rejection of unexpected ledger truth.

## 6. Design Review Narrative

- The invariant is no captured PaymentIntent without a balanced ledger
  transaction group.
- The tradeoff is using PaymentIntent captured state plus ledger group as
  capture truth before introducing a separate capture object.
- The next safest Phase 2 step is either cancel/void semantics for authorized
  uncaptured payments or refund ledger entries for the existing refund API.
- The synthetic-data tradeoff is local operational lineage in PaymentIntent
  metadata without pretending merchant-controlled metadata is an authoritative
  training-data origin label.
