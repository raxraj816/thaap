# Daily Deep Dive: 2026-06-28

This deep dive records the implemented Chapter 19 webhook delivery system and
the reasoning needed to defend it in a Staff-level payments design review.

## 1. System Goal

- Make webhook delivery executable without weakening payment truth, tenant
  isolation, secret confidentiality, or outbound-network safety.
- Webhooks connect THAAP's payment/risk state machine to a merchant's order,
  support, fulfillment, and fraud-operation systems.
- The design protects payment transaction independence, historical event truth,
  tenant isolation, signing-key confidentiality, outbound-network boundaries,
  and observable retry behavior.

## 2. Plain-English Design Brief

- The mental model is `event -> delivery -> attempts`.
- The event is what happened, the delivery is where it is going, and attempts
  are each network try.
- Without immutable payloads, a retry could report the payment's new state as if
  it were the old event. Without attempt rows, operations cannot explain what
  happened. Without leases, two workers can send the same attempt concurrently.
  Without target policy, a merchant URL becomes an SSRF primitive.
- A lease is safe only when claimed work is dispatched immediately. Pre-claiming
  a serial batch turns ordinary endpoint latency into predictable lease expiry.
  Likewise, a socket inactivity timeout is not a wall-clock request deadline.
- Chapter 19 now provides a bounded PostgreSQL worker, exact signing, deterministic
  retries, safe merchant inspection, and a local callback demo.
- Phase 5 owns general outbox/Kafka publication. Phase 4.5 owns advanced merchant
  replay/verification/rotation-window operations. Phase 9 owns distributed
  worker scaling and managed egress.

## 3. Code Map

- `WebhookDeliveryService` creates one immutable event and endpoint deliveries
  inside the originating payment mutation transaction.
- `WebhookEndpoint` stores explicit operational state plus signing-secret
  prefix/hash and authenticated encrypted secret material.
- `WebhookDelivery` owns endpoint routing, aggregate retry state, and claim
  lease; `WebhookDeliveryAttempt` owns append-only transmission evidence.
- `WebhookController` exposes create/rotate/disable plus bounded tenant-scoped
  delivery detail and attempt reads.
- V9 adds `webhook_events`, endpoint event subscriptions,
  `webhook_delivery_attempts`, endpoint operational status/encrypted secret
  fields, delivery event/lease fields, and tenant-bound constraints.
- Application boundaries include event-envelope creation, key
  encryption/signing, target policy, claim/finalize service, HTTP transport,
  retry policy, bounded scheduler, and safe delivery/attempt APIs.

## 4. Request/Data Flow

1. A tenant-scoped payment mutation reaches its commit path.
2. If active subscribed endpoints exist, THAAP creates one immutable event and
   one delivery per matching endpoint inside the mutation transaction while
   holding shared endpoint locks.
3. A scheduler receives a bounded processing budget at an injected time.
4. For each budget slot, PostgreSQL locks one due row with
   `FOR UPDATE SKIP LOCKED`; the claim transaction creates a numbered attempt,
   token, and lease immediately before dispatch.
5. After claim commit, target policy validates the endpoint, the exact stored
   payload is prepared, and the worker renews the matching lease under a row
   lock immediately before HTTP.
6. The payload is signed with the fresh send time and HTTP is attempted with a
   strict total deadline.
7. A second transaction locks the delivery and finalizes only the matching
   claim token and attempt.
8. Success becomes `SUCCEEDED`; failure schedules the exact next attempt or
   becomes `EXHAUSTED`.
9. Merchant APIs expose safe aggregate and attempt evidence without secrets,
   payload internals, response bodies, URLs, or claim tokens.

## 5. Database Invariants

- Event, endpoint, delivery, and attempt tenant identities must agree through
  composite foreign keys.
- Delivery event type/resource identity must match the linked immutable event
  through the same composite foreign key.
- `(event_id, endpoint_id)` prevents duplicate routing truth.
- `(delivery_id, attempt_number)` prevents duplicate attempt identity.
- Retry-scheduled rows require next-attempt time; delivering rows require claim
  token and lease; terminal rows have no next attempt.
- Payload hash and exact persisted bytes bind the signature to immutable event
  truth.
- Removing these constraints permits cross-tenant delivery, double routing,
  duplicate attempt numbers, or impossible operational states.

## 6. Security And Privacy Invariants

- Raw endpoint signing keys are encrypted with AES-256-GCM under a separate
  versioned key-encryption key. Prefix/hash remain non-secret metadata; raw keys
  are reveal-once.
- Key-encryption-key rollover keeps prior versions in a decryption keyring,
  fails startup if active ciphertext is unreadable, and lazily rewraps old
  ciphertext under the current key without changing the merchant signing key.
- Payloads contain safe event and resource identifiers, not PAN, CVV, PII,
  internal card fingerprints, API/idempotency/signing material, processor
  secrets, or unrestricted metadata.
- Redirects are disabled, response bodies are discarded, and callback targets
  pass scheme, allowlist, DNS/address, and local-profile policy.
- Explicit address-byte policy rejects IPv6 ULA, CGNAT, and other special
  ranges; a wall-clock watchdog bounds TLS, write, and response parsing.
- Database compromise without the external key-encryption key must not enable
  signature forgery.

## 7. Fraud/ML Relevance

- Later review, chargeback, dispute, card-testing, and merchant-risk events can
  reuse the same event/delivery/attempt contract.
- Stable event IDs help merchants deduplicate risk-operation side effects.
- Chapter 19 avoids placing rich feature snapshots, rule internals, model
  reasons, buyer identity, or mutable fraud state in generic webhook payloads.
- The general event/outbox and replay boundary waits for Phase 5 lineage rather
  than being faked inside a webhook table.

## 8. Tests As Proof

- Migration tests prove clean V9 and honest V8 legacy-secret handling.
- Contract tests prove subscriptions, safe bounded reads, rotation/disable
  tenancy, audit evidence, and unchanged payment truth.
- Cryptographic tests prove exact bytes, tamper rejection, wrong secret,
  ciphertext authentication, and reveal-once behavior.
- PostgreSQL concurrency tests prove one claim winner and stale-finalizer
  rejection.
- Clock-driven tests prove all retry times without sleeping.
- Network-policy tests prove redirects and prohibited destinations never
  receive a call.
- Adversarial tests prove special CIDR rejection, total slow-trickle timeout,
  claim/send ordering, key rollover, cursor continuation, bulk disable, and
  delivery/event lineage equality.
- PostgreSQL endpoint-state tests prove disable is monotonic against concurrent
  rotation and event creation; observability tests cover unknown recovery,
  terminal bulk disable, true due backlog, and bounded latency logs.
- Sensitive-data and metric-tag tests prove observability does not become a
  leak.
- The critical Staff-level test is crash-after-send lease recovery: it must
  admit possible duplicate HTTP receipt while preserving one event and coherent
  numbered attempt evidence.

## 9. Staff Engineer Review Notes

- PostgreSQL remains the queue for this bounded V1 instead of introducing Kafka
  before cross-consumer events exist.
- Exact event bytes and append-only attempts reduce reconciliation ambiguity.
- The scheduler and HTTP client are adapters, keeping retry and claim rules
  deterministic and replaceable.
- At-least-once semantics are explicit rather than hiding the network crash gap.
- General outbox infrastructure, multi-region workers, response-body retention,
  and advanced replay controls would expand surface area before local delivery
  truth is proven.

## 13. Interview Narrative

Practice saying this out loud:

- The tradeoff I made was using a bounded PostgreSQL lease worker before Kafka
  because delivery volume is local and the event truth boundary matters first.
- The invariant I enforced was that payment truth and immutable webhook event
  truth commit before any external HTTP begins.
- The production risk I reduced was duplicate/cross-tenant delivery corruption,
  secret forgery, payload drift, and SSRF.
- I deferred distributed queueing and advanced merchant replay because they have
  named later triggers and Chapter 19 keeps their contracts reversible.
- The tests prove exact signing, tenant-bound schema, one claim winner,
  deterministic retry, lease recovery, target isolation, and unchanged payment
  and ledger truth.
