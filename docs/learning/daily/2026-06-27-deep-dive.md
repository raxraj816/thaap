# Daily Deep Dive: 2026-06-27

## 1. System Goal

Chapter 16 needed to become a trustworthy local payment-risk evidence producer,
not merely a script that happened to print expected values. The hardening slice
makes success mean that payment lifecycle, authorization, fraud lineage,
tenant isolation, privacy, and zero-ledger claims all agree.

## 2. Plain-English Design Brief

The mental model is a fail-closed test harness that also produces durable local
data. If THAAP creates money truth where no capture occurred, links fraud
evidence to the wrong attempt, targets a shared environment, or leaks a secret,
the generator must stop rather than publish a passing artifact.

We built local safety and operational lineage now. Trusted server-side
synthetic-origin classification remains deferred because the necessary schema
and dataset-consumer boundary do not exist. Resumable interrupted runs remain a
separate generator-reliability deferral because there is no durable run-state,
cleanup, or safe resume protocol yet.

The destination ownership is explicit:

- `TD-0001`, Phase 4.5, **Developer Scenario Runner And Traffic-Origin Governance**:
  Payments Core owns the trusted schema/API boundary; Risk Operations owns
  scenario-runner policy and analytics exclusion behavior.
- `TD-0002`, Phase 7, **Synthetic Generator V2 Run Orchestration**: ML/Data Platform owns
  durable run state, checkpointing, retry, resume, and cleanup; Payments Core
  remains responsible for idempotent mutation APIs and origin propagation.

These debts now live in the canonical technical debt register. The readiness
gate validates required fields, immutable IDs, non-vague owners/targets,
resolution evidence rules, and bidirectional master-plan registration so their
survival no longer depends on conversational memory.

## 4. Request/Data Flow

1. The CLI reads the bootstrap token from the environment and validates that the
   API origin is loopback.
2. A collision-resistant run ID is created before merchant mutations.
3. Public APIs create merchants, customers, PaymentMethods, PaymentIntents, and
   confirms; each PaymentIntent carries the run ID and generator version.
4. Merchant reads retrieve PaymentIntent, PaymentAttempt, FraudDecision,
   FeatureSnapshot, Authorization, and ledger evidence.
5. Exact cross-object and money-truth assertions run before the sanitized
   summary is atomically published.

## 5. Database Invariants

- This slice adds no schema migration.
- Existing foreign keys and tenant constraints remain the durable source of
  payment and fraud linkage.
- `syntheticRunId` metadata is operational traceability, not a database-enforced
  origin claim.

## 6. Security And Privacy Invariants

- The admin bootstrap token never appears in CLI arguments or summary output.
- Only loopback HTTP(S) origins without credentials, paths, queries, or
  fragments are accepted.
- Raw card, buyer contact data, API keys, and generated idempotency keys are
  forbidden in the summary scan.
- Authorization reads remain tenant-scoped and omit simulator-specific public
  contract fields.

## 7. Fraud/ML Relevance

Every generated confirm must have a FraudDecision and FeatureSnapshot linked to
the same PaymentAttempt. This gives future replay and label work honest local
examples. It does not yet make the records safe for training: trusted origin,
label provenance, sampling policy, and dataset versioning are still missing.

## 14. Chapter 17 Deep Dive: Capture Method And Void Truth

### First-Principles Model

An authorization, capture, and void answer different questions:

1. Authorization: did the simulated issuer approve reserving funds?
2. Capture: did the merchant finalize the approved charge?
3. Void: did the merchant cancel the uncaptured approval so it cannot later be
   captured?

Rewriting an approved Authorization to "voided" would destroy history. Chapter
17 therefore keeps the original processor result and appends a separate
`AuthorizationVoid` as later payment-lifecycle truth.

### Transaction Boundaries

- Approved `AUTOMATIC` confirm performs fraud lineage, authorization, capture
  ledger writes, PaymentIntent capture, webhook records, audit logs, and
  idempotency completion in one database transaction.
- Approved `MANUAL` confirm stops at `REQUIRES_CAPTURE`.
- Cancel locks the PaymentIntent. If it is `REQUIRES_CAPTURE`, the transaction
  appends a void before setting `CANCELED`; otherwise it cancels without
  inventing processor evidence.
- Cancel state, void, webhook, audit, and idempotency completion either all
  commit or all roll back.

### Schema Invariants

V6 adds `authorization_voids` with:

- tenant ownership on every row
- composite lineage to the exact Authorization and PaymentAttempt
- composite lineage from that PaymentAttempt to the exact PaymentIntent
- one void per authorization
- one void per PaymentIntent
- constrained status `RECORDED`
- constrained reason `MERCHANT_CANCELED`

V6 reclassifies legacy approved `AUTOMATIC` intents already waiting in
`REQUIRES_CAPTURE`. Staff review found that the same compatibility rule also
applies to every other open intent that could later progress toward capture.
Because V6 had already been applied locally, editing it would violate Flyway
checksum immutability. Forward-only V7 therefore completes the boundary for
confirmation, retry, fraud/action, processing-recovery, authorized, and
capture-ready states. Before Chapter 17 all of those rows were governed by the
explicit-capture contract, so a deployment must not change a later confirm or
retry into an unrequested money movement. Terminal rows remain untouched
because their capture method is historical context rather than future behavior.

### Failure Modes And Proof

- Ledger failure during automatic confirm cannot leave an approved-but-partly
  captured payment: the entire confirm rolls back.
- Audit failure during cancel cannot leave a canceled PaymentIntent without its
  required operational evidence: state, void, webhook, and idempotency all roll
  back.
- Concurrent capture and cancel serialize on the PaymentIntent row lock. A
  PostgreSQL 16 race test proves exactly one operation commits and the loser
  observes the terminal state, leaving either balanced capture evidence or
  canceled-plus-void evidence, never both.
- Cross-merchant API access returns not found.
- Database tests reject mismatched PaymentIntent/PaymentAttempt/Authorization
  lineage even within the same merchant.
- Idempotent replay cannot duplicate ledger, void, webhook, or audit truth.

### Fraud And ML Relevance

The original FraudDecision and FeatureSnapshot remain immutable decision-time
evidence. Cancel and void happen later and must become separate outcome signals
for future labels, analytics, and model evaluation. A cancellation is not
automatically fraud, and a void must not retroactively change why THAAP allowed
the attempt.

### Stripe/Mastercard-Style Review Narrative

- The invariant is that an approved payment has one unambiguous capture path:
  automatic capture now, manual capture later, or durable void before capture.
- The transaction boundary prevents false money truth under retries and
  persistence failures.
- The schema proves tenant and cross-object lineage instead of relying only on
  service code.
- The simulator says `RECORDED`, not "network reversal succeeded," because no
  real PSP call exists.
- The next dependency-ready slice is durable refund truth and balanced reversal
  accounting.

## 15. Chapter 18 Deep Dive: Durable Refund And Reversal Truth

### First-Principles Model

A refund does not erase capture. It appends a later money event that reverses
the captured accounting while preserving authorization, fraud decision, and
capture history. This is why Chapter 18 introduces a durable Refund rather than
returning an ephemeral response ID after changing PaymentIntent status.

### Transaction And Locking Boundary

`POST /refunds` reserves idempotency and then locks the merchant-scoped
PaymentIntent. The transaction requires `CAPTURED`, the matching approved
Authorization, and a complete capture ledger pair before it:

1. inserts the Refund;
2. writes debit `MERCHANT_PAYABLE` and credit `CUSTOMER_RECEIVABLE`;
3. changes PaymentIntent to `REFUNDED`;
4. creates `refund.created` delivery records using the Refund ID;
5. writes a safe Refund audit log;
6. completes the idempotency response.

Any exception rolls all six facts back. The PaymentIntent row lock serializes
two refund requests, and the unique Refund-per-PaymentIntent constraint remains
the database backstop.

### Schema And Lineage

The Refund carries merchant, PaymentIntent, PaymentAttempt, and Authorization
IDs. Composite foreign keys prove both that the authorization belongs to the
attempt and that the attempt belongs to the payment.

Ledger entries now carry explicit `payment_intent_id` and optional `refund_id`.
For capture, `source_id` equals the PaymentIntent and `refund_id` is null. For
refund, `source_id` equals the Refund and a composite foreign key proves that
Refund belongs to the same PaymentIntent. Source-specific check constraints
also enforce the allowed account/direction pairs.

### Migration Honesty

The old thin endpoint generated a response-only UUID. A pre-V8 `REFUNDED` row
therefore lacks reconstructable Refund identity, authorization linkage, and
ledger evidence. V8 fails with a named guard when such rows exist. In a
local-only simulator, explicit reset/remediation is safer than deployment-time
fabrication of financial history.

### Failure Modes And Proof

- Missing capture ledger evidence rejects refund even when status says
  `CAPTURED`.
- Partial, over, double, canceled, declined, action-required, and uncaptured
  refunds create no side effects.
- Injected ledger, webhook, and audit failures each roll back the whole refund.
- H2 and PostgreSQL tests prove V8 backfill/guard behavior and Hibernate schema
  validation.
- A PostgreSQL race proves one `201`, one `409`, one Refund, and one balanced
  reversal group.
- FraudDecision and FeatureSnapshot counts remain unchanged after refund.

### Stripe/Mastercard-Style Review Narrative

- Refund eligibility is based on evidence, not status alone.
- Accounting is append-only and independently balanced per transaction group.
- Composite constraints defend tenant and cross-object lineage below the API.
- `RECORDED` is honest simulator-local truth and does not claim external network
  success.
- Webhook delivery execution remains Chapter 19; Chapter 18 creates durable
  delivery intent without coupling external I/O to the money transaction.

### Deferral Governance Review

The first Chapter 18 documentation pass made every exclusion visible but grouped
them in one broad defer list. That did not meet THAAP's stricter rule requiring
an exact reason, destination owner, trigger, and completion evidence.

The master plan now assigns:

- partial refunds, the separate Capture object, and fee reversal to
  **Partial Money Accounting**;
- refund reasons and review approval to Phase 4 **Refund Operations And Review
  Actions**;
- refund/dispute interaction to Phase 4 **Dispute Offset Accounting**; and
- provider submission and reconciliation to post-V1 **Real PSP Refund
  Execution**.

No debt ID was created because the current full-refund simulator contract is
complete and none of those product triggers exists yet. The documentation
defect was dependency-ready and was fixed immediately. Accepting any trigger
without its named prerequisite would either pull that slice forward or require
a registered debt with a concrete resolution target.
