# Daily Deep Dive: 2026-07-05

## 1. System Goal

Re-certify Phase 2.5 after seven escaped findings by fixing the product boundary
and the review method that allowed each escape. No payment or fraud truth may
be rewritten while webhook and generator recovery become fail-stop safe.

## 2. Why The Issues Clustered

The original changes were broad and individually plausible, but several proofs
stopped one boundary too early:

- URL validation and redirect rejection stopped before proxy routing.
- Secret loading stopped before the exact signature timestamp.
- KEK validation stopped at the primary endpoint ciphertext.
- exception cleanup stopped before process death.
- secret erasure stopped before operator cleanup usefulness.
- generator retry proof reused the same caller classification after restart.
- the crash failpoint stopped after local resource persistence rather than
  immediately after the remote merchant/customer response.

This is a recurring distributed-systems pattern: local correctness does not
prove the handoff between state, time, process, and network boundaries.

## 3. Code And Data Flow

### Credentialed Python request

1. Validate the configured base URL as loopback.
2. Build an opener with an empty proxy policy.
3. Reject every redirect before constructing a follow-up request.
4. Send credentials only to the directly resolved validated origin.

### Endpoint creation

1. Lock the tenant/idempotency identity.
2. Return completed replay, reject a live lease, or fence/reclaim an expired
   lease with a new random token.
3. Create endpoint and encrypted reveal-once response in the operation
   transaction.
4. Lock the reservation by ID, verify the same token still owns it, and mark it
   completed.
5. Cleanup deletes only an unfinished record owned by that exact token.

### Webhook signing

1. Prepare durable dispatch state.
2. Authorize the claim-bound generation under the endpoint lock and obtain its
   bounded/unbounded use window.
3. Read the signature timestamp.
4. Reject at or after previous-generation expiry.
5. Only then sign and transport.

### Generator abandonment

1. Record safe resource identity immediately after remote success.
2. Store secret-bearing checkpoint payload only as needed for resume.
3. On complete/abandon, erase checkpoint responses.
4. Retain the safe resource ledger for reconciliation.

### Merchant/customer creation and exact-window resume

1. Derive a stable domain-separated generator key for merchant or customer.
2. Reserve server work under a fenced owner token in an independent
   transaction.
3. For merchant creation, bind HMACed key/request identity and derive the same
   high-entropy API key under the server pepper; store only its normal hash in
   the merchant row.
4. For customer creation, run the customer insert and safe-ID idempotency
   response in one merchant-scoped transaction.
5. Inject client death immediately after the server response and before
   `generator_resources` or checkpoint persistence.
6. Resume under the persisted retry classification; server replay returns the
   same object/credential, then local resource lineage is restored.

## 4. Database Invariants

- `IN_PROGRESS` creation records have a token and expiry; `COMPLETED` records
  have neither.
- A stale owner cannot complete or delete a record after another owner
  reclaims it.
- Merchant creation identity and request binding are HMACed; completed lineage
  links to exactly one merchant and contains no replayable plaintext.
- General idempotency leases make historical unfinished customer/payment work
  reclaimable while token-fenced transaction rollback prevents a stale owner
  from committing domain mutation.
- Successful completion resets replay expiry from completion time.
- Required KEK versions are the union of every ciphertext still reachable
  through a valid product operation.
- Generator safe references contain IDs and types, never API keys, raw
  idempotency keys, signing secrets, cards, or PII.

## 5. Security And Privacy Analysis

An environment proxy is a credential recipient even when the application URL
is loopback. Disabling proxies in these local privileged tools is therefore an
authorization decision, not convenience.

Expiry is a cryptographic-use constraint. A secret copied into memory does not
acquire perpetual authority. The exact timestamp placed in the signature must
belong to the allowed generation window.

KEK removal is safe only when no valid product path can request the ciphertext.
Current endpoint state, rotation overlap, and reveal-once replay are three
separate retention reasons.

Deterministic merchant API-key replay is safe here because the derivation is
keyed by a server secret and domain separated from stored key/request hashes.
Knowing the idempotency key, merchant name, or database hashes does not reveal
the API key. A caller must also pass the bootstrap authorization boundary to
request replay.

## 6. Concurrency And Failure Proof

The PostgreSQL test does more than start two threads. The first transaction
reclaims and completes while retaining the row lock. A NOWAIT probe proves the
lock is held; `pg_stat_activity` proves the second caller is waiting on that
database lock. After release, the second caller replays the completed result.
Postconditions prove one endpoint/secret, one merchant/API key, one
tenant-scoped customer, and cleared lease fields.

V14 and V15 separately reconstruct historical stranded shapes and prove
upgrade, because a fresh-schema test cannot certify recovery of rows created
by older code. The SQLite test similarly proves both retry-classification drift
directions rather than merely rerunning the same binary contract.

## 11. Post-Closure Boundary Reopening

### Transaction fence ordering

A lease timestamp is not mutual exclusion by itself. If work begins before the
reservation row is locked, expiry can admit a second worker even though only
one database transaction eventually commits. That is unacceptable at a
processor boundary because database rollback cannot reverse an authorization
sent over the network. The repaired order is:

1. reserve durably
2. begin the operation transaction
3. lock the reservation row
4. validate the owner token
5. invoke fraud, processor, ledger, webhook, and mutation work
6. complete the same locked record

The forced PostgreSQL test holds step 5, waits until the lease is objectively
expired, and proves the contender blocks at step 3.

### HMAC rotation without duplicate identity

Changing an HMAC key changes the digest. A version column tells us which key
created a record, but it does not make old and new digests collide at the
database uniqueness boundary. V16 therefore introduces an alias relation:

```text
HMAC(v1, external key) ─┐
                        ├─> one merchant_creation_record
HMAC(v2, external key) ─┘
```

The primary key on each alias prevents mixed-version writers from independently
claiming the shared old/new identity set. Replay uses the creation record's
original key version, so the API key remains byte-for-byte identical. A
two-phase rotation makes both versions available before promotion, and startup
fails closed while live replay state still requires an absent version.

### Lease coverage across network reads

Read-only verification still consumes workflow ownership time. Because one
request is bounded to 30 seconds, a 90-second lease is safe only if it is
renewed between requests. `ApiClient` now heartbeats before and after every
request, and configuration requires the lease to exceed a single request
timeout. The delayed-server proof crosses the original lease cumulatively and
then attempts acquisition from a second SQLite owner.

## 9. Complete Persisted-HMAC And Typed-Lineage Recovery

### Separate cryptographic jobs

Replay identities and fraud-correlation identities have different lifecycle
requirements. Replay digests must rotate online while preserving a bounded
24-hour protocol window. Card, email, and phone pseudonyms must remain stable
across that routine rotation or historical velocity and graph edges split.
THAAP now expresses those as two explicit components:

```text
rotatable replay keyring
  -> merchant aliases
  -> generic request_hash + request_hash_key_version
  -> webhook tenant/key aliases + original-version request hash

stable correlation key
  -> card fingerprint
  -> customer email pseudonym
  -> customer phone pseudonym
```

V17 backfills historical replay hashes as `v1`, creates webhook alias rows, and
keeps old-writer compatibility through a `v1` column default. New writers use
ordered current/previous keyrings, ordered database locks, constant-time request
hash comparison, and startup required-key inventories. A live record blocks key
removal; an expired record can be safely restarted or retired.

### Typed generator protocol

`resource_type` is now part of the durable step protocol beside `retry_safe`.
Both values are immutable on restart. The SQLite upgrade adds the column, maps
every historical known step—including `tenant_isolation.verifier_merchant`—and
backfills safe resource references from completed responses. New resource
operations must declare their type and return an ID plus tenant lineage.

### Hostile partitions

- same request before and after replay-key rotation
- changed webhook request with the same external key after rotation
- mixed v1/v2 PostgreSQL workers contending on one endpoint reservation
- live old-version replay with the historical key missing
- expired old-version replay after historical-key removal
- stable PAN/email/phone correlation while replay keys change
- completed and interrupted pre-column SQLite journals
- resource-type drift across binary restart
- verifier merchant inclusion without API-key persistence

All partitions passed in the final run: 265 Java tests and 67 repository Python
tests with zero failures, errors, or skips. This resolves `ER-0034` and
`ER-0035`; the V17 upgrade and forced PostgreSQL rolling-worker test are part of
the proof, not inferred from unit behavior.
