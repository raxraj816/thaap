## 2. Payment Processing Concepts Learned

- Payment API clients need stable failure semantics as much as stable success
  responses, especially when retries and idempotency are involved.
- `409 conflict` is the correct shape for idempotency-key reuse with a
  different request body because the key itself is valid but the operation
  conflicts with previous state.

## 3. Fraud Detection Concepts Learned

- Request correlation is future fraud-investigation infrastructure: it connects
  merchant-facing requests, application logs, persisted decisions, reviews, and
  analyst support workflows.
- Validation errors should avoid echoing rejected values because payment and
  fraud request bodies can contain card-adjacent or customer-identifying data.

## 4. Security Concepts Learned

- Tenant authentication failures now use the same API error contract as other
  failures instead of relying on framework-default responses.
- Unexpected server failures return a generic client message while preserving
  server-side logging with request correlation.
- Request IDs are constrained to visible ASCII and a bounded length before being
  propagated into response headers and logs.

## 5. Architecture / Design Notes

- The API contract lives in `com.thaap.payments.api` as a cross-cutting
  foundation package.
- `RequestIdFilter` runs at highest precedence so downstream request handling
  and exception handling share the same request ID.
- Error responses intentionally omit rejected validation values.
- The logging pattern now includes `requestId` from MDC.
