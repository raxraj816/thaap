# Daily Deep Dive: 2026-07-05

## 1. System Goal

Re-certify Phase 2.5 after five escaped findings by fixing the product boundary
and the review method that allowed each escape. No payment or fraud truth may
be rewritten while webhook and generator recovery become fail-stop safe.

## 2. Why The Issues Clustered

The original changes were broad and individually plausible, but several proofs
stopped one boundary too early:

- URL validation and redirect rejection stopped before proxy routing.
- Secret loading stopped before the exact signature timestamp.
- KEK validation stopped at the primary endpoint ciphertext.
- exception cleanup stopped before process death.
- secret erasure stopped before operator cleanup usefulness.

This is a recurring distributed-systems pattern: local correctness does not
prove the handoff between state, time, process, and network boundaries.

## 3. Code And Data Flow

### Credentialed Python request

1. Validate the configured base URL as loopback.
2. Build an opener with an empty proxy policy.
3. Reject every redirect before constructing a follow-up request.
4. Send credentials only to the directly resolved validated origin.

### Endpoint creation

1. Lock the tenant/idempotency identity.
2. Return completed replay, reject a live lease, or fence/reclaim an expired
   lease with a new random token.
3. Create endpoint and encrypted reveal-once response in the operation
   transaction.
4. Lock the reservation by ID, verify the same token still owns it, and mark it
   completed.
5. Cleanup deletes only an unfinished record owned by that exact token.

### Webhook signing

1. Prepare durable dispatch state.
2. Authorize the claim-bound generation under the endpoint lock and obtain its
   bounded/unbounded use window.
3. Read the signature timestamp.
4. Reject at or after previous-generation expiry.
5. Only then sign and transport.

### Generator abandonment

1. Record safe resource identity immediately after remote success.
2. Store secret-bearing checkpoint payload only as needed for resume.
3. On complete/abandon, erase checkpoint responses.
4. Retain the safe resource ledger for reconciliation.

## 4. Database Invariants

- `IN_PROGRESS` creation records have a token and expiry; `COMPLETED` records
  have neither.
- A stale owner cannot complete or delete a record after another owner
  reclaims it.
- Successful completion resets replay expiry from completion time.
- Required KEK versions are the union of every ciphertext still reachable
  through a valid product operation.
- Generator safe references contain IDs and types, never API keys, raw
  idempotency keys, signing secrets, cards, or PII.

## 5. Security And Privacy Analysis

An environment proxy is a credential recipient even when the application URL
is loopback. Disabling proxies in these local privileged tools is therefore an
authorization decision, not convenience.

Expiry is a cryptographic-use constraint. A secret copied into memory does not
acquire perpetual authority. The exact timestamp placed in the signature must
belong to the allowed generation window.

KEK removal is safe only when no valid product path can request the ciphertext.
Current endpoint state, rotation overlap, and reveal-once replay are three
separate retention reasons.

## 6. Concurrency And Failure Proof

The PostgreSQL test does more than start two threads. The first transaction
reclaims and completes while retaining the row lock. A NOWAIT probe proves the
lock is held; `pg_stat_activity` proves the second caller is waiting on that
database lock. After release, the second caller replays the completed result.
Postconditions prove one endpoint, one secret value, and cleared lease fields.

V14 separately reconstructs the historical stranded shape and proves upgrade,
because a fresh-schema test cannot certify recovery of rows created by older
code.

## 9. Design Review Defense

The resolution is defensible because every claim is tested at its enforcement
boundary: sockets for routing, exact clock instant for expiry, SQL inventory
for KEKs, PostgreSQL row locks for ownership, historical migration state for
recovery, and SQLite persistence for cleanup lineage.
