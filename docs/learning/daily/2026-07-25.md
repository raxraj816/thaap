## 2. Payment Processing Concepts Learned

- A delivery chapter is a temporary sequencing coordinate. A payment capability
  such as authorization void, refund ledger, or review approval is a durable
  domain concept and therefore belongs in executable names.
- Flyway class identity is persisted deployment history. Renaming an unapplied
  migration is trivial; renaming one applied to a local database requires an
  explicit repair and validation against the exact database.

## 3. Fraud Detection Concepts Learned

- Fraud evidence should remain discoverable by capability: feature lineage,
  decision aggregation, review resolution, velocity, fraud lists, and merchant
  policy. Chapter prefixes obscure which invariant a test actually proves.
- Naming quality supports model and rule governance because reviewers can trace
  evidence by stable lineage boundary rather than by roadmap memory.
- Rotation is a decision-quality boundary: abandoning an old Redis window can
  turn a correct REVIEW into ALLOW even when every stored value remains private.

## 4. Security Concepts Learned

- Demo credentials and tenant fixtures kept their loopback, sanitization, and
  isolation boundaries while temporary chapter namespaces were removed.
- Historical applied migration bytes remain immutable. The naming checker uses
  exact allowlists for V6/V8 and their two constraint assertions rather than a
  broad bypass that could hide new violations.
- Idempotent replay is part of authorization. A stored manager response cannot
  be returned merely because merchant and key match; the authenticated operator
  and credential lifecycle must own that replay row.

## 5. Architecture / Design Notes

- Phase 4.5 product monitoring is not Micrometer telemetry and does not require
  pretending Phase 5 Kafka exists. It derives denominator-defined product facts
  from durable PostgreSQL evidence under explicit `asOf`, coverage, origin, and
  label-availability semantics.
- A narrow local analyst/developer cockpit can be pulled forward because the
  backend authorization and workflow dependencies exist. Full hosted identity
  and the broad dashboard remain separately owned boundaries.
- Historical policy simulation is narrower than the future general ReplayEngine:
  it can use a mature PostgreSQL-backed batch job over immutable decision-time
  features without inventing a custom queue or asynchronous event platform.
- Chapter language remains valid only where chapter governance is the real
  responsibility: plans, learning notes, matrices, dossiers, and the
  chapter-closure validator.
- Removing chapter text from governed Lua comments changed the exact bytes, so
  both production SHA-1 contracts and their review evidence were updated
  together. Comments are part of a byte-level protocol artifact.
- Redis compensation is a distributed ownership protocol: only the transaction
  that inserted a member receives an owner token, and cleanup is an atomic
  compare-delete. A retry that merely observes an existing member owns nothing.
- Nested pseudonyms must rotate layer by layer. The old outer fraud-list HMAC is
  useful only with the matching old inner RiskContext HMAC alias.

## 17. Chapter 36 Closure Learning

- A product risk rate is a tuple, not a percentage: cohort, numerator,
  denominator, half-open window, `asOf`, coverage, origin policy, and definition
  version must travel together.
- `available_at` is the anti-leakage clock. Caller-reported evidence time and
  receipt time describe the event; server-assigned availability controls when
  a report or future training cohort may observe it.
- “Eligible” is a fraud-data contract. An undecided attempt is not a confirmed-
  fraud denominator, and an attempt without processor/control evidence is not
  an enumeration denominator. Both now fail to null/coverage rather than zero.
- Exact drill-down is part of product trust. HMAC-bound keyset cursors let an
  analyst reconcile every aggregate without exposing PAN, email, fingerprint,
  identity HMAC, note content, or broad entities.
- Catalogue readiness must compare semantics, not counts. Eighteen wrong rows
  are still wrong, so readiness now verifies every source/family/type/display
  mapping against the immutable application V1 catalogue.
- Retained NULL taxonomy versions and new labels are different time domains.
  V50 preserves old bytes; V51 requires all new PostgreSQL labels to bind V1.
- Repeatable-read is useful only with an explicit forced interleaving. The
  payment write committed while the monitoring read paused, and the read kept
  one coherent snapshot without locking the payment path.
- The live demo proved `1/2` live approval, `2/3` when synthetic is explicitly
  included, drill-down `1/2`, exact replay, one non-activating recommendation,
  zero profile activation, durable SQL reconciliation, and readiness UP.

## 21. Chapter 38 Pre-Implementation Freeze

- Created and froze the Chapter 38 matrix and closure dossier before simulation
  schema, dependency, configuration, code, or tests.
- The run identity freezes candidate bytes/digest, cohort, `asOf`, origin,
  label cutoff/policy, evaluator, feature/rule/taxonomy versions, and query
  digest. A worker never asks current Redis or RiskContext what was true.
- Spring Batch's JDBC repository owns durable job execution metadata; THAAP's
  run/result/event/report tables own product truth. Chunk writes remain
  idempotent because framework metadata and business rows can be retried around
  a failure boundary.
- Stable checkpoint identity is `(decision_created_at,payment_attempt_id)`, not
  an offset or timestamp alone. Results are unique by merchant/run/attempt.
- Cancel and finalize are competing terminal transitions on one locked run;
  first commit wins and stale workers cannot revive terminal state.
- The activation gate is evidence-only. It checks exact digest, freshness,
  cohort/coverage, data quality, protected-source safety, tenant, and different
  approver, but Chapter 39 still owns the activation mutation.
