# Deep Dive: 2026-08-07 — The Proof That Named Nothing

An invariant proof matrix is the durable answer to one question: *if you doubted
that this system holds a property, what would you run?* This is about discovering
that 59 of those answers pointed at nothing, and about the difference between a
gate that validates a document's shape and one that validates its claims.

## The domain problem first

A payments platform accumulates properties that must never stop being true. Money
must balance. A merchant must never see another merchant's rows. A late fraud label
must not retroactively rewrite what was known at authorization time. These are not
features — no user story asks for them — so nothing in ordinary product work keeps
them honest. They survive only because someone wrote down what proves each one.

That is what `docs/reviews/CHAPTER_NN_INVARIANT_PROOF_MATRIX.md` is. Each row names
an invariant, the failure sequence that would break it, the implementation that
holds it, and — the load-bearing field — the `Proof`: the artifact an auditor runs
to see the property defended.

The `Proof` field is the only part of the row that connects the document to reality.
Everything else is prose about intent. `Proof` is a promise that something exists.

## The claim this audit tested

Yesterday's correction, from `ER-0096` and `ER-0098`, was: *every script named as
proof in a chapter matrix must have a recorded execution before the chapter closes.*
Both findings had the same root cause — a gate that had been written but never run,
and was red the first time anyone ran it.

That correction is scoped to scripts, and its verification method is execution. So
it asks: does this named thing pass? The wider question it implies, and the one this
audit asked, is weaker and more embarrassing: **does this named thing exist at all?**

A script that has never run at least exists to be run. A test class that was never
written produces no failing run to notice. It is invisible to a correction whose
detection method is "execute it and look at the result," because there is nothing to
execute. The weaker failure is the one that hides from the stronger check.

## What the audit found

Every backticked test class and file reference in the `Proof` field of all 42 chapter
matrices, resolved against the repository. 59 references across seven chapters
resolved to nothing. Chapters 19–35, 37–43R and 53–59 were clean.

The drift is entirely Chapter 36 and Phase 5, and the mechanism is uniform:

1. Every Phase 5 matrix is `PRE_IMPLEMENTATION`. It is written *before* the code, so
   its `Proof` fields are obligations in future tense —
   "`ProjectionRebuildObservabilityTests` will inspect Micrometer meters."
2. Implementation consolidated each domain into one contract class plus a
   `*PostgreSqlTests` subclass re-running the same bodies against real PostgreSQL via
   Testcontainers.
3. `Status` was flipped to `PASS`. Nobody rewrote `Proof`.

Step 2 is *good*. One test body proven against both H2 and real PostgreSQL is stronger
than two suites that drift apart. The defect is that the durable traceability artifact
was never updated to say so, so it kept pointing at names from the plan.

Then the classification, which is where the real work was. Thirty-six of the 59 are
naming drift: the concern is genuinely held, just by a differently-named class. The
tell is that the closure dossiers, where they name classes at all, name only real
ones — the people writing the dossier were looking at the code.

The other 23 are not drift. They are absent. Determining which was which meant
reading suite bodies rather than method names, and for concerns that depend on a
mechanism, searching for the mechanism directly. A repository-wide search for
`MeterRegistry` returns no rebuild, replay or event-foundation test at all, so
`C50-OBS-001`, `C51-OBS-001`, `C44-OBS-001` and `C46-OBS-001` are unproven rather
than proven under another name. Inferring a boundary from a convenient surface is
the specific error `ER-0098` recorded; the audit could not commit it again while
investigating it.

## Why every existing check passed

`invariant-proof-check.py` validated that a row had every required field, that
`Status` was `PASS`, and that no `TBD`/`TODO`/`FIXME`/`PLACEHOLDER` marker appeared.

Look at what that set has in common: it is a check on the *shape* of a row. A row
claiming a class that does not exist has perfect shape. It has a populated `Proof`
field. It has no unfinished-work marker — the whole problem is that it reads as
finished. It is exactly the input a shape check is designed to accept.

`chapter-closure-check.py` did not catch it either, because it reconciles matrix
metadata against dossier metadata. Two documents agreeing with each other is not the
same as either agreeing with the filesystem.

Nothing in the pipeline ever asked the filesystem a question.

## Designing the resolver: two failure modes, pulling opposite ways

The fix is conceptually trivial — resolve the names — and the entire difficulty is
that the gate can fail in two opposite directions, and the second one is fatal.

**Too permissive** and it misses a fabricated proof, which is the bug being fixed.

**Too noisy** and it flags backticked prose across 511 rows. The matrices quote SQL
keywords (`AUDIT`, `LIMIT`), register coordinates (`ER-0096`), statuses (`PASS`),
enum values (`SYNTHETIC_SCENARIO`). A gate that reports fifty false failures on its
first run does not get tuned; it gets commented out. That is not a hypothetical —
a bypassed gate is precisely how the first unrun gate survived long enough to become
`ER-0096`.

So the match is narrow and deliberately conservative. In `invariant-proof-check.py`:

```python
CLASS_ARTIFACT = re.compile(r"^[A-Z][A-Za-z0-9]*(?:Tests|Test)$")
FILE_ARTIFACT = re.compile(r"^[A-Za-z0-9_./-]+\.(?:py|sh|ts|tsx|java|kt)$")
```

Something shaped like a test class, or like a source file with a known extension.
Everything else in backticks is prose and is ignored — the gate declines to have an
opinion. `AUDIT` is not `PascalCaseTests` and has no extension, so it never enters
the resolver.

Resolution itself has one accommodation. A path reference falls back to its basename:

```python
if (root / candidate).is_file():
    continue
if candidate.rsplit("/", 1)[-1] in names:
    continue
```

Chapter 58 names SDK suites as `tests/test_secure_client.py`, which is relative to
the client package, not the repository root. Demanding repository-relative paths
would have meant rewriting correct rows to satisfy a tool — the tool bending to the
document, rather than the reverse, in the one case where the document was right.

The index is built once for the whole run (`repository_artifacts`) and threaded
through `validate_matrix`, so 42 matrices cost one directory walk. It stores both the
basename and the extension-free stem, which is what lets a `Proof` field name a test
class the way an engineer says it aloud.

`os.walk` rather than `pathlib.Path.walk`, because the latter needs Python 3.12 and
the declared floor for the supported SDK is 3.11. A gate that only runs on the
author's interpreter is a gate that does not run.

## The escape hatch, and why it is not free

Twenty-three rows name proofs that were planned and never built. Deleting the rows
would erase the record that the concern exists. Leaving them would keep the gate red
forever, which converts it back into a gate people bypass.

So a row may cite a `TD-NNNN` coordinate:

```python
if DEBT_REFERENCE.search(proof):
    return []
```

The point is that this is not a silent suppression. Citing `TD-0007` obliges an
author to write a register entry, and `technical-debt-check.py` holds that entry to
the register's rules: an owner, a trigger, and done criteria. The gap does not
disappear — it moves from inside a `PASS` row, where nothing tracks it, to a register
where something does. The exemption costs paperwork proportional to the debt, which
is the correct price.

The known weakness is that the exemption is field-wide rather than per-artifact. One
`TD-0007` citation skips *every* backticked artifact in that sentence, so a fabricated
name in the same field would ride through. I confirmed both halves of this: the hole
is real, and it is currently latent — re-running the resolver across all 23
debt-exempt rows with the exemption disabled surfaces zero additional unresolved
artifacts. Nothing is masked today. The right shape is to exempt only what the debt
entry names.

## The enforcement that was never enforcing

`ER-0098` recorded that `openapi-contract-check.py` was now wired into the readiness
run, and that removing it would fail a test.

It would not have. The readiness tests created a stub for each checker and asserted
the script exited 0. But a stub that the script never calls is simply never called,
and the run still exits 0. The test could not distinguish "the gate ran and passed"
from "the gate does not exist." The correction was written down, believed by
everyone including its author, and completely inert.

The replacement asserts invocation rather than outcome. Each stub touches a marker
file; the test asserts every marker exists:

```python
markers = {gate: root / f"ran-{gate}" for gate in required_gates}
...
never_invoked = sorted(
    gate for gate, marker in markers.items() if not marker.is_file())
self.assertEqual([], never_invoked)
```

And then — the part that matters — the test was itself tested. Strip one gate line
from a copy of the readiness script, point `SCRIPT_PATH` at the copy, run the test:
it fails with `['python-sdk-package-check.py']`. Restore it: green.

This is mutation testing in its cheapest possible form, four seconds of work, and it
is the only thing that distinguishes an enforcement from a claim about one. The
generalised lesson, now written into `ER-0099`: **when you write a process
correction, execute it against the failure it claims to prevent.** `ER-0098` was
found because someone finally deleted a line to watch a test fail.

## What is still broken, on purpose

`invariant-proof-check.py` requires every row to be `PASS`. That means a matrix
cannot say the true thing about those 23 rows — *held on the ordinary path, unproven
adversarially*. So they close as `PASS` while their own `Proof` field states the
suite was never written, which is incoherent, and which is the honest description of
where the repository actually stands.

The fix is a `PARTIAL` status that mandates a debt reference and is rejected at phase
closure rather than chapter closure. That way a reviewer who spots a thin row has
somewhere to record it short of blocking a merged phase — which today they do not,
and that absence is part of why this drift accumulated.

It is not made here because it changes the meaning of all 511 invariant rows and
needs its own chapter and migration. Making it inside an audit would be exactly the
scope creep that produces an unreviewable change. It is recorded in
`docs/reviews/PHASE_5_PROOF_ARTIFACT_AUDIT.md` with the reasoning, so the next person
inherits the decision rather than the puzzle.

## How I would defend this in a design review

**"Why not just write the 23 missing suites?"** Several need harness support that no
chapter has built — process restart across a rebuild chunk boundary, forced lease
takeover, mixed producer versions. Writing them means building that harness, which is
a chapter of work. Doing it inside an audit would bury the finding in a large
implementation diff, and the finding is the valuable part.

**"Isn't a P2 on unproven tenant isolation too low?"** The exposure is bounded and I
checked the bound rather than assuming it. None of the 23 is a payment, fraud, ledger
or tenant correctness claim that another suite contradicts; the source-truth rows they
sit beside are proven. What is missing is the adversarial half — the canary scan, the
forced lease takeover, the restart boundary, the meter assertion. That is real, and it
is where the escaped findings of Phases 4 and 6 were found, which is why the trigger
is "before Phase 7 treats projection rebuild or offline replay as a trusted model
input" rather than a date.

**"How do you know 36 rows are really covered?"** By reading suite bodies, not method
names, and by searching for the underlying mechanism where a concern depends on one.
That is why the observability rows landed in the *unproven* bucket instead of the
drift bucket: `MeterRegistry` appears in no rebuild, replay or event-foundation test,
so there was no plausible class it could have been renamed to.

**"What stops this recurring?"** The gate now fails closed on any artifact the
repository does not contain, and I verified it fails closed by feeding it a fabricated
name rather than by trusting the tests. Six tests pin the behaviour in both directions
— missing class fails, real class passes, prose is ignored, basename fallback works,
and the repository index genuinely finds a committed suite. A `PRE_IMPLEMENTATION`
matrix can still be written in future tense; what it can no longer do is reach `PASS`
while naming something that was never built.
