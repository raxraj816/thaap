# Daily Deep Dive: 2026-06-15

This note explains the Chapter 7 PaymentIntent lifecycle hardening slice.

## 1. System Goal

We hardened `PaymentIntent` before adding deeper fraud, processor, and ledger
side effects.

The goal was to make the payment container trustworthy:

- complete the near-term status vocabulary
- reject impossible capture, cancel, and refund transitions
- expose reconciliation timestamps
- add optional description and constrained metadata
- reject unsupported currencies and absurd simulator amounts

This matters because downstream fraud, processor, review, webhook, and ledger
systems will treat PaymentIntent state as payment truth.

## 2. Plain-English Design Brief

A PaymentIntent is a state machine. It should not let callers skip real payment
events.

Without guards, a merchant could capture a newly created intent or refund a
payment that was never captured. That would create false lifecycle evidence
before processor simulation, ledgering, and fraud decisions exist.

What we built now:

- `PaymentIntentStatus` now includes the planned lifecycle vocabulary.
- `capture()` requires `REQUIRES_CAPTURE`.
- `refund()` requires `CAPTURED` and, in V1, requires the requested refund
  amount to equal the captured PaymentIntent amount.
- `cancel()` is allowed only from pre-terminal customer/action states.
- `PaymentIntentResponse` includes `createdAt` and `updatedAt`.
- PaymentIntent create supports `description` and constrained metadata.
- PaymentIntent create supports only `USD`, `EUR`, `GBP`, and `INR` for V1.
- PaymentIntent create caps amount at `100000000` minor units.

What we intentionally deferred:

- processor transitions into `AUTHORIZED` / `REQUIRES_CAPTURE`
- capture ledger entries
- refund entity and partial refund accounting
- dispute and chargeback state transitions
- per-merchant and per-currency transaction limits

## 3. Code Map

- `PaymentIntent` owns the domain state and transition guard clauses.
- `PaymentIntentStatus` owns the payment lifecycle vocabulary.
- `PaymentIntentController` owns create validation and public response shape.
- `PaymentIntentMetadataConverter` stores constrained metadata as JSON text.
- `WebhookSigningSecret` owns cryptographic webhook secret generation with
  explicit `SecureRandom` byte material.
- `RefundController` now relies on the idempotency service transaction boundary
  rather than misleading self-invoked `@Transactional`.
- `V1__create_payments_api_schema.sql` stores description and metadata.
- `PaymentIntentCreateContractTests` proves validation, timestamps, and
  metadata.
- `PaymentIntentLifecycleContractTests` proves transition guards.

## 4. Request/Data Flow

Create flow:

1. Merchant calls `POST /payment_intents`.
2. `MerchantContext` is resolved from `X-Api-Key`.
3. Bean validation checks amount bounds, supported currency, description length,
   and metadata shape.
4. `IdempotencyService` reserves the mutation key.
5. Customer ownership is checked by `(customer_id, merchant_id)`.
6. `PaymentIntent` is persisted with normalized currency, optional description,
   metadata, `createdAt`, and `updatedAt`.
7. `payment_intent.created` delivery rows are created for active endpoints.
8. The idempotency record stores a replayable public response.

Mutation flow:

1. Merchant calls `capture`, `cancel`, or `refund`.
2. `IdempotencyService` reserves the mutation key.
3. The PaymentIntent is loaded through tenant scope.
4. The domain method validates the current status.
5. Valid transitions update status and `updatedAt`.
6. Invalid transitions return `409 conflict` and release the idempotency
   reservation.

## 5. Database Invariants

- `payment_intents.description` is optional and capped at 500 characters.
- `payment_intents.metadata` is non-null JSON text and defaults to `{}`.
- `payment_intents.created_at` and `updated_at` remain required.
- Tenant ownership still flows through `(merchant_id, customer_id)` foreign key.

The schema does not yet encode every state transition. Those rules live in the
domain methods and are proven through contract tests.

## 6. Security And Privacy Invariants

Metadata is merchant-provided and useful for reconciliation, but it must not
become a secret or PII dumping ground.

The API constrains metadata to:

- 20 keys max
- key pattern `[A-Za-z0-9_-]{1,40}`
- non-null values up to 500 characters

The docs explicitly forbid PAN, CVV, secrets, and sensitive personal data in
metadata.

## 7. Fraud/ML Relevance

Fraud and ML workflows need reliable lifecycle timestamps and statuses.

This slice improves future fraud work by making sure:

- attempts are not scored against impossible parent-payment states
- analysts can correlate PaymentIntent timestamps with webhooks and attempts
- metadata can carry merchant reconciliation context without polluting payment
  security boundaries
- future labels will attach to a coherent lifecycle

## 8. Tests As Proof

`PaymentIntentCreateContractTests` proves:

- create returns and persists description, metadata, `createdAt`, and
  `updatedAt`
- unsupported currency `XYZ` is rejected
- amount over `100000000` is rejected
- invalid metadata keys are rejected
- existing idempotency, replay, and tenant ownership behavior still works

`PaymentIntentLifecycleContractTests` proves:

- cancel from `REQUIRES_CONFIRMATION` succeeds
- capture before authorization returns conflict and leaves state unchanged
- second cancel returns conflict and does not create duplicate webhook delivery
- refund before capture returns conflict and leaves state unchanged
- partial refund attempts return conflict and leave captured state unchanged
- full refund attempts from captured state move the PaymentIntent to `REFUNDED`

The targeted test run covered the PaymentIntent lifecycle, confirm,
idempotency, and migration proof set with 0 failures.

## 9. Staff Engineer Review Notes

The important tradeoff was to add status vocabulary without pretending all
transitions are implemented.

That is why `REQUIRES_CAPTURE` exists but current APIs do not move an intent
there yet. The processor/capture chapters must own that transition because it
represents a real authorization result.

The risk reduced is downstream falsehood: fraud, processor, ledger, and analyst
systems should not inherit impossible payment states.

## 13. Interview Narrative

The tradeoff I made was adding the lifecycle vocabulary now while enabling only
the transitions whose domain facts exist.

The invariant I enforced was: a PaymentIntent cannot be captured before it is
capture-ready, and cannot be refunded before it is captured.

The production risk I reduced was impossible payment state leaking into fraud,
processor, webhook, analyst, and ledger workflows.

I deferred processor, capture ledgering, partial refund accounting, disputes,
and per-merchant limits because each needs its own side-effect owner and tests.

The tests prove validation, metadata/timestamp response shape, state-transition
guards, and no state mutation after invalid operations.
