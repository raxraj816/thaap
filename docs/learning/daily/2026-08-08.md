## 2. Payment Processing Concepts Learned

- A timestamp on a payment record is part of the public contract, not decoration. `POST /refunds`
  was returning `createdAt` as `.400031361Z` while every later `GET` of the same immutable field
  returned `.400031Z`. No money, lineage or tenant invariant broke — but a consumer that stored the
  create response and compared it to a later read would see one field with two values, and would be
  right to treat that as corruption.
- The failure is worst precisely where it looks most harmless. Nothing throws, nothing logs, and
  the digits that differ are the ones nobody reads.

## 3. Fraud Detection Concepts Learned

- Event lineage is only as sound as the ordering key underneath it. `CanonicalEventCodec` refuses a
  payload timestamp finer than the database can store, which is what turned a silent divergence in
  the fraud-label and review-resolution streams into a loud `IllegalArgumentException`. That guard
  was written on 2026-08-01 and could not fire once on this machine.

## 4. Security Concepts Learned

- Nothing new about secrets today. The relevant security-adjacent lesson is about trust in
  evidence: a guard that cannot execute in your environment provides no assurance there, no matter
  how correct it is. `CanonicalEventCodec.validateInstant()` was right for a week and silent for a
  week.

## 5. Architecture / Design Notes

- **Fix precision at the source, not at the call site.** The codebase already carried roughly
  thirty ad-hoc `.truncatedTo(ChronoUnit.MICROS)` calls added since 2026-07-01, one per place
  someone suspected it mattered. Every one is a no-op on macOS, so nobody who added one could learn
  whether it was load-bearing. A rule applied by memory at 315 places will be forgotten at the
  316th; a clock that cannot produce the wrong value cannot be forgotten.
- **Truncate rather than round.** PostgreSQL rounds, so `.656610779Z` becomes `.656611Z` — an
  instant the application never held. Truncation keeps the stored value one that actually occurred
  in the process.
- **The scattering was the diagnosis.** When the same defensive call starts showing up across
  unrelated files, that is not diligence. It is a missing invariant at the source announcing
  itself, and the correct response is to ask why each site has to remember.
- **A shared test fixture is production state with no owner.** Spring hands one cached application
  context to every test class with a matching configuration, and nothing at the call site says how
  many classes that is. A `@BeforeEach` that resets a bean is therefore not local cleanup; it is a
  write to shared state, and the only reason it usually looks harmless is that most beans are
  rebuilt on use. The invariant is that a test must leave shared state as it found it, or must not
  share it — and since the sharing is invisible in the source, it has to be enforced by a gate
  rather than by noticing.
- **When a signal is missing, enumerate who can remove it before studying what stores it.** Three
  hypotheses about Micrometer died over several hours; one grep for `registry::remove` would have
  named the file. Suspect your own code before the library's, because your code is the part that
  changed.
- **An assertion over shared state must scope itself to what it is asserting about.** Both defects
  the randomized job found are the same sentence: a query that says "my fixture used one card" or
  "replay my events" was written against the whole table. The correct form names the fixture. A
  clean database makes the unscoped form work, which is why it survived — but working because
  nobody else left anything behind is not the same as being right.
- **A diagnostic must be able to answer the question it was built for.** Recording registry
  identity as `System.identityHashCode` cannot distinguish one object losing meters from two
  different objects, which is precisely the question. Identity in instrumentation should be a value
  the program assigns, not one the JVM derives.

## 7. Bugs, Surprises, Or Tradeoffs

- **The whole thing.** `Instant.now()` returns microseconds on macOS and nanoseconds on Linux. The
  defect entered on 2026-05-31 with the first payment entities and survived ten weeks, not because
  review was careless but because every test run in this repository's history executed on an
  operating system whose clock is coarser than the deployment target. The bug was unobservable by
  construction.
- **The gate paid for itself on its first run.** `43b7f36` added the first and only CI workflow
  this repository has ever had, yesterday. Its first execution found a ten-week-old production
  defect. The argument for CI was "stop enforcing by memory"; the actual return was "run somewhere
  that is not your laptop."
- **Tradeoff accepted:** two rapid calls can now land in the same microsecond where nanoseconds
  previously separated them. This is not a new risk — macOS has always been microsecond-resolution
  and the suite is green there — so Linux is becoming as coarse as the development machines
  already were.
- **Deliberately not changed:** the `400` and `500` input guards. They were correct throughout.
  Relaxing them would have made CI green by deleting the only honest reporting of the defect.
- **The four backlog-gauge failures were a second, unrelated defect**, and CI caught them after
  the timestamp fix landed: 1384 tests, 4 failures, 0 errors. See §7a.

## 7a. The Second Defect: A Gauge That Could Stop Existing

`ReviewBulkBacklogReadinessTests` read `-1.0` for both backlog gauges, which is the helper's
sentinel for "the meter is not in the registry" — not a stale value, an absent one.

Four hypotheses were tested and three died:

- **`meterRegistry.clear()` at `PaymentIntentConfirmContractTests:89`.** Dead twice over. Running
  the two classes together in CI's order passes, because they have different Spring context keys;
  and in the reproduction the clear runs at log line 11238, *before* the gauges are registered at
  13284.
- **Spring test-context cache eviction.** Dead. Re-running with
  `spring.test.context.cache.maxSize=200` fails identically.
- **Micrometer's weak reference being collected.** Dead. A probe against Micrometer 1.16.5 shows a
  collected gauge stays in the registry reporting `NaN`; it does not disappear. Our symptom is
  disappearance.

What is established: the failure is **position-dependent**. The class passes at position 47
(macOS), 21 (Linux container) and fails at 179 (CI) and 198 (local, reversed order). Instrumenting
the reproduction showed the gauges registered into registry `2062175164`, and the same live
registry 7,000 log lines later holding 319 meters with those two gone.

**At the time this section was written the mechanism was not identified, and the section said so.
It was identified later the same day — see §7b, which supersedes the paragraph below.**

What the instrumentation did reveal is a genuine design flaw, which is what was fixed. Every
surviving `decision_intelligence.*` meter is a counter or timer that `DecisionIntelligenceMetrics`
re-registers on every call. The two gauges were the only meters registered once, in the
constructor — so anything that removed them removed them permanently, while the counters silently
reappeared and hid the gap. `publishBacklogGauges()` now runs wherever the value is published, and
holds a strong reference rather than Micrometer's default weak one.

The lesson is the same shape as the timestamp bug, one layer up: **a signal whose whole purpose is
to report a silent failure must not itself be able to fail silently.** Nothing else reports a bulk
run whose worker died. A gauge that can stop existing, in a class where every neighbouring meter
heals itself, is the wrong design for that job regardless of what removed it.

Verified against the reproduction: at position 198, where it failed reliably, 4/4 pass and the
suite is 1384/0.

## 7b. What Actually Removed Them

`PaymentInvestigationObservabilityTests.setUp` did, in eleven lines of test code:

```java
registry.getMeters().stream()
        .filter(meter -> meter.getId().getName().startsWith("thaap.decision_intelligence"))
        .forEach(registry::remove);
```

It declares `@ActiveProfiles("test")` and `@SpringBootTest(properties =
"thaap.review-bulk.worker-enabled=false")` — **byte-identical** to `ReviewBulkBacklogReadinessTests`.
Spring caches one application context, and therefore one `MeterRegistry` bean, per distinct test
configuration. Thirty-one classes share that configuration, so they share one registry, and the
sweep in one of them is a sweep in all of them.

Everything else in §7a follows from that. The counters and timers reappear because
`DecisionIntelligenceMetrics` re-registers them on every call, which is why the registry still held
321 meters. The two gauges were registered once, in a constructor that runs once per context, so
they were gone for the life of that context. And the failure is position-dependent because the only
thing that decides the outcome is whether the investigation class ran before the bulk class.

**How it was found, after three wrong answers.** An instrumented `SimpleMeterRegistry` logged a
stack trace on every `remove` and `clear`, stamped each instance with a monotonic sequence number,
and carried two canary meters registered once in the same constructor as the gauges — a counter and
a *strongly* referenced gauge. One run at `-Dsurefire.runOrder=reversealphabetical` reproduced
1384 tests / 4 failures and answered every open question at once:

- registry `#49` logged `REMOVE name=thaap.decision_intelligence.bulk.backlog` with
  `PaymentInvestigationObservabilityTests.setUp` in the stack;
- the same registry later reported both canaries **present** and both gauges **absent**.

The surviving canaries kill three explanations in one observation. Same registry, so it was not
identity confusion. A once-registered counter survived, so nothing removes meters generally. A
once-registered *strong* gauge survived, so the weak reference was not it either.

**The search was looking in the wrong place.** All three dead hypotheses were about Micrometer. The
answer was in this repository, and `grep -rn 'registry::remove' src/test` finds it in one step. The
earlier investigation had correctly ruled out `meterRegistry.clear()` at
`PaymentIntentConfirmContractTests:89` — its context key genuinely does differ — and then
generalised that to "no test removes these meters" instead of to "that test does not".

**The instrumentation could not settle the question it was built for.** Registry identity was
recorded as `System.identityHashCode`, which cannot distinguish *this registry lost two meters*
from *this is a different registry*. Identity in a diagnostic has to be a value the program
assigns.

Fixed by giving both mutating classes a registry of their own. `@ExclusiveMeterRegistry`
contributes a `ContextCustomizer` whose identity is the annotated class, and because a context's
cache key includes its customizers, that class gets a context — and a registry — nobody else shares.
It is the same extension point Spring uses to isolate a class declaring bean overrides, which is why
`PaymentIntentConfirmContractTests` had accidental isolation already.

The first version of this fix was an inert property, `thaap.test.exclusive-meter-registry=<name>`,
which produces the identical cache-key split. It was replaced because it is a magic string: it names
nothing, it is copied without understanding, and a gate can only match it as text. An annotation
carries the intent in its name and can be checked as a type.

`MeterRegistryIsolationTests` fails the build if a `@SpringBootTest` class prunes a registry without
declaring ownership — verified the way `ER-0098` requires. It also asserts, through Spring's own
`SpringFactoriesLoader`, that the factory is registered at all; without that, deleting one line of
`spring.factories` would turn the annotation into a comment and nothing would go red. That
assertion was itself verified by deleting the registration and watching the gate fail.

One honest qualification: the isolation is **defence in depth, not what currently keeps the suite
green**. With the self-healing gauges in place the two classes now pass together even without the
isolation — measured, by removing the registration and re-running them, not assumed. The isolation
matters for the next once-registered meter, which will not have a self-healing sibling.

Recorded as `ER-0101`.

The §7a fix stays. It was justified on its own terms — a signal whose only job is to report a
silent failure must not be able to fail silently — and it is now the second line of defence rather
than the only one.

## 7c. The New Gate Paid For Itself Immediately, And Corrected Me Twice

The randomized-order job failed on its **first ever execution**, and again on its second, on two
different classes that had nothing to do with meters:

- `PaymentInvestigationScopeBoundaryTests` asserted `SELECT DISTINCT card_fingerprint FROM
  payment_methods` equals 1, to prove its own fixture was not vacuous. The query is unscoped, so it
  counted rows left by whichever class ran before it. It read 2.
- `PaymentInvestigationNavigationScopeBoundaryTests` failed in `setUp`, because
  `RiskWorkspaceScenario.drainProjection` replays *every* event in the database, and a leftover
  event whose subject a later class had deleted comes back `QUARANTINED` instead of `APPLIED`.

Auditing the family: **15 of the 41 classes using `RiskWorkspaceScenario` never cleaned the
database; 26 did.** The 13 beyond the two that failed were latent instances of the identical defect,
and the pinned ordering would have kept hiding them. All 15 now clean, and the fingerprint query is
scoped to the fixture's own merchants — it should measure the fixture it asserts about, not the
table. `ER-0102`.

**And a claim I wrote in the workflow was wrong.** I said a failing ordering was reproducible from
the printed seed with one flag. Replaying CI's seed `84512339639` on macOS produced a completely
different ordering — CI started at `ReviewNoteCipherTests`, this machine at
`PublicationRecoveryContractTests`. The reason is that surefire shuffles the list the directory
scanner produced, and *that input order is itself filesystem order*, so one seed means two
permutations across ext4 and APFS. `runOrder=alphabetical,random` does not fix it either; surefire
honours only the first entry, which I checked rather than assumed. The workflow now says a seed
replays on a runner of the same platform, and carries a `workflow_dispatch` seed input so a failing
ordering can be replayed where it is actually reproducible.

The lesson is small and sharp: **a claim about reproducibility is a claim like any other, and has
to be executed before it is written down.** I wrote that one from how the flag reads, and the flag
reads correctly — it is the input to the shuffle that is not stable.

## 13. Payment Processing Concepts Learned

- **A version number is a promise about liability, not about features.** `1.0.0` on a
  payments product reads to almost every reader as "ready for production traffic",
  and THAAP moves no real money and holds no PCI scope. So the boundary is stated in
  the changelog itself, in the section that explains what a THAAP version number
  means, rather than in a footnote — and a test fails the build if that text goes
  missing.
- **The client IP is a payment control, not a log field.** Behind a load balancer,
  the socket address belongs to the balancer. Without forwarded headers, every
  per-IP rate limit collapses into one bucket and every per-IP velocity feature
  becomes a constant — still computed, still recorded in the fraud snapshot, and
  meaning nothing. A degraded feature that keeps producing values is worse than one
  that is switched off.

## 14. Fraud Detection Concepts Learned

- **Two peppers with one value is one pepper.** The hash pepper keys credential and
  replay identity; the correlation pepper keys the stable pseudonyms that tie a
  customer's PAN, email and phone together across time. They have deliberately
  different lifecycles: rotating the first is routine, rotating the second is an
  offline re-key of fraud identity. Set them to the same string and a routine
  credential rotation silently splits every customer's fraud history in two. The gate
  refuses reuse for exactly this reason.

## 15. Security Concepts Learned

- **This repository publishes working secrets on purpose, and that is the risk.** The
  compose stack, both READMEs and the test fixtures all carry real, usable values so
  that a stranger can start THAAP without a secrets ceremony. That is the right call,
  and it makes "somebody copied the quickstart that was written to be copied" the
  most likely route to a deployed system holding a known key. So every published
  value is listed in the contract and refused, and a test scrapes those four files
  and fails if a newly committed default is missing from the list.
- **A validator must not quote what it rejected.** The obvious error message —
  "THAAP_HASH_PEPPER is invalid: local-hash-pepper-not-for-production" — writes that
  secret into every log aggregator the startup output reaches, converting a
  configuration mistake into a disclosure. The message names the variable, the
  reason, and the command that generates a good one, and never the value.
- **Fail before you touch anything.** The refusal runs as an `EnvironmentPostProcessor`,
  so an instance that must not run never opens a connection or takes the Flyway lock.

## 17. Bugs, Surprises, Or Tradeoffs

- **The gate was registered at a path that does not exist in Spring Boot 4.** Written
  first as `META-INF/spring/org.springframework.boot.env.EnvironmentPostProcessor.imports`
  — correct for Boot 3, and silently inert in Boot 4, which loads environment
  post-processors through `spring.factories` under
  `org.springframework.boot.EnvironmentPostProcessor`. Fifty-five unit tests passed
  against a gate that was wired to nothing. The startup test caught it on its first
  run, which is the entire reason that test class exists. See the deep dive, §15.
- **`build.time` was excluded rather than kept.** It is the natural thing to record
  and it is the only build-info property that is not a function of the source:
  keeping it would mean one commit producing a different artifact on every rebuild,
  retiring the reproducibility Chapter 60 had just established.
- **The commit has to be passed in, not read.** `.dockerignore` excludes `.git/` as a
  security control, so the build that most needs its provenance is the one that
  cannot look it up. `unknown` is the honest default for a developer build;
  `release-identity-check.sh` is what stops a release carrying it.
- **The placeholder-marker rule cannot reach a Base64 key, and does not pretend to.**
  Every marker contains a hyphen or a letter outside the hexadecimal alphabet, which
  is what keeps a generated secret from tripping it. Base64 KEKs are covered by the
  shape rule and the published-value list instead. The test is scoped to opaque
  tokens to say so out loud rather than quietly passing on three of eight.
