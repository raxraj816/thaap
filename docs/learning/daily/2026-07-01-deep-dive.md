# Daily Deep Dive: 2026-07-01

## 1. System Goal

THAAP hardened nine Chapter 19 claims:

- Webhook event/delivery routing may only occur inside the transaction that
  creates or mutates the payment/refund truth being announced.
- V8-to-V9 migration preserves known delivery truth without fabricating an
  event fan-out relationship that V8 never stored.
- Webhook operations expose a bounded failure cause for every normal,
  recovery, preparation, and bulk-disable failure path.
- Callback acknowledgement requires a supported, syntactically valid HTTP text
  status line rather than any token beginning with `HTTP/`.
- Migration cannot preserve aggregate retry/success/failure claims without
  authoritative attempt evidence.
- Disabled legacy endpoints cannot strand queued delivery work.
- Signature freshness excludes potentially unbounded dispatch lock wait.
- Payload and response-head byte limits are enforced exactly at runtime.
- Bulk-disable metrics count actual state transitions under concurrency.

These claims matter because webhook records are merchant-visible integration
truth. Orphan records can announce a payment mutation that rolled back, while
invented lineage can make historically separate emissions appear identical.
Collapsed metrics hide whether merchants, THAAP infrastructure, or endpoint
operations caused failures. Permissive protocol parsing can manufacture
successful acknowledgement from malformed response bytes.

## 2. Plain-English Design Brief

Think of a webhook event as a receipt for a domain fact. The fact and the
receipt must enter the database together. `Propagation.MANDATORY` rejects
routing when the caller has not already opened that shared transaction.

For migration, V8 retained pristine queued receipts but no event identity or
attempt evidence. Attributes such as merchant, resource, event type, and
timestamp are not a safe sibling grouping key, so each accepted pristine row
gets a synthetic event whose ID equals the delivery ID. A row claiming execution
fails before V9 schema creation because preserving its aggregate status would
manufacture incomplete attempt history. Queued work for an inactive endpoint is
terminalized rather than left unreachable.

No debt was registered. There is no truthful future reconstruction step because
the missing historical identity and attempt evidence were never persisted.

For observability, outcome says whether an attempt succeeded, retries, failed
terminally, or became uncertain; delivery status says whether work remains;
bounded error code says why. `thaap.webhook.failures` therefore uses only
canonical `event.type` and enum `error.code`, never tenant or endpoint identity.
The finalization transaction returns those committed classifications directly;
the executor never rereads the delivery after commit merely to decide which
metric to emit.

For protocol handling, the socket transport supports HTTP/1.0 and HTTP/1.1 text
responses. HTTP/2 is binary and outside this boundary. A valid response needs
an exact supported version token, three ASCII status digits in `100..599`, a
control-safe reason phrase, and a complete bounded header section.

## 4. Request/Data Flow

1. A merchant sends an idempotent payment-intent or refund mutation.
2. `IdempotencyService` reserves the key, then opens the operation transaction.
3. The controller creates or mutates payment/refund truth.
4. `createDeliveriesInCurrentTransaction` joins that transaction, creates one
   immutable event, and fans it out to active subscribed endpoints.
5. The domain mutation, webhook state, and completed idempotency response commit
   together; any failure rolls them all back.
6. A separate executor performs external HTTP only after committed work exists.

## 5. Database Invariants

- Every delivery references a same-merchant immutable event.
- Event type and resource identity agree across event and delivery rows.
- One post-V9 event has at most one delivery per endpoint.
- Every accepted pristine V8 delivery obtains a non-null event reference, but no
  unsupported sibling relationship or attempt history is inferred.
- Unsupported V8 execution state is rejected before V9 creates new tables.
- Pristine queued work for inactive legacy endpoints is terminal and explained.

Composite foreign keys and unique constraints enforce these storage claims.
`MANDATORY` protects the application transaction boundary that schema
constraints alone cannot express.

## 6. Security And Privacy Invariants

This slice introduces no new secret material. Its security contribution is
integrity: a future internal caller cannot accidentally publish standalone
merchant-visible webhook truth outside the payment/refund transaction.

The migration continues to construct allowlisted immutable payload fields and
does not invent recoverable signing secrets for legacy endpoints.

## 7. Fraud/ML Relevance

Reliable event lineage matters to replay, operational analytics, labels, and
future datasets. False grouping could undercount emissions, collapse distinct
records during deduplication, or teach downstream systems that unrelated
deliveries were one event.

The migration deliberately avoids reconstructing fan-out lineage because the
source evidence is absent.

## 9. Staff Engineer Review Notes

The transaction precondition is runtime-enforced because Java's type system
cannot represent “an active Spring transaction exists.” The method name makes
the precondition visible during code review, and the negative test prevents a
future annotation removal from silently weakening atomicity.

Changing propagation to `REQUIRED` would be dangerous: it would work for current
callers but silently create an independent transaction for a future bare caller.
The conservative migration costs perfect historical fan-out analytics, but it
preserves facts rather than manufacturing confidence.

The observability escape happened because prior tests asked “was a counter
incremented?” rather than “can an operator tell two causes apart?” The protocol
escape happened because prior hostile tests varied status number and framing
but not the version token. Both are examples of proof-shape failure: tests
exercised the implementation without falsifying the whole promise.

The final five escapes shared the same shape. Migration proof checked whether
DDL completed, not whether aggregate state still had its required child
evidence. Protocol proof checked obvious oversize, not exact byte accounting.
Timestamp proof checked cryptographic correctness, not preceding lock time.
Metrics proof checked sequential increments, not the state-change race between
observation and update. The correction is to derive proof from the cross-boundary
failure sequence before accepting implementation-shaped tests.

## 14. Why Example-Level Fixes Kept Failing

The repeated closure failure was not that HTTP has infinitely many edge cases.
It was that review selected one malformed representation at a time:

- invalid status number
- malformed version token
- missing final empty line
- oversized response head

Those tests left the next parsed component—response fields—outside the proof.
The same shape appeared in configuration: runtime timeout tests never examined
the conversion from a nanosecond-capable `Duration` into integer milliseconds.

The corrected mental model is a source-domain-to-state-transition table:

| Boundary | Complete family |
| --- | --- |
| Field name | letters, digits, every allowed token punctuation, separator colon, whitespace, delimiters, controls, DEL |
| Field value | tab, visible ASCII, every control, DEL |
| Field framing | missing colon, whitespace before colon, obsolete folding, missing CRLF, missing final empty line |
| Duration conversion | null, negative, zero, fractional-millisecond, exact 1 ms, exact integer maximum, maximum plus one, conversion overflow |

`responseHeaderGrammarClassifiesEveryOctetForTheAsciiContract` proves all 256
input-octet partitions without hand-picking examples.
`socketTransportRejectsMalformedHeaderFieldsBeforeAcknowledgingSuccess` then
proves representative invalid families through the actual socket parser.
`webhookTimeoutConfigurationRejectsEveryUnrepresentableOrUnboundedDuration`
proves the entire DNS-resolution/connect/request configuration conversion
domain through one shared production validator.
`malformedSuccessfulResponseHeadCannotBecomeDurableSuccess` closes the proof
ladder by asserting the real executor, attempt row, and delivery row preserve
retry truth rather than turning a malformed `204` into terminal success.

The repository process now requires `Boundary family review: PASS`. An escaped
grammar, numeric, concurrency, dependency, migration, or authorization finding
invalidates its whole family until partition proof and real-boundary regression
both pass.
