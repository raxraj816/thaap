# Daily Deep Dive: 2026-06-01

## 1. System Goal

We implemented the API error contract and request correlation foundation:
standard JSON errors, validation formatting, request ID propagation, logging
MDC, framework exception handling, and tests across common failure classes.

This matters because payment clients retry, reconcile, debug, and escalate
failures. A payment platform needs stable failure semantics, not only stable
success responses.

## 2. Plain-English Design Brief

The mental model:

- `RequestIdFilter` ensures every request has an `X-Request-Id`.
- The request ID is returned to clients and added to logging MDC.
- `GlobalApiExceptionHandler` converts framework/domain exceptions into one
  response shape.
- Validation errors report fields and messages without echoing rejected values.
- Unexpected server errors return a generic message while logs keep details.

What would go wrong without this:

- Clients would receive inconsistent framework-default errors.
- Support/debugging could not connect a merchant report to server logs.
- Validation failures might leak sensitive request values.
- Idempotency conflicts and auth failures would look different from other API
  errors.

## 3. Code Map

- `RequestIdFilter` reads or generates `X-Request-Id`, stores it on the request,
  writes the response header, and places it in MDC.
- `ApiErrorResponse` defines the standard error envelope.
- `ApiErrorField` defines per-field validation error details.
- `GlobalApiExceptionHandler` maps validation, bad request, auth, not found,
  conflict, framework 404, and unexpected errors into the standard shape.
- `apps/payments-api/src/main/resources/application.yml` includes request ID in
  the logging pattern.
- `ApiErrorContractTests` proves the public contract across representative
  failures.
- `apps/payments-api/README.md` documents request ID and error response
  examples.
- `docs/learning/concepts/API_ERROR_CONTRACTS_AND_REQUEST_IDS.md` captures the
  concept from first principles.

## 4. Request/Data Flow

Normal error flow:

1. A request enters the servlet filter chain.
2. `RequestIdFilter` accepts a valid request ID or generates a UUID.
3. The filter stores the request ID as a request attribute.
4. The filter writes `X-Request-Id` to the response header.
5. Controller or framework code raises an exception.
6. `GlobalApiExceptionHandler` reads the request ID.
7. The handler returns `ApiErrorResponse` with request ID, timestamp, status,
   error code, message, path, and optional field errors.
8. MDC is cleared in the filter `finally` block.

Fallback flow:

1. If the filter did not run, the exception handler still generates a request
   ID.
2. The handler writes that request ID to the response header and body.

## 5. Database Invariants

No schema changed on this day.

The payment reliability invariant was API-level:

- mutating APIs and future idempotency behavior need deterministic error shapes
  so clients can decide whether to retry, fix input, or stop.

Future storage relevance:

- persisted audit logs, fraud decisions, webhook deliveries, and support cases
  should eventually be able to connect back to request IDs.

## 6. Security And Privacy Invariants

Important invariants:

- validation errors do not echo rejected values
- unexpected exceptions do not leak stack traces or internal messages
- request IDs are bounded to 128 visible ASCII characters before propagation
- invalid tenant authentication failures use the standard contract
- MDC cleanup prevents request IDs from leaking between requests on reused
  threads

The security principle is controlled disclosure: tell clients enough to fix or
correlate a problem, not enough to expose sensitive internals.

## 7. Fraud/ML Relevance

Request correlation becomes future investigation infrastructure:

- a merchant support ticket can cite a request ID
- logs can connect the request to payment intent, payment attempt, fraud
  decision, review case, or webhook delivery
- analysts can reason about a timeline of failed and successful attempts
- model-serving failures can later be traced without exposing model internals to
  clients

The fraud lesson: observability starts before ML. If events cannot be traced,
fraud explanations become guesswork.

## 8. Tests As Proof

`ApiErrorContractTests` covers:

- provided request ID echoed in header and error body
- generated request ID propagation
- fallback request ID when the filter did not run

## 9. Staff Engineer Review Notes

Tradeoff:

- We kept a simple global exception handler instead of introducing a domain
  exception hierarchy too early.

Risk reduced:

- Clients no longer depend on framework-default error bodies that can change or
  leak details.

Kept reversible:

- Error codes are simple and can be refined as domain-specific payment, fraud,
  ledger, and webhook exceptions appear.

Dangerous overbuild:

- Creating dozens of domain exception classes before the domain behavior exists
  would produce naming churn without stronger guarantees.

## 13. Interview Narrative

Practice saying this out loud:

- The tradeoff I made was to standardize the API error boundary early while
  deferring a richer domain exception hierarchy until payment and fraud
  semantics require it.
- The invariant I enforced was that every API failure returns a request ID,
  stable status, stable error code, message, path, and safe field errors.
- The production risk I reduced was untraceable or inconsistent payment API
  failures during retries, merchant support, and fraud investigations.
- I deferred domain-specific exception classes because framework and
  validation-level failures were the immediate contract risk.
- The tests prove request ID propagation, validation formatting, auth/not-found
  conflict behavior, unknown-route handling, and safe internal-server-error
  responses.
