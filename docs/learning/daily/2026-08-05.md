## Three things worth remembering

### 1. A missing constraint can be the design, not a defect

The bulk item table has no foreign key to `manual_review_cases`. Measured against
the plan's sentence "V90 adds tenant-qualified foreign keys," that reads as a
gap, and the obvious move is to add it. Adding it would have been wrong.

Resolving the review at admission time is exactly what leaks: a request naming
another tenant's review case would fail differently from one naming a review case
that does not exist, and the difference is an existence oracle. The frozen design
accepts the request, binds the item to its tenant through the request's own
foreign key, and terminates the unknown or foreign review as a per-item
`NOT_FOUND` at the mutation boundary — which is why `NOT_FOUND` is in the frozen
item-state table at all.

The check that caught this was reading the existing test's comment before
changing the schema. The lesson: when a constraint looks absent, find out whether
something depends on its absence before adding it. The frozen state table was the
evidence, and it was already written down.

### 2. "Each proof passes" and "the proofs pass together" are different claims

Adding a migration test with its own `@Container` turned the full suite red in a
class nobody had touched, with a missing-bean error that looked nothing like
resource exhaustion. This was the second occurrence of the same failure in one
day; `ER-0094` had already corrected it.

The first correction said: extend the shared base in areas that already have one.
That was followed exactly, and the defect recurred, because the migration package
had two container-declaring classes and no base. A correction phrased around a
location in the current tree does not bind the next case. `ER-0095` restates it
as a property of the risk: no class declares its own container, and a package
gets a base when it acquires its second such class.

### 3. Assert the column set, not the columns you thought of

The saved-view lineage proof asserts the table's *entire* column set rather than
checking that specific forbidden columns are absent. A view that stored a cursor
or a captured result page could serve rows frozen at save time as though they
were current — and a test listing the columns it expects to be missing cannot
catch a column nobody imagined. The same shape is used for the Spring Batch
metadata scan, which discovers `BATCH_*` tables and their text columns from
`information_schema` rather than from a hand-written list, and asserts the
discovered list is non-empty so it cannot pass by finding nothing.

## Chapter 56 — the window that can never show today

The first insight proofs failed in a way that looked like a bug and was not.
Create a payment, drain the projection, ask for insights: nothing. Zero rows,
zero denominators, empty money.

The cause is the frozen range contract. Every window is UTC-day-aligned, must end
at or before now, and defaults to "the previous seven complete UTC days." The
latest aligned boundary that is not in the future is the start of *today* — so
the current partial day is never observable, by construction. That is the promise
working: comparing a half-finished day against seven complete ones is exactly the
distortion the alignment rule exists to prevent.

Two things follow. First, a proof that builds its population "now" has to shift
those rows into a complete prior day, and shifting only the column the filter
reads violates `ck_payment_risk_projections_intent_time` — the whole row moves or
none of it does. Second, this belongs in the dossier, because the next person to
write an insight test will hit the same wall and will be tempted to "fix" the
range validator.

The general lesson is the same one the missing foreign key taught: when a system
returns nothing where you expected something, find out what the contract promises
before deciding the code is wrong.

The last two rows were the operationally interesting ones. `C55-OBS-001` needed a

directions — the bulk package declares no aggregate route and imports no insight
code, and the insight package declares no mutation mapping and never reaches into
bulk. Two owners publishing the same number under different as-of semantics is
exactly the ambiguity that boundary exists to prevent.

## Where Chapter 56 stands

Eight of twelve rows hold on executed evidence. The two that took the most care
were the reconciliation rows, and they are the ones worth remembering.

`C56-OUT-001` does not compare the published distribution against another derived
number — it compares it bucket-for-bucket against a `GROUP BY` over the projection
itself, and each money figure against that table's own sum columns. The point is
traceability: a total nobody can walk back to a specific payment is exactly the
kind of confident wrong number this product exists to avoid.

`C56-REV-001` reconciles backlog against authoritative review rows and every
counted assignment against a durable `review_assignment_events` row, so throughput
cannot be a derived guess. It also pins the thing the platform genuinely does not
know: conflicted attempts publish `null` with a named status, because a `0` there
asserts that no conflict ever happened, and the source cannot support that claim.

Drill-through was the dependency blocking two further rows, so it got built rather
than deferred. Two decisions in it are worth keeping.

The descriptor carries only closed filter values and the aligned range — no
merchant, operator, generation, or row id — and the tenant is re-derived from the
caller's own credential on replay. The proof has a *neighbour* replay the identical
descriptor and receive an empty page, which is the only way to show the filter is
not the thing carrying tenancy.

The filter is handed to the search route in memory, not through the URL. The route
allowlist carries only UUIDs and static slugs; a filter in the address bar would be
both unvalidated input and a shareable link into another operator's view. And a
segment the search grammar cannot express (`UNKNOWN`, a projection placeholder)
offers no control at all — a link that cannot reproduce its own segment sends an
analyst to a population that disagrees with the card they clicked, which is worse
than no link.

Changing the response record made the committed OpenAPI artifact stale, and the
drift gate caught it in the full suite rather than in review. Regenerating from the
runtime contract fixed it and the compatibility gate confirmed the change was
additive. That gate earning its keep on an ordinary feature change is the point of
having it.

### The proof that changed shape when the system pushed back

The snapshot row was supposed to be proven by forcing a generation activation
during a read. Attempting one directly in the database is refused:
`projection activation requires current complete reconciliation`.

The first instinct is to work around the guard. The better answer is that the
guard *is* the evidence. A generation cannot be swapped casually at all, which is
strictly stronger than surviving one forced swap, so the proof now asserts the
refusal and then asserts the active generation is unchanged and a fresh read still
names it.

Two smaller things fell out of it. My fabrication retired the live generation
before the refused insert, and because those were separate auto-commit statements
the retire stuck — taking the insight surface down and failing a later assertion.
A test that half-applies a forbidden change is breaking the system rather than
observing it, so the attempt now runs in one transaction and a refusal leaves
nothing behind. And planner choice on a three-row fixture is meaningless, so the
index proof disables `enable_seqscan` and requires an index plan: that shows the
index is *reachable by the shipped query shape*, which is a different and more
honest claim than "the query was fast".

All twelve rows now hold. The one limit stated rather than hidden: plans are
measured on fixture-sized data, so they prove reachability, not latency at scale.

## Chapter 57 — evidence that existed but was never claimed

Chapter 57 arrived with roughly sixty test methods across ten classes and every
one of its twelve matrix rows still reading `PENDING`. The tests passed. The
matrix said nothing had been proven.

That gap is worth naming because it is the mirror image of the usual failure. The
usual failure is a matrix that claims more than the tests support. This was a
matrix that claimed less — which is safer, but not harmless: an unclaimed row is
indistinguishable from an unproven one, so the next person either redoes the work
or, worse, trusts the row and ships. Reconciling them meant reading each test's
method names against the row's invariant and writing down which adversarial
partition each one actually closes.

Two things fell out of doing that honestly. `C57-CMP-001` looked closed — a
compatibility gate with 17 unit tests and a passing negative fixture — but the
gate proves a field did not *disappear*, not that its *meaning* survived. Money
staying an integer minor unit is a semantic claim no structural diff makes, so
the row stays `PENDING` with that named. And `C57-OBS-001` had no proof at all:
version resolution is the one place every public request passes through and the
requested value is attacker-controlled free text, so it is the easiest place in
the system to build an unbounded time series. Twenty-six distinct hostile values
now have to land on one counter, or the test fails.

The lesson is that a proof matrix is a claim about evidence, and an unmapped
passing test is not yet evidence — it is only a test.

## Chapter 58 — the SDK test that runs against a real socket

The Python SDK's security suite does something most client-library tests do not:
it stands up a real `ThreadingHTTPServer` and drives the wrapper against actual
sockets. That choice is what makes four of its claims provable at all.

You cannot prove "redirects are not followed" against a mock, because a mock has
no redirect to follow. Same for "ambient proxy environment variables are
ignored" — the failure mode is a hostile `HTTPS_PROXY` in the caller's shell
silently intercepting sandbox traffic, and only a real transport can be asked
whether it honoured it. Same again for the sharpest one: a read timeout must be
reported *distinctly* from an unknown mutation outcome, because that distinction
is exactly what tells an integrator whether replaying is safe. Get it wrong and
the SDK turns an ambiguous timeout into a double charge.

The suite also ran from a clean `venv` built from `pyproject.toml` rather than
from the repository working tree. That is a different claim from "the tests
pass": it proves the declared dependency set is sufficient and the package is
installable as published. A library that only imports from its own source tree
has not been shown to work for anyone else.

What is still missing is honest to state: the end-to-end sandbox quickstart has
not been run against a live application, and regeneration byte-stability is
scripted and pinned but needs Docker, so it is asserted rather than demonstrated.
Four rows `PASS`, eight `PENDING`.
