## 2. Payment Processing Concepts Learned

- A payments product needs a standing decision lens because seemingly small
  implementation choices can affect authorization correctness, ledger safety,
  fraud lineage, tenant boundaries, and operator trust.
- A PaymentIntent is a state machine. Invalid capture/refund transitions must
  fail before processor and ledger chapters exist, because downstream systems
  will treat PaymentIntent state as payment truth.
- A refund API that marks a whole PaymentIntent `REFUNDED` cannot safely accept
  arbitrary partial amounts; either it has refund accounting, or it only allows
  exact full refunds.

## 3. Fraud Detection Concepts Learned

- Fraud systems are product systems as much as model systems: risk decisions
  must be useful to merchants and analysts, explainable under review, and safe
  to evolve as signals and models mature.
- THAAP's fastest winning wedge is a transparent, replayable fraud-risk loop:
  simulate realistic payment risk, explain the decision, let an analyst act,
  and feed the outcome back into rules, labels, and model evaluation.

## 4. Security Concepts Learned

- The role agreement makes tenant isolation, privacy, and payment-security
  boundaries default concerns rather than optional review items.
- Metadata is useful for merchant reconciliation, but it must be constrained and
  documented as non-sensitive: no PAN, CVV, secrets, or sensitive personal data.
- Cryptographic secrets should be generated from explicit random bytes, not
  UUID formatting, even when UUID entropy is acceptable for scaffolding.
- Explicit local types in production payment/security code make reviews and
  learning easier because important domain objects are visible at the line
  where they are introduced.

## 5. Architecture / Design Notes

- The agent's default posture is now explicit: convert founder intent into
  chapter-sized vertical slices, defend the architecture like a
  Stripe/Mastercard-style design review, and keep the apprenticeship trail
  current.
- The product should not chase broad Stripe/Mastercard parity early. It should
  sequence work by the shortest path to a demoable merchant-payment-risk-
  analyst-feedback loop with durable state, tests, auditability, and
  explainability.
- In Spring, self-invoked `@Transactional` methods are not a reliable boundary.
  For the current mutation paths, `IdempotencyService` owns the real transaction
  boundary through `TransactionTemplate`, so annotations on protected controller
  helpers were removed to avoid teaching the wrong mental model.
- Chapter 7 hardening pulled review findings forward before fraud/processor
  orchestration. The implementation added status vocabulary but only enabled
  transitions whose domain facts already exist.
