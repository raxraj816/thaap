# Deep Dive: 2026-08-07 — What A Proof Field Is Actually Promising

## The question

`ER-0096` and `ER-0098` both closed on the same shape: a gate that existed, had never
been executed, and was red. The correction was that a script named as proof needs a
recorded run before its row closes. This session asked the wider question that correction
implies — not "was it run?" but "does it exist at all?"

## Method, and why it was chosen

Extract every backticked test class and file reference from the `Proof` field of all 42
matrices, resolve each against the filesystem, and classify what survives.

The classification is the part that needed care. A missing name has two very different
explanations: the concern is genuinely held under a different name, or the concern is not
held at all. Only the second is a finding. Distinguishing them cannot be done from
naming, because naming is precisely what drifted.

So the rule adopted was: where a concern depends on a mechanism, search the repository
for the *mechanism*, not the name. "Is rebuild observability proven?" becomes "does any
test in this repository reference `MeterRegistry` and rebuild?" That question has an
unambiguous answer. It returned nothing, and that is why `C50-OBS-001` is a real gap
rather than a suspected one.

I tried a faster keyword sweep across all suites first and discarded it. It produced
obvious false negatives — `DomainEventWriterContractTests` proves tenant independence in
a method whose name my pattern did not match. Reporting from it would have been
`ER-0098`'s recorded mistake in a new costume: inferring a boundary from a convenient
surface. The audit says so explicitly, so a later reader knows which claims are
mechanism-verified and which are not.

## What the numbers mean

59 unresolved references. 36 were naming drift; the dossiers, where they name classes at
all, name only real ones — the reality was recorded, just not in the artifact that
carries traceability forward. 23 were real.

The 23 cluster by concern, not by chapter: observability, privacy, restart, deployment,
forced-ordering concurrency, authorization. That distribution is the finding underneath
the finding. When eleven planned suites collapse into seven test methods, what survives
is the ordinary path. What falls out is the adversarial half — the canary scan, the lease
takeover, the restart boundary, the meter assertion. Every escaped finding in Phases 4
and 6 was found in exactly that territory.

## The status vocabulary problem

`invariant-proof-check.py` required every row to be `PASS`. So a row that was held on the
ordinary path and unproven adversarially had no representation. It could be `PASS` — a
lie of omission — or it could block a merged phase.

That is not a cosmetic gap. It is the mechanism by which the condition survived review.
A reviewer who noticed a thin Chapter 46 row at closure time had exactly two moves
available, and one of them was unavailable in practice.

`PARTIAL` closes it, with two constraints that stop it becoming a loophole:

1. A `PARTIAL` row must cite a `TD-NNNN`. An unowned partial row is the state the audit
   was raised about, so the gate rejects it.
2. `--reject-partial`, passed by `phase-closure-check.py`, makes a *phase* unable to
   close while any partial row remains — while a *chapter* may proceed honestly.

The asymmetry is the whole design. Chapter closure is frequent and local; phase closure
is rare and is where the aggregate claim gets made. Debt is tolerable in the first and
not in the second.

Implementation cost: about thirty lines, because exactly one line in the repository
enforced row status. The vocabulary had never been load-bearing, only unexamined.

## Paying it, and what payment taught

Six rows retired. Three needed production changes, which is the more interesting outcome
than the tests.

`ProjectionRebuildMetrics` had no duration and no lease-recovery meter, though
`ProjectionRebuildStore` had been writing `LEASED` versus `LEASE_RECOVERED` as durable
events since Chapter 50. The signal existed in the event log and not in the metric. The
temptation was to infer recovery in the dispatcher from the fencing epoch — and that is
wrong, because the epoch increments on every claim, fresh or recovered. So the store now
carries a `recovered` flag on the lease: the component that *knows* reports the fact
rather than a downstream component guessing it.

`TransactionalDomainEventWriter` emitted nothing. Its rejection counter now fires
immediately rather than after commit, because the rejecting transaction is about to roll
back — a deferred counter would make an integrity failure indistinguishable from an
ordinary rollback, which is the single distinction that signal exists to draw.

## Where the schema taught me something

Forcing a replay lease takeover looked like a one-line `UPDATE` setting
`lease_expires_at` into the past. `ck_replay_dataset_manifests_time` rejects it: the
constraint requires `lease_expires_at > updated_at`, so **an already-expired lease cannot
be written**. Expiry is only reachable through the passage of time relative to the claim.

That is a good constraint — it forbids a class of corrupt state outright — and it means a
test must reach expiry the way production does. Anchoring on `updated_at` left
microseconds of margin and raced. Anchoring on `created_at`, which precedes a full HTTP
creation round trip and a claim transaction, gives a real margin.

It is a margin, not a guarantee, and the note in the test says so. A deterministic
version needs the injectable `Clock` the worker already accepts; rewiring it class-wide
looked riskier than the margin, and that judgement is recorded rather than hidden.

## What I got wrong

I reported the replay execution probe as having zero call sites, and proposed wiring it.
My grep was `probe\.`; the field is `executionProbe`. Both methods were wired at exactly
the two documented points. Nothing was built on the claim, but it was stated to the user
as a finding before it was checked, and a one-character-wider pattern would have caught
it.

I also seeded a privacy canary as a full-looking credential in a field that holds a
12-character prefix, then had to chase whether the resulting failure was a production
leak. It was not. The right response was not simply to fix the fixture: the margin
between "identifier" and "secret material" there is one character, so the test now pins
the property rather than the coincidence.

## The recursion worth naming

`ER-0098` recorded that removing a gate from the readiness run would fail a test. It
would not have. The readiness tests stubbed each checker and asserted only the exit code;
an unreferenced stub is never executed and the run still exits zero.

So a process correction written to prevent invisible gate failures was itself an
invisible gate failure. It survived because nobody deleted the line to watch a test go
red.

The durable rule this session ends on: **when you write a process correction, execute it
against the failure it claims to prevent.** Not read it. Not reason about it. Break the
thing on purpose and watch the gate catch you. I did that for the invocation test — deleted
`openapi-contract-check.py` from the readiness script, confirmed the failure, restored it,
confirmed the pass — and that is the only reason I believe the enforcement is real this
time.
