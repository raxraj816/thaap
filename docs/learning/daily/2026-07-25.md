## 2. Payment Processing Concepts Learned

- A delivery chapter is a temporary sequencing coordinate. A payment capability
  such as authorization void, refund ledger, or review approval is a durable
  domain concept and therefore belongs in executable names.
- Flyway class identity is persisted deployment history. Renaming an unapplied
  migration is trivial; renaming one applied to a local database requires an
  explicit repair and validation against the exact database.

## 3. Fraud Detection Concepts Learned

- Fraud evidence should remain discoverable by capability: feature lineage,
  decision aggregation, review resolution, velocity, fraud lists, and merchant
  policy. Chapter prefixes obscure which invariant a test actually proves.
- Naming quality supports model and rule governance because reviewers can trace
  evidence by stable lineage boundary rather than by roadmap memory.
- Rotation is a decision-quality boundary: abandoning an old Redis window can
  turn a correct REVIEW into ALLOW even when every stored value remains private.

## 4. Security Concepts Learned

- Demo credentials and tenant fixtures kept their loopback, sanitization, and
  isolation boundaries while temporary chapter namespaces were removed.
- Historical applied migration bytes remain immutable. The naming checker uses
  exact allowlists for V6/V8 and their two constraint assertions rather than a
  broad bypass that could hide new violations.
- Idempotent replay is part of authorization. A stored manager response cannot
  be returned merely because merchant and key match; the authenticated operator
  and credential lifecycle must own that replay row.

## 5. Architecture / Design Notes

- Chapter language remains valid only where chapter governance is the real
  responsibility: plans, learning notes, matrices, dossiers, and the
  chapter-closure validator.
- Removing chapter text from governed Lua comments changed the exact bytes, so
  both production SHA-1 contracts and their review evidence were updated
  together. Comments are part of a byte-level protocol artifact.
- Redis compensation is a distributed ownership protocol: only the transaction
  that inserted a member receives an owner token, and cleanup is an atomic
  compare-delete. A retry that merely observes an existing member owns nothing.
- Nested pseudonyms must rotate layer by layer. The old outer fraud-list HMAC is
  useful only with the matching old inner RiskContext HMAC alias.

## 7. Bugs, Surprises, Or Tradeoffs

- The first non-clean Java run retained old class files, proving why source-file
  renames require `mvn clean test`, not only `mvn test`.
- A longer capability-based PostgreSQL test schema made a legacy hash fixture
  exceed `VARCHAR(64)`; the capability name was shortened without returning to a
  chapter identifier.
- The first full run exposed the changed Lua digests and one stale expected
  append-only message. Both were corrected and re-proven at the real boundary.
- The remediation hostile pass found that token fencing alone was insufficient
  if a retry overwrote ownership of an existing member. Moving owner creation
  inside the successful insertion branch closed that second-order race.
