## 2. Payment Processing Concepts Learned

- A webhook event is merchant-visible payment truth. It must commit or roll
  back with the payment/refund mutation that caused it.

## 3. Fraud Detection Concepts Learned

- Historical integration lineage should not be inferred from coincident
  resource IDs and timestamps; false lineage would later contaminate replay,
  analytics, and training-data interpretation.

## 4. Security Concepts Learned

- Fail-closed transaction propagation prevents a future caller from creating
  orphan merchant-visible webhook truth.
- Bounded `error.code` metrics preserve operational diagnosis without exposing
  tenant, endpoint, URL, resource, payload, or secret cardinality.
- Finalization returns the committed state classification directly, preventing
  a second database read from failing after durable state has already changed.
- A merchant-controlled callback cannot convert non-HTTP bytes into successful
  delivery truth merely by including a numeric `204`.
- Aggregate delivery status is not a substitute for append-only attempt
  evidence during migration.
- A cryptographic timestamp is only fresh if it is minted after unbounded lock
  waits, not merely during the same worker method.
- Operational counters must describe committed affected rows rather than an
  earlier observation that can race state transition.

## 5. Architecture / Design Notes

- Spring cannot express transaction context in Java's type system.
  `Propagation.MANDATORY`, an intention-revealing method name, and a negative
  contract test together make the runtime precondition explicit and durable.
- V8 did not persist an event identity. One synthetic event per legacy delivery
  is a conservative compatibility representation, not unresolved technical
  debt; there is no truthful future reconstruction step to register.
- Outcome and status answer what happened to the state machine; error code
  answers why. Payments operations need all three dimensions.
- A custom protocol parser must prove every accepted grammar component.
  Numeric range and framing tests do not prove HTTP-version validity.
- Numeric limits belong at the consuming boundary and need exact N/N+1 proof,
  including status lines, CRLFs, and repeated informational sections.

## 7. Bugs, Surprises, Or Tradeoffs

- The review statement that there was one caller in
  `PaymentIntentConfirmService` was stale. Production has five call sites
  across the payment-intent and refund controllers, all currently executed
  inside `IdempotencyService` transaction templates.
- Structural readiness passed while two semantic promises were still false:
  metrics counted failures without distinguishing their cause, and the socket
  parser checked only an `HTTP/` prefix. These are recorded as `ER-0006` and
  `ER-0007`, not hidden by the later fix.
- A later hostile pass found five more contradictions even though all gates
  were green. The common cause was proof that followed the implementation:
  migration tests asserted zero attempts without reconciling attempt lineage,
  protocol tests used obviously oversized inputs rather than exact limits, and
  metrics tests never forced state change between count and update.
