# Daily Deep Dive: 2026-06-02

## 1. System Goal

We turned the Day 4 migration from basic table creation into a stronger
payments-security foundation. The system now has explicit schema history,
tenant-safe constraints, hashed API-key storage, safe card metadata, capture
method storage, and webhook retry/signing metadata.

This matters because payment and fraud systems are long-lived audit systems.
Their tables are not just storage; they become contracts for tenant isolation,
idempotency, fraud lineage, operational recovery, and future ML datasets.

## 2. Plain-English Design Brief

The mental model:

- Flyway owns the database schema.
- Hibernate validates that Java entities match that schema.
- `merchant_id` is the tenant boundary for merchant-owned rows.
- Secrets are revealed once, then stored only as prefixes and hashes.
- Card data is reduced immediately to safe simulator metadata.
- Fraud/ML fields are deferred until `PaymentAttempt` exists, because decisions
  need real lineage.

What would go wrong without this design:

- Plaintext API keys in the database would turn DB access into merchant
  credential access.
- Webhook rows without retry/signing fields would need immediate churn once
  delivery behavior grows.
- Payment methods without BIN/funding/country would block early fraud feature
  extraction.
- Fraud decisions with orphan `payment_attempt_id` values would create fake
  lineage before the real attempt table exists.

## 3. Code Map

- `apps/payments-api/src/main/resources/db/migration/V1__create_payments_api_schema.sql`
  defines the authoritative schema.
- `Merchant` stores `apiKeyPrefix` and `apiKeyHash`, never the raw API key.
- `SecretHasher` centralizes SHA-256 hashing and non-secret prefix derivation.
- `MerchantContextArgumentResolver` hashes `X-Api-Key` before merchant lookup.
- `PaymentMethod` stores token, fingerprint, BIN, last4, funding, and country.
- `PaymentIntent` stores `captureMethod`.
- `WebhookEndpoint` stores signing-secret prefix/hash.
- `WebhookDelivery` stores attempt and retry metadata.
- `DatabaseMigrationTests` proves schema history, indexes, and key invariants.
- `PostgreSqlMigrationTests` provides a Docker-dependent real PostgreSQL check.
- `MerchantTenantIsolationTests` exercises API-level tenant and response
  behavior.

## 4. Request/Data Flow

Merchant creation:

1. `POST /admin/merchants` generates a raw test API key.
2. `Merchant` stores only `apiKeyPrefix` and `apiKeyHash`.
3. The raw key is returned once in the response.
4. Future merchant-facing requests send that raw key in `X-Api-Key`.
5. `MerchantContextArgumentResolver` hashes the header and looks up the
   merchant by hash.

Payment method creation:

1. Merchant sends `POST /payment_methods` with a test card number.
2. Controller validates the customer belongs to the same merchant.
3. Card number is normalized and immediately reduced to token, fingerprint,
   BIN, last4, funding, and country.
4. Full card number is not persisted or returned.

Webhook endpoint and delivery:

1. Merchant creates a webhook endpoint.
2. Endpoint receives a signing secret, revealed once.
3. Database stores signing-secret prefix/hash.
4. Payment events create delivery rows with `attemptCount = 0` and nullable
   retry timestamps/error fields.

## 5. Database Invariants

Important invariants:

- `merchants.api_key_hash` is unique.
- There is no plaintext `api_key` column.
- `idempotency_records` are unique by `(merchant_id, idempotency_key)`.
- `payment_methods` and `payment_intents` reference customers through
  `(merchant_id, customer_id)`, preventing cross-merchant child attachment.
- `webhook_deliveries` reference endpoints through
  `(merchant_id, webhook_endpoint_id)`.
- Merchant-scoped hot lookup indexes exist for list and retry paths.

Why this matters:

- Application code can regress. Database constraints are the durable backstop.
- Fraud and analytics later depend on tenant-clean historical data.
- Idempotency must survive retries, crashes, and concurrent requests.

## 6. Security And Privacy Invariants

Secrets:

- API keys: raw value returned once, prefix/hash stored.
- Webhook signing secrets: raw value returned once, prefix/hash stored.

Card data:

- Full PAN: accepted transiently as test input only.
- CVV: not accepted or stored in this slice.
- Stored card metadata: token, fingerprint, BIN, last4, funding, country.

The security principle is data minimization. Store what the platform needs for
simulation, fraud features, and audit. Do not store values that create avoidable
credential or cardholder-data risk.

## 7. Fraud/ML Relevance

This slice enables future fraud work by adding stable, safe features:

- BIN can support card-testing, issuer, and geography rules.
- Funding type can support risk segmentation.
- Card country can support country-mismatch features.
- Capture method affects payment lifecycle and eventual label interpretation.

Deferred intentionally:

- `fraud_decisions.payment_attempt_id`
- `risk_score`
- `risk_level`
- `reason_codes`
- model/rule version fields

Those should arrive after `PaymentAttempt` and fraud decision behavior exist.
Otherwise the schema would look mature while the lineage remains fake.

## 9. Staff Engineer Review Notes

Tradeoff:

- We changed the initial migration because the schema is still fresh. In a
  production system with deployed data, this would require an expand/contract
  migration.

Risk reduced:

- Raw merchant credentials and webhook secrets are no longer persisted.
- Cross-tenant attachment is protected by database constraints.
- Future fraud features can use safe card metadata without needing raw PAN.

Kept reversible:

- Fraud/ML richness remains deferred until lineage exists.
- Card funding/country derivation is simple and can be replaced by a simulator
  card metadata catalog later.

Dangerous overbuild:

- Adding risk scores or model fields before there is a real decision engine,
  feature snapshot, model version, and payment attempt.

## 13. Interview Narrative

Practice saying this out loud:

- The tradeoff I made was to pull forward stable security and payment
  primitives into the first migration, while deferring fraud/ML fields until
  they have real payment-attempt lineage.
- The invariant I enforced was that merchant-owned child rows cannot attach to
  another merchant's objects, even if application code regresses.
- The production risk I reduced was raw credential exposure from plaintext API
  keys and webhook signing secrets.
- I deferred risk scores and reason codes because fraud decisions need
  `PaymentAttempt`, feature snapshots, and decision behavior before those fields
  become meaningful.
- The tests prove Flyway migration, schema invariants, tenant-scoped foreign
  keys, safe card metadata, default capture method, and webhook operational
  metadata.
