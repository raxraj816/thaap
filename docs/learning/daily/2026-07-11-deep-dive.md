# Daily Deep Dive: 2026-07-11

This note is for end-to-end understanding of a Staff-level implementation slice.
It should make the code explainable, not merely documented.

## 1. System Goal

- Re-close Chapter 21 only after merchant replay and webhook secret/lease
  protocols survive their full time-and-concurrency transition grammars.
- Payments platforms fail at boundaries between individually valid states;
  this slice prevents duplicate credentials, expired signatures, lost webhook
  events, late runtime key failures, and stolen live reservations.

## 2. Plain-English Design Brief

- A replay window is one durable epoch: calls inside it return the same result;
  calls after it create a new epoch and therefore a new credential.
- A webhook generation is authorized only if its validity is checked at the
  same locked instant used to mint its signature timestamp.
- A stale claim should retry against current durable state; integrity failures
  remain terminal.
- No defect affecting the frozen promise is deferred.

## 3. Code Map

- `MerchantCreationService`: reservation ownership, expired-epoch replacement,
  deterministic credential derivation, and completion.
- `WebhookEndpointService`: endpoint creation and rotation transaction order.
- `WebhookEndpointSecretService`: tenant-scoped endpoint lock, exact-time
  generation validation, decryption, lazy KEK re-encryption, and signing.
- `WebhookDeliveryExecutor`: target preparation, recovery classification,
  transport, and attempt finalization.
- `WebhookExecutionConfiguration`: persisted KEK readiness independent of
  worker mode.
- Contract tests prove API/storage behavior; PostgreSQL tests force the two
  lock orderings that an H2 or mock test cannot certify.

## 4. Request/Data Flow

Merchant creation: the admin request is canonicalized and HMACed; an existing
live alias replays its record, while an expired record and aliases are deleted
and flushed. A new UUID record becomes the lifecycle epoch. The API key is
derived from original key version + record UUID + request identities, the
merchant and completed reservation commit together, and only the response
reveals the raw key.

Webhook delivery: the claim already names a secret generation. After target
preparation, the executor supplies a time lower bound. The signing transaction
locks the tenant endpoint, captures exact use time, validates current or
strictly-unexpired previous generation, decrypts, signs under the lock, and
returns the header. A concurrent rotation waits. A stale generation normally
records retryable known-no-send evidence; at the retry ceiling, current state
is rebound before the first socket opportunity.

Endpoint creation: the operation transaction locks and validates the durable
reservation before secret generation or persistence. Even after wall-clock
lease expiry, a contender cannot reclaim until the owning transaction releases
the row, at which point it observes completed truth and replays it.

## 5. Database Invariants

- One live merchant-creation alias maps to one creation record; a record UUID
  distinguishes successive expired epochs without storing the external key.
- One tenant/url endpoint row and one tenant/idempotency alias binding prevent
  duplicate delivery streams.
- Endpoint current/previous generations and expiry are read under the same row
  lock used by rotation and signing.
- Reservation owner token and status are validated before mutation. Without
  that ordering, a lease timeout could admit two secret generations or audit
  histories even if one transaction later rolled back.

## 6. Security And Privacy Invariants

- Merchant API keys and webhook signing secrets are revealed raw only in
  bounded responses. Merchant credentials persist as prefix/hash; webhook
  material persists as prefix/hash plus tenant-bound AES-GCM ciphertext.
- External idempotency keys and canonical requests persist as HMAC outputs with
  explicit key versions. The record UUID is non-secret domain separation.
- KEK startup inventory fails closed across current, unexpired previous, and
  live replay ciphertext even in observe/admin-only mode.

## 7. Fraud/ML Relevance

- Reliable merchant and webhook identity keeps duplicate retries from creating
  duplicate fraud events or misleading analyst timelines.
- Stable correlation keys remain unchanged, so velocity, graph, and future ML
  features do not split during replay-key rotation.
- No scoring or label behavior was added; Chapter 21 repairs infrastructure
  truth and does not invent Phase 3 fraud promises.

## 9. Staff Engineer Review Notes

- Signing under a database row lock intentionally lengthens a short transaction
  by local HMAC work. That small bounded cost buys an atomic authorization/use
  boundary without holding the lock over network I/O.
- Stale generation is retryable, but ciphertext integrity/key-configuration
  defects are not silently reclassified; this preserves diagnosability.
- No migration was required: existing UUIDs, locks, and attempt state already
  represented the needed truth. The correction is reversible at code level.
- Building a distributed signing service or queue would add protocol surface
  without improving this bounded local product wedge.

## 14. Phase 3 Planning Addendum

The post-closure dependency-ready step was planning, not production code. The
Phase 3 roadmap previously named entities and completion outcomes but did not
define enough product truth to safely modify confirm orchestration.

The detailed plan now freezes five boundaries before implementation:

1. Decision mechanics: evaluate every rule, persist matches and non-matches,
   and aggregate with `BLOCK > REVIEW > REQUEST_3DS > ALLOW`.
2. Data mechanics: materialize typed FeatureValues and an immutable snapshot
   from decision-time durable sources; never reconstruct history from current
   entity state.
3. Payment mechanics: only `ALLOW` reaches the processor. Fraud step-up cannot
   create processor 3DS fiction, and review intake cannot create money truth.
4. Product mechanics: Phase 3 creates review intake and permits only atomic
   merchant cancellation; Phase 4 owns analyst resolution and payment actions.
5. Proof mechanics: Chapters 22–25 each require their own pre-implementation
   matrix, migration proof, forced PostgreSQL orderings, public demo,
   traceability pass, and later hostile pass.

The initial `rules_v1` policy is intentionally narrow and application-owned.
It uses amount and attempt-number boundaries to exercise all four actions
without prematurely introducing an arbitrary rule DSL, Redis velocity, mutable
merchant policy, or ML. Its score is explicitly a severity projection rather
than a calibrated probability.

Chapter 22's matrix and dossier now exist before code. Founder review confirmed
the promise freeze and moved the matrix to `FROZEN`; that was a product review
checkpoint, not a formatting step. No planned test name or schema paragraph is
completion evidence until its real production boundary is implemented and
exercised.

The review also corrected two product semantics. A fraud block now produces an
explicit terminal PaymentIntent `BLOCKED`, preserving the distinction from
technical or processor `FAILED`. A review-pending merchant can use the existing
cancel API; the transaction must lock PaymentIntent before ManualReviewCase and
atomically cancel the intent, attempt, and case without rewriting the original
fraud decision.

## 15. Chapter 22 Typed Lineage Implementation

The key distinction is between a snapshot and feature lineage. A snapshot is a
convenient decision-time document; lineage is the normalized evidence that says
which immutable definition gave a value its meaning, which exact typed column
held it, when it was observed and computed, which attempt and merchant owned it,
and whether it was knowable when the decision began. Chapter 22 now writes both
representations atomically so API explanation and offline training cannot drift.

The materializer starts after the PaymentIntent row is locked and the owned
PaymentMethod is resolved. `decision_started_at` is captured before feature
work. Each source carries its durable observation timestamp: PaymentIntent
creation for amount/currency/capture method, PaymentMethod creation for safe
card country/funding, and PaymentAttempt creation for attempt number/origin.
Any observation after decision start is rejected as future leakage rather than
misclassified as stale data.

The storage design uses one nullable column per supported type plus a database
constraint requiring exactly the column named by `value_type`. This prevents a
LONG represented as a JSON string—or a row carrying both LONG and STRING—from
becoming ambiguous training truth. Composite foreign keys bind the definition
ID/code/version triple and merchant/attempt pair. Catalogue mutation is rejected
by database triggers on both supported engines, not merely hidden behind a Java
repository without setters.

The privacy boundary is an allowlist, not a blacklist. The old broad map
contained BIN, last4, and resource IDs. The new snapshot contains exactly seven
lexically ordered codes and excludes PAN, token, fingerprint, BIN, last4,
customer data, descriptions, metadata, credentials, idempotency material, and
resource identifiers. Operational metrics use bounded stage/cause/freshness/
origin values; feature values and tenant/resource identifiers never become
dimensions.

The current proof demonstrates the normal public API path and rollback at both
new persistence families. Completion still requires dedicated before/at/after
time partitions, every typed-column/database-invalid partition, catalogue
startup corruption partitions, Chapter 21 upgrade preservation, and forced
PostgreSQL waits inside feature persistence. A green aggregate suite cannot
substitute for those boundary-specific claims.

The next proof pass closed those named gaps and found an implementation-order
defect before closure: JPA `save` registers an entity but does not guarantee its
SQL has executed. Without an explicit flush, the processor adapter could be
invoked before typed lineage reached PostgreSQL, even though a later commit
would still appear atomic. Confirm now saves each required value and flushes
the persistence context before applying the allow branch. PostgreSQL proof
holds an `ACCESS EXCLUSIVE` table lock to stop that exact insert, observes the
backend wait in `pg_stat_activity`, proves zero Authorization rows, then starts
either a distinct-key or same-key contender. The distinct key waits on the
PaymentIntent lock and loses coherently; the same key waits on the idempotency
record and returns the exact completed response. This is lock-order evidence,
not simultaneous thread start.

The hostile representation pass also found that default Jackson behavior
reloads small JSON integers as `Integer` even when FeatureValue declares LONG.
The snapshot converter now uses LONG for integral numbers and BigDecimal for
floating numbers, with round-trip proof. DECIMAL values are rejected before
persistence if scale or integer digits exceed exact `NUMERIC(19,6)` capacity,
preventing database rounding from changing decision evidence.

## 16. Chapter 22 Closure

The final hostile pass treated deletion as part of immutability, not merely
field mutation. V19 therefore rejects both `UPDATE` and `DELETE` for
FeatureValues, FeatureSnapshots, and FraudDecisions, while definitions reject
all insert/update/delete drift after the fixed seed migration. That database
truth exposed a test-lifecycle dependency: ordinary row-by-row cleanup could no
longer erase immutable fixtures and separate PostgreSQL truncates conflicted
with their foreign keys. Cleanup now performs one multi-table truncate for the
immutable lineage family, with H2 referential integrity disabled only around
the same bounded test operation.

Closure evidence is layered. The 298-test backend and 74-test Python suites are
regression context. Exact claims rest on boundary tests: microsecond
before/at/after point-in-time joins, typed-column ambiguity rejection, catalogue
startup corruption, V17-to-V19 byte preservation, every feature-write rollback
position, same/distinct-key PostgreSQL waits at the actual SQL flush, and the
loopback public-API demo. The matrix and dossier now pass with zero non-resolved
debt and no escaped finding. The architecture remains honest: Chapter 22 gives
future rules reliable evidence, but `rules_stub_v1` is still allow-only until
Chapter 23 adds and proves payment-coherent fraud actions.
