## 2. Payment Lifecycle Progress

- `POST /payment_intents` now creates the merchant-facing payment container in
  `REQUIRES_CONFIRMATION`.
- Chapter 7 hardening now makes PaymentIntent a stricter lifecycle container:
  it exposes reconciliation timestamps, stores optional description and
  constrained metadata, rejects unsupported V1 currencies, and enforces an
  amount ceiling.
- Capture and refund now reject impossible pre-authorization/pre-capture states
  instead of mutating the PaymentIntent.
- Create remains correctly before money movement: no authorization, capture,
  ledger entry, fraud decision, or PaymentAttempt is created yet.
- The next lifecycle boundary is `POST /payment_intents/{id}/confirm`, but it
  should start only after the idempotency service can tolerate retry storms.
- Chapter 8 now gives future confirm/capture/refund paths a shared retry-safe
  mutation boundary.
- Chapter 9 adds `PaymentAttempt` as the durable confirm lineage unit.
- `POST /payment_intents/{id}/confirm` now creates attempts through
  tenant-scoped PaymentIntent and PaymentMethod lookups.
- `GET /payment_attempts/{id}` now exposes attempts through merchant scope.

## 3. Tenant And Security Risks Reduced

- Tenant isolation is enforced through merchant context, tenant-scoped queries,
  and composite database ownership constraints.
- PaymentIntent create rejects another merchant's customer.
- API keys and webhook signing secrets are stored as prefixes and hashes.
- Webhook signing secrets now use explicit `SecureRandom` byte generation
  instead of UUID-derived material.
- Raw card input is reduced to simulator-safe metadata and internal keyed
  fingerprints.
- Idempotency keys are scoped by `(merchant_id, idempotency_key)`, preventing
  cross-merchant replay or conflict.
- Idempotency records now bind key reuse to both operation and request hash, so
  same-body mutations cannot replay across different endpoints.
- Confirm rejects cross-merchant PaymentIntents, cross-merchant PaymentMethods,
  and PaymentMethods that belong to a different customer than the PaymentIntent.
- Metadata is constrained and documented as non-sensitive so it does not become
  an accidental PAN/CVV/secret/PII storage path.

## 4. Reliability And Operations Risks Reduced

- Idempotency is now a state machine rather than a response cache.
- The service reserves an `IN_PROGRESS` row before running a mutation.
- Concurrent duplicates see the committed reservation and fail with a
  deterministic conflict before duplicate side effects run.
- Completed records replay the original response.
- Failed mutations release the reservation so retryable failures are not cached
  as successful work.
- The migration stores operation, status, response status/body, timestamps, and
  `expires_at`, giving operations a future cleanup and diagnosis hook.

## 5. Risks That Remain

- PaymentAttempt exists, but it only records confirm lineage.
- PaymentIntent statuses now include the planned vocabulary, but processor and
  ledger chapters still need to own transitions into authorization,
  capture-ready, captured, disputed, and failed terminal states.
- Processor authorization is not implemented, so there is no processor result
  persistence, auth code, decline code, or network status.
- FraudDecision and FeatureSnapshot are not created on confirm yet, so ML/fraud
  lineage is still intentionally absent.
- Feature freshness is not yet measured, so future FraudDecision work must
  capture feature age, stale feature names, and missing feature names instead
  of storing only score/action outputs.
- Ledger entries are still deferred until authorization/capture/refund behavior
  exists.
- Expired `IN_PROGRESS` idempotency records are stored but do not yet have a
  cleanup or takeover policy after process crash.
- Redis acceleration remains deferred; PostgreSQL is still the source of truth.

## 7. Explicit Deferrals

- Deferral: confirm orchestration.
  - Reason: Chapter 9 creates the attempt, but it does not yet run fraud,
    processor simulation, or final status mapping.
  - Target: Chapter 10.
  - Evidence to unblock: PaymentAttempt entity/repository/tests now exist.
- Deferral: processor simulator.
  - Reason: processor outcomes need a durable PaymentAttempt target.
  - Target: Chapter 11.
  - Evidence to unblock: confirm creates attempts with stable status fields.
- Deferral: transition into `REQUIRES_CAPTURE`.
  - Reason: capture readiness must come from an authorization/processor result,
    not a shortcut in PaymentIntent create tests.
  - Target: Chapter 10/11 confirm orchestration and processor simulator.
  - Evidence to unblock: durable processor authorization result linked to
    PaymentAttempt.
- Deferral: partial refund accounting.
  - Reason: V1 now allows only full refunds where the refund amount equals the
    captured PaymentIntent amount; partial refunds and refund ledger entries
    need durable capture/refund records.
  - Target: refund/ledger chapters after capture is implemented.
  - Evidence to unblock: durable capture records and ledger invariants exist.
- Deferral: fraud decision stub and feature snapshots.
  - Reason: fraud lineage belongs to PaymentAttempt, not PaymentIntent create.
  - Target: Chapter 12.
  - Evidence to unblock: attempts and confirm orchestration exist; first
    FeatureSnapshot implementation must include freshness metadata.
- Deferral: ledger.
  - Reason: ledger entries need settled money-movement semantics and double-entry
    invariants.
  - Target: Phase 2 capture/refund/ledger chapters.
  - Evidence to unblock: authorization and capture/refund flows are defined.
- Deferral: idempotency expired-key cleanup.
  - Reason: Chapter 8 stores `expires_at`, but cleanup policy needs operational
    semantics for abandoned in-progress rows after crash.
  - Target: later reliability slice.
  - Evidence to unblock: background worker or admin recovery policy exists.
## 8. Design Review Narrative

Practice saying this out loud:

- We reviewed the platform before adding confirm side effects and found the main
  prerequisite was processor-safe idempotency.
- The invariant we strengthened is one merchant mutation per idempotency key,
  operation, and request hash, with deterministic replay or conflict. We also
  added the invariant that confirm creates a tenant-scoped PaymentAttempt before
  fraud or processor outcomes can attach.
- The production risk reduced is duplicate durable side effects during network
  retries or concurrent duplicate requests.
- The tradeoff is that abandoned in-progress keys now need a future cleanup
  policy, but failed in-process mutations do not poison future retries.
- We deliberately kept processor, fraud, final status mapping, and ledger work
  deferred until the attempt lineage boundary exists.
