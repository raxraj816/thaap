## 1. System Goal

- We separated roadmap identity from executable product identity across the
  repository and added an automated enforcement boundary.
- Payments and fraud systems are reviewed by durable invariants. A test named
  for feature lineage or review approval remains meaningful after the delivery
  plan changes; a test named only for a chapter does not.
- The change reduces review ambiguity, broken evidence references, unsafe
  migration renames, and future copy-forward naming debt.

## 2. Plain-English Design Brief

- Chapters answer “when did we build it?” Capabilities answer “what truth does
  this code own?” Only the second answer belongs in durable executable names.
- Without enforcement, temporary roadmap coordinates spread into class names,
  fixtures, database objects, logs, and demos, making later ownership and audit
  searches depend on historical plan knowledge.
- We renamed every inappropriate artifact and executable identifier, reconciled
  all references, repaired the local V27 history, and added a tested gate.
- Nothing was deferred. Two applied SQL migrations retain exact historical
  chapter tokens because rewriting their bytes would falsify Flyway history;
  those exact exceptions are allowlisted and documented.

## 4. Request/Data Flow

4. Only exact governance tools, immutable V6/V8 bytes, and two exact historical
   constraint assertions bypass content rejection.
5. Any violation fails commit readiness before the change can be declared done.

## 14. Post-Closure Payment-Risk Hardening

The later hostile review exposed a useful Staff-level lesson: each subsystem
was locally plausible, but six promises failed when their boundaries were
composed.

1. Velocity HMAC rotation now reads and writes current plus retained-version
   Redis identities for the overlap window. It uses the maximum compatible
   count, not a sum, because post-rotation attempts exist in both windows.
2. A velocity member receives a random owner token only when `ZADD NX` actually
   inserts it. Rollback executes an exact-byte compare-delete script; a retry
   that saw an existing member cannot remove it, and an old callback cannot
   remove a newer insertion.
3. RiskContext persists bounded `version=digest` aliases for IP, device, and
   session before raw inputs disappear. Fraud-list evaluation selects the inner
   alias matching the entry's outer HMAC version, closing the nested rotation
   cross-product.
4. V49 scopes risk-operator idempotency by merchant, principal type, operator,
   credential prefix, and key. Authentication still happens at request
   resolution, and a different lower-role actor cannot replay the first actor's
   response before service authorization.
5. Post-authorization response assembly consults a review only for a REVIEW
   signal and validates the exact source signal ID. A prior NO_ACTION response
   therefore stays immutable after a later signal opens a review.
6. Exact evidence is generated from the final invocation: 629 clean Java tests,
   114 Python tests, 49 production migrations, and 14 migration contracts.

The enforcement-boundary rule is the common thread. A keyring inventory does
not prove decision continuity, stable identity does not prove safe cleanup,
authentication does not prove authorized replay, and a green suite does not
prove that documentation names the suite that actually ran.

## 15. Phase 4.5 Planning Mental Model

Phase 4 built truthful payment-risk facts. Phase 4.5 must make those facts
operable without weakening them. That creates four distinct boundaries:

1. Product monitoring is a denominator-defined query over durable facts, not a
   Micrometer counter and not a probability.
2. Historical simulation re-evaluates immutable decision-time features; it may
   inspect outcomes available by its cutoff but cannot feed future evidence into
   the candidate decision.
3. Analyst workspace data has its own privacy lifecycle. Structured filters are
   safe query definitions; free-form notes require encryption, access audit,
   retention, and redaction rather than being treated like ordinary metadata.
4. Operational replay appends evidence. A webhook redelivery reuses the signed
   event identity, while a policy rollback activates an earlier approved version;
   neither operation rewrites the original business fact.

The proposed sequence starts with taxonomy and merchant-risk monitoring because
every later UI, simulation report, filter, and policy gate needs shared time,
coverage, origin, and label semantics. It then builds the analyst workspace,
simulation, governed controls, dispute operations, developer scenarios, and
webhook operations before an integrated closure chapter.

## 17. Chapter 36 Deep Dive — Denominator Truth And Evidence Time

The merchant-facing number is not derived from operational counters. It is a
repeatable PostgreSQL query over immutable payment/fraud facts. Authorization
rates share the same terminal outcome denominator; chargeback rate anchors the
cohort on capture ledger time; confirmed fraud requires a decided attempt and a
current label visible by `asOf`; enumeration requires actual processor or
persisted control coverage; backlog is a count with no fake denominator; and
volume compares one complete bucket with the median of six prior complete
buckets.

Three clocks matter. `created_at` selects the business cohort, occurrence and
receipt describe external evidence, and `available_at` says when THAAP could
have known that evidence. The late-chargeback contract proves a captured
payment is denominator-only before availability, becomes chargeback/fraud
numerator truth exactly at availability, and enters the dispute-window cohort
only when the half-open window contains that availability timestamp. This is
the same anti-leakage boundary a future offline ML dataset must use.

The concurrency claim is deliberately narrow: each report uses a short,
five-second, read-only `REPEATABLE_READ` transaction. A deterministic probe
pauses after the approval denominator; a second connection inserts and commits
a decline without blocking; the original report still returns the coherent old
snapshot. That proves isolation and non-interference rather than merely starting
two threads at once.

The product security boundary returns only resource type, resource UUID,
occurrence time, membership booleans, closed evidence code, and count. Cursors
are HMAC-authenticated over merchant, metric, window, `asOf`, origin, last time,
and last resource ID. Copying a cursor across any of those dimensions fails
closed. Snapshot payloads contain only the aggregate DTO, and metric tags remain
closed catalogues.

In a design review: Chapter 36 advances the challenger wedge through
explainability. A merchant can see exactly why `1/2` differs from `2/3`, trace
the two durable rows, freeze the result as review evidence, and receive a
deterministic recommendation—while THAAP still refuses to call that ratio a
probability or silently activate a risk tier.

## 18. Chapter 37 Design Freeze — Plaintext Is A Temporary Capability

A protected note is not merely a string stored in an encrypted column. It is a
temporary capability produced only when five boundaries agree: the credential
is live, the operator belongs to the merchant, the role is allowed, an analyst
still owns the case when the row is locked, and the note has not been redacted
or expired. Encryption protects database media; these authorization and
lifecycle checks protect product meaning.

AES-GCM authenticates ciphertext and associated data together. THAAP will bind
the exact merchant, review, note, author, and microsecond creation timestamp in
an unambiguous versioned encoding. That prevents copying valid ciphertext onto
another row or silently changing identity metadata. Key rotation is similarly
a data-lineage boundary: new notes use the current version, old live notes use
their exact retained version, and readiness fails when required material is
missing. Destroyed ciphertext is intentionally excluded from that inventory.

Saved searches have the same semantic concern in a different form. Canonical
JSON and a digest make one filter meaning stable across member and set order,
but execution must still revalidate the schema version. An unsupported version
must stop with `saved_search_upgrade_required`; guessing today's equivalent
would turn an analyst's old queue into a new, silently broadened investigation.

The difficult concurrency proof is terminal note lifecycle. Read, correction,
manager redaction, and retention expiry must share a row-lock order. Whichever
transition wins is visible as one coherent state; ciphertext nulling and the
redaction event commit atomically, and a rollback leaves a retryable live note.
The browser completes the boundary by keeping credentials and drafts only in
memory so server-side encryption is not undermined by persistent client storage.

## 19. Chapter 37 Deep Dive — Three Meanings That Must Not Drift

The analyst workspace has three independent kinds of meaning. Queue meaning is
the typed filter, sort, SLA state, time interval, and cursor position. Saved-
search meaning is the canonical versioned encoding and digest of that queue.
Note meaning is operational human context, explicitly excluded from labels,
features, rules, simulations, and payment decisions. Treating these as one
generic JSON/search/text feature would make the product easy to build and
impossible to defend.

Keyset pagination uses `(created_at,id)` because timestamps alone are not
unique. The cursor authenticates merchant, canonical filter, sort, last time,
and last ID. PostgreSQL proof forces multiple rows to the same timestamp and
walks pages without omission or duplication. That is stronger than a happy-
path two-page test because it exercises the tie-breaker at the real SQL
boundary.

Encryption is only one layer of note safety. The request first authenticates a
live operator and locks the case; an analyst must still own its assignment
version, while a manager remains tenant-bound. NFKC normalization happens
before payment/secret detection. AES-GCM then binds merchant, review, note,
author, and microsecond creation time in binary AAD. Reads repeat live
authorization under lock. Redaction and retention null ciphertext, nonce, and
key version in the same transaction that appends exactly one immutable terminal
event.

Idempotency exposed a subtle cross-capability lesson. Protected note responses
need encrypted replay so retry remains exact without storing plaintext. Reusing
the mature authentication replay cipher was sound, but initially changing the
authentication envelope identifier was not. The full suite caught the durable
compatibility break. The corrected model has two explicit formats sharing one
reviewed cipher and one readiness inventory: authentication retains its old
format; note content uses the new sensitive format.

In a Stripe/Mastercard-style review: the cockpit is credible because it is not
the security boundary. Every browser action re-enters a tenant-qualified,
role-aware, lock-time authorization path; browser state is memory-only; and the
live demo proves that investigation convenience cannot rewrite financial or
fraud lineage.

## 20. Chapter 38 Design Freeze — Two Clocks, Two Repositories, One Truth

A simulation asks a counterfactual question: “What action would this frozen
candidate have produced using only what the original decision knew?” The
candidate decision clock is therefore the attempt's historical decision time.
The outcome-analysis clock is the run's label cutoff: it may observe a later
fraud or legitimate label only when `available_at` says THAAP already knew it.
Mixing those clocks creates target leakage; treating unlabeled as legitimate
creates false model quality.

Spring Batch metadata and THAAP product rows solve different problems. Batch
metadata records job/step execution and restart context. Product rows bind the
tenant, candidate digest, cohort contract, per-attempt result, aggregate report,
and activation evidence. A restart can repeat work around a commit ambiguity,
so product writes must still be unique and idempotent; framework adoption does
not remove domain invariants.

The gate intentionally cannot activate a policy. It returns a typed disposition
over a locked candidate and successful report. Chapter 39 must consume that
evidence inside its own dual-controlled activation transaction. This separation
prevents a background analytics job from becoming an undeclared configuration
writer.
