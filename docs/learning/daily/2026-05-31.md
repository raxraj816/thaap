## 2. Payment Processing Concepts Learned

- The payment backend needs a durable transactional store before domain APIs are useful.
- Health checks should verify the infrastructure that will later guard payment lifecycle state.
- Merchant-facing payment operations must derive tenant scope from credentials instead of trusting request-body `merchantId`.
- Idempotency is part of tenant isolation: the same key can be valid for different merchants but must conflict within one merchant when the request hash changes.
- Webhooks let THAAP push payment/fraud state changes to merchant systems instead of forcing merchants to poll; see [Webhooks From First Principles](../concepts/WEBHOOKS.md).
- Related first-principles notes:

  - [Idempotency](../concepts/IDEMPOTENCY.md)
  - [Payment Method Tokenization](../concepts/PAYMENT_METHOD_TOKENIZATION.md)

## 3. Fraud Detection Concepts Learned

- Redis starts as infrastructure for future velocity counters and idempotency acceleration.
- Redis remains non-durable support infrastructure; PostgreSQL is still the source of truth.
- Fraud decisions, rules, reviews, features, replay rows, model predictions, graph records, and analytics projections must carry or derive `merchant_id` to prevent cross-tenant leakage.

## 4. Security Concepts Learned

- Local credentials are development-only defaults and are documented through `.env.example`.
- `Merchant` is the V1 tenant root.
- `X-Api-Key` is the initial V1 tenant-resolution mechanism for merchant-facing APIs.
- API keys are currently local scaffolding; before non-local deployment they must be stored as hashed secrets with a non-secret lookup prefix.
- Database RLS is deferred, but application-level tenant enforcement and cross-merchant tests are mandatory.
- See [Merchant Tenant Isolation From First Principles](../concepts/MERCHANT_TENANT_ISOLATION.md).

## 7. Bugs, Surprises, Or Tradeoffs

- Maven could not write to the user-level `~/.m2` under the workspace sandbox, so builds now use the workspace-local Maven repository.
- Initial dependency resolution required network access; later runs can use the local cache.
- Test health disables Redis so tests do not require Docker, while the local profile still checks Redis.
- Test dependencies avoid Mockito and assert Actuator health through health beans so sandboxed test runs do not require dynamic Java agent attachment or a bound TCP port.
- The initial scaffold used Java 21 and Spring Boot 3.5.11; it was corrected to the system baseline of Java 25 and current stable Spring Boot 4.0.6.
- Spring Boot 4 test auto-configuration is split differently than expected, so tenant isolation tests build `MockMvc` from `WebApplicationContext` directly.
- Jackson needed an explicit `ObjectMapper` bean for idempotency response serialization in this setup.
