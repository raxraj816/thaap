## 2. Payment Processing Concepts Learned

- A webhook retry system does not move money, but it carries merchant-facing
  payment truth. False delivery evidence can cause duplicate fulfillment,
  missing merchant updates, or impossible support investigations.
- “At least once” delivery must be honest about uncertainty. If a process
  crashes after dispatch begins, the platform cannot safely claim the request
  was never sent.
- The no-bytes boundary is not claim time. It is the durable dispatch-started
  marker written immediately before HTTP; merchant disable must still win until
  that marker exists.

## 3. Fraud Detection Concepts Learned

- Webhook event identity and attempt evidence become part of future
  fraud-review lineage. If later labels, analyst actions, or merchant decisions
  depend on these events, ambiguous delivery truth must be represented
  explicitly instead of collapsed into success/failure.

## 4. Security Concepts Learned

- Security review includes operational edge cases. DNS resolution, HTTP status
  parsing, partial socket writes, and endpoint disable are all trust boundaries
  because they decide what evidence THAAP persists and what a merchant can
  safely believe.
- Length is necessary but not sufficient for key configuration. THAAP cannot
  prove true entropy from a string, but it can cheaply reject a known-bad
  all-zero AES key before any merchant signing secret is encrypted.

## 5. Architecture / Design Notes

- The durable dispatch marker is the boundary between “known no HTTP” and
  “HTTP outcome unknown.” It is written under the delivery lock immediately
  before HTTP.
- `prepareForDispatch` now locks endpoint state before delivery state. If the
  endpoint is no longer `ACTIVE`, it closes the claimed attempt before transport
  and keeps `http_request_sent=false`.
- Resolver capacity and deadline failures are local infrastructure failures.
  They now create retryable no-send attempt evidence instead of permanent
  unsafe-target denial.
- Signed webhook payload construction is a security boundary, not formatting
  glue. The body is what merchants verify, so the code now relies on a JSON
  serializer and tests parse the exact hashed bytes as JSON.
- The payload size guard belongs at the representation boundary. Measuring
  UTF-8 bytes after serialization protects the exact body merchants verify,
  while avoiding false comfort from Java character counts.
- Secret rotation still needs an explicit old/new verification window for
  product-grade shared merchant operations. `TD-0003` owns that work; endpoint
  disable and DNS target pinning did not receive debt because their current
  invariants are proven in Chapter 19.
- Delivery row ownership remains the primary concurrency boundary for attempt
  mutation, but explicit attempt `FOR UPDATE` reads make the invariant easier
  to review and harder for future code to accidentally bypass.
- Review comments about virtual-thread deadline handling, bounded metric
  cardinality, response-body omission, and missing broad `payment_intent.updated`
  events did not require Chapter 19 code changes. The real future product work
  is governed by `TD-0004` and `TD-0005`.
- Expired `DELIVERING` rows are selected for recovery regardless of endpoint
  active status. Endpoint active status gates new queued work, not closure of
  already in-flight evidence.
- The corrected review process is now:
  product promise -> failure sequence -> production boundary -> adversarial
  proof -> matrix PASS -> escaped-review assessment -> closure dossier ->
  readiness gate.
- Structural scripts do not certify semantics. They prevent missing provenance,
  unresolved blocking severity, stale source status, and absent closure
  evidence from being mistaken for a Staff review.

## 7. Bugs, Surprises, Or Tradeoffs

- The uncomfortable root cause was process shape: earlier fixes were too
  reactive and too close to the code already written. The pass did not begin
  from a frozen list of failure sequences, so each correction still left room
  for adjacent edge cases.
- Stale evidence is itself a bug. Docs carrying old invariant or test counts
  after scope changed would have been a false completion signal.
- One bounded Chapter 19 debt was accepted after the final review pass:
  `TD-0003` tracks old/new signing-secret rotation windows. It is not a
  delivery-truth defect in the current local/test V1 wedge, but it must be
  resolved before shared non-local merchant webhook operations.
