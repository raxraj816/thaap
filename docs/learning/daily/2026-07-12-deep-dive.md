# Daily Deep Dive: 2026-07-12

This note is for end-to-end understanding of a Staff-level implementation slice.
It should make the code explainable, not merely documented.

## 1. System Goal

- Repair Chapter 22 so a fraud decision can be defended from one governed
  feature artifact through engine evaluation, immutable snapshot, typed rows,
  and PostgreSQL constraints.
- This matters because a payment-risk platform cannot train, explain, or replay
  from evidence whose declared type differs from its definition or whose engine
  input differs from the stored snapshot.
- The repair protects Chapter 23 before real BLOCK and REQUEST_3DS actions make
  an evidence mismatch merchant-visible.

## 2. Plain-English Design Brief

- One governed feature set must cross three boundaries unchanged: evaluation,
  explanation, and offline lineage.
- Without that identity, an engine can use an unrecorded fact or the database
  can retain an immutable value under the wrong type definition.
- Repair the schema identity, engine interface, and real flush-failure proof.
- Nothing in the escaped frozen promises is deferred.

## 3. Code Map

- `FeatureMaterializer` projects owned payment objects into the exact safe V1
  catalogue.
- `DecisionFeatureContext` validates and freezes the only values visible to
  `ConfirmDecisionEngine`.
- `MaterializedFeatureSet` proves the context and typed FeatureValues agree.
- `PaymentIntentController` evaluates that context, persists decision/snapshot/
  values, flushes SQL, and only then calls `ProcessorAdapter`.
- V18 owns definition/type/tenant/origin constraints; V19 owns immutability.
- Database contract, processor-call, and PostgreSQL concurrency tests own the
  three repaired proof families.

## 4. Request/Data Flow

1. Confirm reserves and locks its merchant-scoped idempotency record and
   PaymentIntent.
2. Owned PaymentMethod and attempt state are validated.
3. `FeatureMaterializer` creates typed FeatureValues plus one exact
   `DecisionFeatureContext`.
4. The engine evaluates only that context.
5. Decision, snapshot, and values are persisted and flushed through V18
   constraints before processor authorization.
6. Processor, money, audit, webhook, and idempotency response truth commit in
   the surrounding transaction or all local truth rolls back.

## 5. Database Invariants

- One value exists per merchant/attempt/code/version.
- `(definition_id, feature_code, feature_version, value_type)` must match one
  immutable definition; the populated typed column must independently match
  `value_type`.
- Merchant and traffic origin match the owning PaymentAttempt.
- Observation precedes computation; application evaluation additionally
  requires observation at or before decision start.
- Losing the definition/type identity would permit semantically corrupt but
  immutable training rows.

## 6. Security And Privacy Invariants

- PaymentMethod still contains tokenized processor data, BIN, last4, and a
  fingerprint, but none enters `DecisionFeatureContext`.
- PAN, CVV, PII, credentials, IDs, metadata, descriptions, and idempotency
  material remain absent from engine input, feature persistence, API, audit,
  webhook, logs, and metric dimensions.
- This applies data minimization at the evaluation boundary, not merely at the
  response boundary.

## 7. Fraud/ML Relevance

- Chapter 23 can evaluate deterministic rules knowing every inspected input is
  versioned, typed, point-in-time, and stored exactly once.
- Offline training joins cannot reinterpret a STRING definition as LONG or
  learn from a hidden engine-only fact.
- No model, velocity store, or general policy DSL was added; those require
  their own lifecycle and failure contracts.

## 8. Tests As Proof

- `databaseBindsEveryDeclaredValueTypeToTheReferencedDefinitionType` crosses
  every seeded definition with all four declared types on PostgreSQL.
- `PaymentIntentConfirmProcessorAdapterCallTests` captures the actual engine
  argument and equates it with snapshot JSON and typed rows.
- `realFeatureFlushFailureRollsBackBeforeProcessorReleasesReservationAndAllowsOneRetry`
  proves the deferred SQL failure path, zero external call, reservation
  cleanup, and coherent retry.
- Mocked position tests remain useful for cheap exhaustive ordering coverage,
  but they are explicitly not the real SQL-boundary proof.

## 9. Staff Engineer Review Notes

- We chose a small immutable local feature context instead of a remote feature
  store or generic risk DSL.
- We reduced explanation drift, hidden-feature use, and immutable type
  corruption before non-ALLOW actions ship.
- The engine interface remains replaceable while its input contract is fixed.
- Adding broad features or policies before freshness, privacy, and action
  semantics are frozen would recreate multiple sources of truth.

## 13. Interview Narrative

Practice saying this out loud:

- The tradeoff I made was a narrow immutable local feature contract instead of
  premature feature-store infrastructure.
- The invariant I enforced was that engine input, snapshot, typed row, and
  definition type agree exactly.

  silently corrupted training row.
