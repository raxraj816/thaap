## 2. Payment Processing Concepts Learned

- A domain event is a committed fact, not a delayed payment command. Republishing
  `capture.created` may repeat delivery, but it must never call capture or post
  ledger entries again.
- The transactional outbox closes the database/Kafka dual-write gap by placing
  source mutation, immutable event, and pending publication in one PostgreSQL
  transaction. Kafka acknowledgement necessarily happens later.
- At-least-once delivery is the honest boundary. Stable event identity, exact
  bytes, and an inbox committed with projection effects make duplicate delivery
  converge without claiming end-to-end exactly once.
- Money in analytics is derived evidence. Authorization, capture, refund, and
  dispute totals remain subordinate to balanced ledger/source truth and cannot
  authorize new money movement.

## 3. Fraud Detection Concepts Learned

- A useful fraud projection must preserve decision-time action, score/level,
  reason, rule/control version, feature catalogue version, traffic origin,
  review state, and label availability. A current risk context cannot recreate
  an old decision honestly.
- Label truth is point-in-time: a label becomes eligible at `available_at`, and
  a later correction may change the latest cohort while never leaking into an
  earlier replay cutoff.
- `unlabeled` and `unknown` are first-class denominators. Treating either as
  zero creates deceptively good fraud-rate and approval-rate metrics.
- Shadow generations let THAAP compare a new handler over the same immutable
  source membership before analysts see it. Count equality alone is weak;
  stream positions, membership/content digests, money, and business invariants
  must agree.

## 4. Security Concepts Learned

- Kafka headers are routing hints, not authenticated truth. Envelope, full-
  record digest, tenant-qualified key, and immutable PostgreSQL source identity
  must agree before tenant projection state changes.
- An unparseable record cannot safely inherit a tenant from an untrusted
  header. Transport-level poison evidence therefore needs a tenant-free,
  payload-free identity based on consumer/topic/partition/offset/digest.
- Same event ID plus different complete bytes is an integrity incident, not an
  inbox duplicate. Exact source bytes are the only duplicate-safe partition.
- Operational evidence intentionally stores closed reason codes and digests,
  never event payloads, exception messages, credentials, PII, payment data, or
  high-cardinality metric labels.
- Platform recovery authority is separate from merchant authority: loopback
  `DATA_OPERATOR` actions are live-credential revalidated, idempotent, and
  audited, while tenant replay datasets require a merchant `RISK_MANAGER`.

## 5. Architecture / Design Notes

- PostgreSQL immutable events and bootstrap facts are the rebuild authority;
  Kafka is the delivery log and projections are disposable read models.
- The canonical envelope uses an exact field set, RFC 8785/JCS bytes, nested
  payload SHA-256, full-record SHA-256, I-JSON integer bounds, PostgreSQL
  microsecond timestamps, and a 64 KiB complete-record ceiling.
- One fixed V1 topic has six partitions and seven-day retention. Stream keys are
  tenant-qualified; changing the partition count in place could remap one stream
  and violate ordering, so topology drift fails readiness.
- Consumer lock order is deterministic across payment and merchant definitions,
  source event, inbox, projection rows, positions, and checkpoints. Recovery
  must follow the same order to avoid definition/quarantine deadlocks.
- Rebuild uses immutable per-stream cutoffs, Spring Batch chunks of 100, a
  60-second fenced lease, live catch-up, five reconciliation families, atomic
  pointer activation, and retained compatible rollback.
- Offline datasets use immutable event/bootstrap/query/output digests, keyset
  checkpoints, decision-time features, availability-bounded labels, and exact
  simulation-overlap evidence. Redis and current RiskContext are outside the
  source boundary.

## 7. Bugs, Surprises, Or Tradeoffs

- A disabled publisher originally returned health `UP`; that would let an
  environment accept new durable work while hiding that delivery was paused.
  Required delivery now fails readiness when disabled.
- The original PostgreSQL event-order test proved row-lock ordering but did not
  append events/outbox rows. It was strengthened before any matrix was marked
  verified.
- Hostile consumer review found three related poison gaps: missing headers could
  block a partition forever, altered bytes after an applied event could be
  mislabeled duplicate, and a hostile header could quarantine a victim tenant's
  source event. These were found before closure and reopened the whole transport
  identity family.
- Merchant aggregate label correction needs state owned by the merchant
  projection. Writing helper payment rows under a merchant generation creates
  cross-definition lineage even if ordinary readers ignore those rows; a
  separate capability-owned cohort table is the correct boundary.
- At-least-once ambiguity is accepted, but source mutation ambiguity is not.
  The tradeoff is duplicate transport plus deterministic deduplication rather
  than a false exactly-once promise.
