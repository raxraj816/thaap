## 2. What Changed Architecturally

- THAAP moved from architecture plan to runnable local platform foundation.
- `Merchant` became the V1 tenant root.
- Merchant-facing APIs now resolve tenant context from `X-Api-Key`.
- API failures now share one error contract and request correlation model.
- Database schema ownership moved toward Flyway migrations and Hibernate
  validation.
- Tenant isolation started moving from controller intent into storage
  constraints.
- The project gained an explicit Staff apprenticeship loop.

## 3. Risks That Increased

- Payment lifecycle: payment primitives are still early; `PaymentAttempt`,
  authorization, capture semantics, ledger, and refund invariants are not fully
  implemented yet.
- Security/tenant isolation: API key hashing is in place, but key rotation,
  audit logs, and rate limits remain future work.
- Fraud/ML lineage: fraud tables are still scaffolding until `PaymentAttempt`,
  `FraudDecision`, `FeatureSnapshot`, and rule execution behavior land.
- Reliability/operations: idempotency has replay behavior, but atomic
  reservation and concurrency hardening are still needed before processor-like
  side effects.
- API/schema compatibility: the initial migration is still early enough to
  change, but future schema changes will need expand/contract discipline.

## 4. Risks That Decreased

- Architecture drift decreased because the master plan is authoritative.
- Cross-tenant leakage risk decreased through merchant context, tenant-scoped
  queries, tests, and composite foreign-key direction.
- Sensitive credential risk decreased because API keys and webhook secrets are
  stored as prefixes and hashes.
- Debuggability improved through request IDs and standard error responses.
- PCI-style scope risk decreased because card data is reduced to simulator-safe
  metadata.

## 5. Complexity Review

- More complex: the project now has docs, ADRs, architecture pack, learning
  notes, concept notes, daily/deep-dive artifacts, and check scripts.
- Justified: yes, because the goal is both implementation and Staff-level
  apprenticeship.
- Keep simple for now:
  - no microservice split
  - no advanced ML before data
  - no real PSP integration
  - no production GenAI agent
  - no graph database until fraud patterns justify it

## 10. Design Review Narrative

Practice saying this out loud:

- This week we built the production-shaped foundation for a multi-tenant
  payments and fraud simulator.
- The main invariant was that merchant-owned data must derive tenant scope from
  credentials and remain tenant-scoped in API behavior and storage.
- The production risk reduced was early cross-tenant leakage, raw credential
  persistence, inconsistent API failures, and unsafe card-data persistence.
- The tradeoff was moving quickly with a modular monolith and local simulator
  while deferring real PSP, ledger, ML, graph, and agents until lineage and
  lifecycle behavior exist.
- The remaining risk is that idempotency, payment attempts, fraud decisions,
  and ledger behavior still need stronger transactional invariants.
- Next, we should continue Day 5/Day 6 work while requiring written
  explain-back and one tiny ownership task for each non-trivial slice.
