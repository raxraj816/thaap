# Daily Deep Dive: 2026-06-05

## 1. System Goal

Day 5 hardened the merchant, customer, and payment-method API contracts before
the project moves deeper into PaymentIntent creation.

This matters because these APIs sit at the edge of tenant identity and
sensitive input. If merchant credentials, raw PII, or raw card input leak into
storage or responses, later payment, fraud, and ML work inherits unsafe data.

## 2. Plain-English Design Brief

The mental model:

- Admin merchant setup requires a bootstrap token, creates a local test
  merchant, and reveals the API key once.
- The database stores only the API key prefix and hash.
- Merchant-facing requests authenticate by hashing `X-Api-Key`.
- Customers store keyed normalized PII hashes, not raw email or phone, and do
  not return those hashes publicly.
- Payment methods store an internal keyed card fingerprint plus simulator-safe
  card metadata, not raw test card input.

Built now:

- Shared hashing helpers for high-entropy generated secrets and keyed sensitive
  values.
- Merchant admin contract tests.
- Customer privacy and validation contract tests.
- Payment method privacy and validation contract tests.

Deferred:

- API key rotation and revocation.
- Full production admin identity, RBAC, and audit.
- Atomic idempotency reservation and concurrency tests.
- Real fraud lineage fields that depend on `PaymentAttempt`.

## 3. Code Map

- `SecretHasher` owns exact SHA-256 hashing and prefix derivation for
  high-entropy generated secrets.
- `SensitiveValueHasher` owns keyed, domain-separated HMACs for PII, card
  fingerprints, and idempotency request hashes.
- `AdminMerchantController` validates `X-Admin-Bootstrap-Token`, generates a
  local test API key, and returns it once.
- `Merchant` stores `apiKeyPrefix` and `apiKeyHash`.
- `MerchantContextArgumentResolver` hashes `X-Api-Key` for lookup.
- `CustomerController` hashes email and optional phone before persistence.
- `PaymentMethodController` normalizes test card input and stores token,
  fingerprint, BIN, last4, funding, and country.
- `MerchantAdminContractTests` proves the merchant credential lifecycle.
- `CustomerAndPaymentMethodContractTests` proves privacy and API error
  contracts.

## 4. Request/Data Flow

Merchant creation:

1. `POST /admin/merchants` validates the merchant name.
2. The controller validates `X-Admin-Bootstrap-Token`.
3. The controller generates a `thaap_test_...` API key.
4. `Merchant` stores prefix/hash and not the raw key.
5. The response returns `id`, `name`, `status`, `apiKeyPrefix`, and raw
   `apiKey`.
6. A later request sends the raw key through `X-Api-Key`.
7. The argument resolver hashes that header and creates `MerchantContext`.

Customer creation:

1. `POST /customers` requires a valid merchant key.
2. Request-body validation checks email shape.
3. Email and phone are lower-normalized and HMAC-hashed with separate domains.
4. The response returns IDs only, not raw PII or internal hashes.

Payment method creation:

1. `POST /payment_methods` requires a valid merchant key and idempotency key.
2. The controller confirms the customer belongs to the same merchant.
3. The card number is normalized and reduced to an internal keyed fingerprint
   plus safe simulator metadata.
4. The response omits raw card input and the internal fingerprint.
5. The database omits raw spaced and normalized card numbers.

## 5. Database Invariants

Relevant Day 4 invariants that Day 5 now proves through API contracts:

- `merchants` has `api_key_prefix` and `api_key_hash`, not `api_key`.
- `api_key_hash` is unique.
- `customers` stores `email_hash` and optional `phone_hash`.
- `payment_methods` stores `token`, `card_fingerprint`, `card_bin`,
  `card_last4`, `card_funding`, and `card_country`.
- Merchant-owned rows carry `merchant_id`.
- Cross-merchant customer attachment is blocked by tenant-scoped lookups and
  composite foreign keys.

## 6. Security And Privacy Invariants

Secrets:

- Raw merchant API key exists only at creation time and in the caller's
  possession after that.
- Merchant creation requires `X-Admin-Bootstrap-Token`; if no bootstrap token
  is configured, the endpoint is disabled.
- Stored API key prefix is non-secret lookup/debug metadata.
- Stored API key hash supports authentication without raw key storage.

Sensitive input:

- Raw email and phone are not persisted or returned.
- Customer PII hashes are internal and not returned.
- Raw card input is not persisted or returned.
- Card fingerprints are internal and not returned.
- CVV is not accepted.
- BIN, last4, funding type, country, and token remain inside the public
  simulator-safe response boundary.

## 7. Fraud/ML Relevance

This slice keeps future fraud data clean:

- Customer hashes can later support velocity and linkage features.
- Internal card fingerprint supports repeat-card features without raw PAN.
- BIN, funding, and country support early deterministic rules.
- Merchant context remains the tenant key for future feature snapshots and
  decisions.

What we avoided:

- No risk scores without a fraud engine.
- No model fields without model versions.
- No decision lineage without `PaymentAttempt`.

## 8. Tests As Proof

Strong proof added:

- Merchant admin contract tests check response shape, prefix/hash storage, raw
  key absence from persisted values, bootstrap-token enforcement, and
  authentication with the returned key.
- Customer contract tests check keyed normalized hashes in storage and raw
  PII/hash absence from public responses.
- Payment method contract tests check safe public metadata, internal keyed
  fingerprint storage, and raw card/fingerprint absence from public responses.
- Validation tests check standard request-id/error response behavior for Day 5
  endpoints.

Existing proof still matters:

- Tenant isolation tests prove cross-merchant access is denied.
- Migration tests prove schema columns and indexes exist.
- API error contract tests prove shared error behavior.

## 9. Staff Engineer Review Notes

Tradeoff:

- Merchant API keys still use SHA-256 because local simulator keys are generated
  high-entropy secrets. Low-entropy customer/card/idempotency hashes use keyed
  HMAC domains.

Risk reduced:

- Unauthorized credential minting risk is reduced by bootstrap-token gating.
- Credential leakage risk from database access is reduced.
- PII and card-data leakage risk from API responses and storage is reduced.
- Future fraud features start from minimized data.

Kept reversible:

- The bootstrap-token admin endpoint can be replaced with real admin auth
  later.
- Card metadata derivation can move to a simulator catalog.
- Customer response shape can be narrowed later with an explicit API version or
  migration plan.

Dangerous overbuild:

- Adding rotation tables, audit logs, RBAC, or fraud fields now would widen the
  slice before their behavior can be tested.

Practice saying this out loud:

- The tradeoff I made was keeping Day 5 to contract hardening instead of adding
  rotation or production admin auth.
