## 2. Payment Processing Concepts Learned

- Payment concepts can be taught publicly without mentioning the private
  implementation: describe the problem, invariants, failure modes, diagrams,
  and operational signals.
- Authorization is permission to capture; capture is where accounting truth
  begins. A `CAPTURED` status without balanced ledger evidence is not defensible
  payment truth.
- Double-entry ledger groups make money movement reviewable because every debit
  must be matched by an equal credit.
- Synthetic payment scenarios are controlled payment stories. They become useful
  only when they flow through the same merchant-facing APIs as real payments,
  because that exercises tenant auth, idempotency, validation, lifecycle state,
  fraud lineage, and processor truth.

## 3. Fraud Detection Concepts Learned

- Explainable fraud intelligence is a strong first public post because it can
  teach decision-time evidence, feature snapshots, reason codes, rule/model
  versions, privacy-safe explanations, and audit review from first principles.
- Synthetic scenarios are Phase 1 fraud/ML infrastructure because rules, review
  queues, replay, and future model evaluation need repeatable payment-risk
  examples before labels and model datasets can be trusted.

## 4. Security Concepts Learned

- Public writing should avoid leaking private product names, repo paths,
  branches, commits, internal notes, or implementation status.
- The new public checker enforces this at the draft level.
- Ledger rows must carry `merchant_id` and be listed only through merchant
  scope, because ledger history is merchant financial data.
- Ledger reads must be bounded. Tenant scope answers "whose data"; pagination
  answers "how much data can one request pull."
- Capture audit payloads can include safe IDs, statuses, amounts, authorization
  IDs, and ledger entry IDs without exposing card input, API keys, card
  fingerprints, or raw PII.
- Synthetic scenario summaries must omit raw PAN, CVV, raw buyer email, raw
  phone, API keys, idempotency keys, hashes, webhook secrets, and card
  fingerprints. The generator records only safe IDs, statuses, decision IDs,
  and processor evidence.

## 5. Architecture / Design Notes

- Private work may inspire topic choice, but the article body should stand on
  its own for a public technical reader.
- The workflow now separates internal learning artifacts from public essays.
- Capture now sits after approved authorization and before refunds/disputes.
  The first ledger chapter intentionally records only full capture with
  `CUSTOMER_RECEIVABLE` debit and `MERCHANT_PAYABLE` credit.
- Capture state, ledger entries, webhook delivery records, capture audit log,
  and idempotency completion share one transaction boundary through
  `IdempotencyService`.
- The database now protects capture ledger source truth instead of relying only
  on controller code: capture rows must reference a same-merchant PaymentIntent,
  use the allowed Chapter 15 account/direction pairs, and avoid duplicate
  capture account postings.
- Chapter 16 keeps generated data honest by using public APIs only. Direct
  database seeding remains deferred because it would bypass the exact product
  boundaries the generated scenarios are supposed to prove.
- Processor outcome codes in the synthetic summary come from the safe
  authorization read endpoint, not from the generator's expected fixture table.

## 7. Bugs, Surprises, Or Tradeoffs

- The earlier version was too close to a THAAP case study. The corrected version
  removes product-specific framing from the public draft and template.
- The deeper failure was optimizing for structure instead of reader value. The
  editorial rubric now explicitly checks hook, reader promise, specificity,
  narrative flow, architecture quality, Staff-level judgment, credibility, and
  publication fit.
- The post template now separates planning notes from publishable prose so the
  writer can think clearly without leaking scaffolding into the final article.
- The tradeoff is that the public checker uses simple blocked terms. It is not a
  full writing-quality review, but it catches the most obvious leaks.
- The capture endpoint previously flipped state and emitted webhook records
  without ledger evidence. That was acceptable as a lifecycle guard scaffold,
  but not acceptable once authorization made capture eligible.
- We intentionally did not add a separate `captures` table yet. For this chapter,
  captured PaymentIntent state plus the ledger transaction group is enough
  capture truth.
- Refund ledger entries, fees, partial capture, partial refunds, disputes, and
  payout settlement remain deferred because each needs its own accounting model.
- Review correction: an application-level existing-ledger check is not enough
  ledger protection. The database must reject impossible source truth too.
- The generator records a deterministic scenario plan, not deterministic
  database UUIDs. That is the right boundary because entity IDs are created by
  the API/database, while scenario labels, card fixture choices, and expected
  outcome classes are controlled by the seed.
- We intentionally did not capture the approved scenario in Chapter 16. Capture
  already has Chapter 15 proof; this generator closes the Phase 1 payment-core
  scenario gap without inventing extra money movement.
