# Daily Deep Dive: 2026-06-21

This note explains the Chapter 12 durable fraud-lineage implementation.

## 1. System Goal

- Persist honest fraud lineage for every successful confirm attempt.
- Record the decision, score, risk level, reasons, latency, and freshness proof
  before processor authorization.
- Create immutable `features_v1` snapshots that future analysts, rule
  simulation, and ML replay can trust.

## 2. Plain-English Design Brief

Before Chapter 12, THAAP could authorize a payment but could not explain the
fraud decision behind the attempt. The decision engine existed, but its result
was in memory only.

Chapter 12 changes that. Confirm now creates a PaymentAttempt, computes a small
safe feature snapshot, runs the deterministic stub decision, persists
FraudDecision, persists FeatureSnapshot, attaches the decision to the attempt,
and only then calls the processor for `ALLOW`.

The decision is intentionally humble: `ALLOW`, score `0.00`, risk level `LOW`,
ruleset version `rules_stub_v1`, nullable model version, and
`RULES_NOT_ENABLED`. This is real lineage, not fake intelligence.

## 3. Code Map

- `V3__add_fraud_lineage.sql` upgrades `fraud_decisions` and creates
  `feature_snapshots`. Existing placeholder decisions are backfilled as
  legacy incomplete rows without fake PaymentAttempt lineage.
- `FraudDecision` stores action, score, level, model/ruleset lineage, latency,
  timestamps, freshness summary, and reason codes.
- `FeatureSnapshot` stores immutable `features_v1` payloads and freshness proof.
- `PaymentIntentController` owns the Chapter 12 confirm orchestration.
- `FraudDecisionController` exposes tenant-scoped decision summaries and detail.
- `PaymentIntentConfirmContractTests`,
  `PaymentIntentConfirmProcessorAdapterCallTests`,
  `MerchantTenantIsolationTests`, and `DatabaseMigrationTests` prove the slice.

## 4. Request/Data Flow

1. Merchant calls `POST /payment_intents/{id}/confirm`.
2. `MerchantContext` and `Idempotency-Key` gate the mutation.
3. PaymentIntent is loaded with a tenant-scoped row lock.
4. PaymentMethod is loaded through tenant scope and customer ownership is checked.
5. PaymentAttempt is created with the next attempt number.
6. THAAP builds safe `features_v1` values from decision-time request/domain facts.
7. The decision engine returns the deterministic Chapter 12 stub decision.
8. FraudDecision is persisted with score, action, reason, latency, and freshness.
9. FeatureSnapshot is persisted and linked to both FraudDecision and
   PaymentAttempt.
10. PaymentAttempt receives `fraudDecisionId`.
11. `ALLOW` moves the attempt to `READY_FOR_PROCESSOR` and intent to
   `PROCESSING`.
12. Processor authorization runs and maps the final attempt/intent state.

The whole flow remains inside the idempotency transaction. Replays return the
stored response. Processor failures roll back attempt, decision, snapshot,
authorization, and intent state.

Feature snapshot persistence failures also roll the whole confirm back. That
matters because a stored FraudDecision without the features that produced it is
not good audit evidence.

## 5. Database Invariants

- One FraudDecision per `(merchant_id, payment_attempt_id)` for new
  confirm-generated rows.
- One FeatureSnapshot per `(merchant_id, fraud_decision_id)`.
- One FeatureSnapshot per `(merchant_id, payment_attempt_id)`.
- FeatureSnapshot references both FraudDecision and PaymentAttempt through
  tenant-scoped foreign keys.
- FraudDecision references PaymentAttempt through a tenant-scoped foreign key.
- `payment_attempts.fraud_decision_id` is the public correlation pointer; the
  owning durability direction is FraudDecision -> PaymentAttempt.
- Legacy placeholder FraudDecision rows may have `payment_attempt_id = null`,
  `ruleset_version = legacy_placeholder_v1`, and freshness `MISSING`. They are
  audit upgrade artifacts, not ML-valid training examples.
- There is intentionally no reverse FK from
  `payment_attempts.fraud_decision_id` to `fraud_decisions.id`: adding it now
  would create circular insert/delete ordering between attempts and decisions
  while the real ownership direction is already protected by
  FraudDecision -> PaymentAttempt and FeatureSnapshot -> both.

## 6. Security And Privacy Invariants

- Feature snapshots do not include raw PAN, CVV, raw email, raw phone, API keys,
  idempotency hashes, card fingerprints, or merchant secrets.
- Safe card metadata such as BIN, last4, funding type, and country remains
  inside the simulator boundary.
- `features_v1` keeps lineage IDs for portable replay/export convenience, but
  dedicated relational columns remain canonical for joins and integrity.
- `features_v1` has a conservative serialized-size guard so a future extractor
  cannot accidentally store unbounded JSON in the confirm transaction.
- Fraud decision list/detail APIs use merchant context and return 404 across
  tenant boundaries.

## 7. Fraud/ML Relevance

- FraudDecision gives analysts the decision summary: action, score, risk level,
  reasons, latency, ruleset, model version, and freshness summary.
- FeatureSnapshot gives ML and replay the immutable facts used at decision time.
- Keeping model version nullable protects ML lineage from fake provenance.
- `features_v1` creates a versioned contract that can grow without rewriting
  historical decision truth.

## 8. Tests As Proof

- Approved confirm proves FraudDecision, FeatureSnapshot, Authorization, and
  PaymentAttempt linkage.
- Processor declines prove fraud lineage exists even when authorization declines.
- 3DS-required outcomes prove action-required processor paths still preserve
  lineage.
- Idempotent replay proves no duplicate attempts, decisions, snapshots,
  authorizations, or webhook deliveries.
- Retry after decline proves attempt 2 receives its own decision and snapshot.
- Non-`ALLOW` and processor-failure tests prove transaction rollback removes
  lineage.
- FeatureSnapshot repository failure proves the transaction rolls back even
  after FraudDecision creation.
- Converter unit tests prove null, blank, normal round-trip, and deterministic
  feature-map serialization behavior.
- Legacy migration scenario proves V3 can run after V1/V2 with old placeholder
  FraudDecision rows.
- Tenant tests prove fraud decision list/detail visibility is merchant-scoped.
- Migration tests prove `V3` schema, columns, indexes, and Hibernate validation.
- PostgreSQL Testcontainers verification now runs against Docker Engine 29 after
  bumping Testcontainers to `1.21.4`; the production-database migration proof is
  no longer silently skipped locally.

## 9. Staff Engineer Review Notes

- Tradeoff: store first features directly in PostgreSQL rather than introducing
  a separate feature store too early.
- Risk reduced: THAAP no longer has authorized attempts with no fraud explanation.
- Risk reduced: future ML work can train from decision-time snapshots, not
  reconstructed current state.
- Reversible choice: the stub decision can be replaced by real rules/model
  scoring without changing the confirm API.
- Dangerous shortcut avoided: inventing fake model lineage or storing raw card
  data in feature payloads.
- Review correction: Docker availability and Testcontainers availability are
  different operational checks. Docker CLI and the engine socket were healthy;
  Testcontainers `1.21.3` failed Docker 29 API negotiation. Upgrading to
  `1.21.4` restored the real PostgreSQL migration test.

## 13. Interview Narrative

- The tradeoff I made was to persist honest stub lineage without pretending a
  real rules engine or model exists.
- The invariant I enforced was one FraudDecision and one FeatureSnapshot per
  successful confirm attempt.
- The production risk I reduced was unexplained authorization history polluting
  analyst review and future ML datasets.
- I deferred rules, velocity counters, model scoring, review behavior, audit
  logs, and ledger side effects because Chapter 12 only owns lineage.
- The tests prove lineage for approved, declined, 3DS, replay, retry, rollback,
  and tenant-isolation paths.
