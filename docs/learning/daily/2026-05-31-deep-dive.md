# Daily Deep Dive: 2026-05-31

## 1. System Goal

We made THAAP locally runnable and added the first backend domain slice:
PostgreSQL, Redis, Spring Boot, health checks, local/test profiles, scripts,
merchant tenant context, merchant-scoped API surfaces, and early idempotency.

This matters because payment systems need durable state, repeatable local
infrastructure, and tenant boundaries before lifecycle logic becomes useful.

## 2. Plain-English Design Brief

The mental model:

- Docker Compose runs the local dependencies.
- `payments-api` is the first real deployable.
- PostgreSQL is durable truth.
- Redis supports future velocity/idempotency acceleration.
- `Merchant` is the tenant root.
- Merchant-facing APIs derive tenant context from `X-Api-Key`.
- Merchant-owned reads and writes are scoped by `merchant_id`.

What would go wrong without this:

- Payment, webhook, fraud, and review objects could leak across merchants.
- Local development would depend on each engineer manually configuring
  databases.
- Health checks would not prove dependency readiness.
- Future idempotency and velocity work would lack the infrastructure it needs.

## 3. Code Map

- `infra/docker/compose.yml` defines PostgreSQL and Redis for local
  development.
- `scripts/local-infra-up.sh`, `scripts/local-infra-down.sh`, and
  `scripts/local-infra-ps.sh` make infrastructure repeatable.
- `apps/payments-api/pom.xml` defines the Java/Spring backend dependencies.
- `apps/payments-api/src/main/resources/application.yml` separates local and
  test profile behavior.
- `PaymentsApiApplication` starts the Spring Boot app.
- `MerchantContext` carries resolved merchant identity.
- `MerchantContextArgumentResolver` resolves merchant context from `X-Api-Key`.
- `AdminMerchantController` creates local test merchants.
- `CustomerController`, `PaymentMethodController`, `PaymentIntentController`,
  `RefundController`, `WebhookController`, `FraudDecisionController`,
  `FraudRuleController`, and `ReviewCaseController` create the first
  merchant-scoped surfaces.
- `IdempotencyService` stores and replays merchant-scoped mutation responses.
- `MerchantTenantIsolationTests` proves the important tenant behaviors.

Later Day 4 hardening improved this slice by moving schema creation to Flyway
and storing API keys/webhook secrets as prefixes and hashes.

## 4. Request/Data Flow

Merchant setup:

1. Admin creates a merchant.
2. The system returns a test API key.
3. Future merchant-facing requests send `X-Api-Key`.
4. The argument resolver converts the key into a `MerchantContext`.
5. Controllers use `merchantContext.merchantId()` for reads and writes.

Tenant-scoped payment intent creation:

1. Merchant sends `POST /payment_intents` with `X-Api-Key` and
   `Idempotency-Key`.
2. Idempotency checks whether the same merchant already used the key.
3. Controller verifies the customer belongs to the same merchant.
4. The payment intent is saved with the merchant ID.
5. A response is stored for future replay.

Webhook visibility:

1. A merchant creates webhook endpoints.
2. Payment events create delivery records for that merchant.
3. `GET /webhook_deliveries` filters by current merchant context.

## 5. Database Invariants

At this stage, local JPA schema update was temporary scaffolding. The intended
invariants were:

- every merchant-owned row carries `merchant_id`
- idempotency records are scoped by merchant and key
- child objects must belong to the current merchant
- tenant list endpoints filter by merchant

Day 4 later moved these from application-level intent into Flyway migrations,
unique constraints, indexes, and composite foreign keys.

## 6. Security And Privacy Invariants

Important invariants:

- clients cannot choose trusted `merchantId` in request bodies
- missing or invalid `X-Api-Key` is rejected
- customer identity values are hashed in this early slice
- card numbers are reduced to simulator token/fingerprint/BIN/last4 metadata
- test profile avoids requiring real Redis for unit-level checks

Known historical gap:

- API key storage was initially local scaffolding. The daily note correctly
  identified hashing and one-time reveal as a required hardening step, and that
  was addressed in the later migration/hardening slice.

## 7. Fraud/ML Relevance

This slice created the tenant substrate for future fraud and ML:

- fraud decisions, rules, reviews, features, replay rows, model predictions,
  graph records, and analytics projections must carry or derive `merchant_id`
- Redis will support future velocity counters
- payment methods produce early safe card metadata useful for fraud features
- tenant isolation is required before merchant-level model evaluation can be
  trusted

The Staff-level lesson: multi-tenant fraud ML is not only about model quality.
It is also about preventing cross-tenant feature leakage and evaluation bias.

## 8. Tests As Proof

Tests and verification covered:

- Spring Boot context startup
- actuator health/liveness/readiness
- local PostgreSQL and Redis health through Docker Compose
- API rejection for missing or invalid merchant API key
- cross-merchant payment intent read denial
- cross-merchant customer ownership checks
- cross-merchant capture/cancel/refund denial
- idempotency scoped by merchant
- webhook delivery visibility scoped by merchant
- fraud/rule/review list scoping
- normalized card-number validation

What a Staff engineer would ask next:

- Move schema ownership from JPA update to Flyway.
- Store secrets as hashes, not raw local scaffolding values.
- Add database constraints so tenant isolation survives application bugs.
- Add idempotency race/concurrency tests before processor side effects exist.

## 9. Staff Engineer Review Notes

Tradeoff:

- We allowed temporary local scaffolding to move quickly, but documented the
  migration and secret-hardening work needed before the foundation could be
  considered production-shaped.

Risk reduced:

- Merchant tenant context became centralized instead of repeated manually in
  each controller.

Kept reversible:

- PostgreSQL and Redis are local Docker services now, but map naturally to
  RDS/Aurora and ElastiCache later.

Dangerous overbuild:

- Adding Kafka, ClickHouse, Neo4j, or MLflow before the payment API had a
  working tenant boundary would distract from the highest-risk foundation.

## 13. Interview Narrative

Practice saying this out loud:

- The tradeoff I made was to build the local platform substrate and tenant API
  boundary before richer payment lifecycle behavior.
- The invariant I enforced was that merchant-facing operations use resolved
  tenant context rather than trusting caller-supplied merchant IDs.
- The production risk I reduced was cross-tenant data leakage across payments,
  webhooks, fraud lists, rules, and review surfaces.
- I deferred Flyway constraints and secret hashing to the next hardening slice
  because the first goal was to make the backend runnable and testable.
- The tests prove that local infrastructure starts, health checks work, and
  merchant A cannot read or mutate merchant B's core objects through the API.
