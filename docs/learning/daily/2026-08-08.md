# Daily Learning Note: 2026-08-08

## 1. What We Built

- `com.thaap.payments.time.DatabaseInstant`: one definition of the precision a persisted instant
  is allowed to carry, plus `tick()` for wrapping a clock so every reading it hands out is already
  at that precision. `EventTimePrecision` now delegates to it rather than repeating the rule.
- The application `Clock` bean now ticks at microseconds. Two production classes that bypassed the
  bean with their own `Clock.systemUTC()` — `WebhookExecutionConfiguration` and
  `WebhookEndpointSecretService` — now wrap theirs the same way.
- 315 call sites swept from bare `Instant.now()` to `DatabaseInstant.now()`: 53 in production,
  262 in tests.
- `DatabaseInstantTests`, including a source scan that fails the build on any reintroduction.
- `ER-0100` in the escaped review register.

## 2. Payment Processing Concepts Learned

- A timestamp on a payment record is part of the public contract, not decoration. `POST /refunds`
  was returning `createdAt` as `.400031361Z` while every later `GET` of the same immutable field
  returned `.400031Z`. No money, lineage or tenant invariant broke — but a consumer that stored the
  create response and compared it to a later read would see one field with two values, and would be
  right to treat that as corruption.
- The failure is worst precisely where it looks most harmless. Nothing throws, nothing logs, and
  the digits that differ are the ones nobody reads.

## 3. Fraud Detection Concepts Learned

- Event lineage is only as sound as the ordering key underneath it. `CanonicalEventCodec` refuses a
  payload timestamp finer than the database can store, which is what turned a silent divergence in
  the fraud-label and review-resolution streams into a loud `IllegalArgumentException`. That guard
  was written on 2026-08-01 and could not fire once on this machine.

## 4. Security Concepts Learned

- Nothing new about secrets today. The relevant security-adjacent lesson is about trust in
  evidence: a guard that cannot execute in your environment provides no assurance there, no matter
  how correct it is. `CanonicalEventCodec.validateInstant()` was right for a week and silent for a
  week.

## 5. Architecture / Design Notes

- **Fix precision at the source, not at the call site.** The codebase already carried roughly
  thirty ad-hoc `.truncatedTo(ChronoUnit.MICROS)` calls added since 2026-07-01, one per place
  someone suspected it mattered. Every one is a no-op on macOS, so nobody who added one could learn
  whether it was load-bearing. A rule applied by memory at 315 places will be forgotten at the
  316th; a clock that cannot produce the wrong value cannot be forgotten.
- **Truncate rather than round.** PostgreSQL rounds, so `.656610779Z` becomes `.656611Z` — an
  instant the application never held. Truncation keeps the stored value one that actually occurred
  in the process.
- **The scattering was the diagnosis.** When the same defensive call starts showing up across
  unrelated files, that is not diligence. It is a missing invariant at the source announcing
  itself, and the correct response is to ask why each site has to remember.

## 6. Tests And Verification

- Linux, inside `eclipse-temurin:25`, against a host confirmed to return
  `sub-microsecond digits=387`: **1384 tests, 0 failures, 0 errors**. All 48 previously failing
  tests pass.
- macOS: **1384 tests, 0 failures**. Nothing regressed.
- `DatabaseInstantTests` pins truncation-not-rounding, that a ticked clock truncates even when the

- The source-scan gate was verified the way `ER-0098` requires: a violating file was planted, the
  test failed and named it, the file was removed, the test passed. A gate nobody has watched fail
  is not a gate.

## 7. Bugs, Surprises, Or Tradeoffs

- **The whole thing.** `Instant.now()` returns microseconds on macOS and nanoseconds on Linux. The
  defect entered on 2026-05-31 with the first payment entities and survived ten weeks, not because
  review was careless but because every test run in this repository's history executed on an
  operating system whose clock is coarser than the deployment target. The bug was unobservable by
  construction.
- **The gate paid for itself on its first run.** `43b7f36` added the first and only CI workflow
  this repository has ever had, yesterday. Its first execution found a ten-week-old production
  defect. The argument for CI was "stop enforcing by memory"; the actual return was "run somewhere
  that is not your laptop."
- **Tradeoff accepted:** two rapid calls can now land in the same microsecond where nanoseconds
  previously separated them. This is not a new risk — macOS has always been microsecond-resolution
  and the suite is green there — so Linux is becoming as coarse as the development machines
  already were.
- **Deliberately not changed:** the `400` and `500` input guards. They were correct throughout.
  Relaxing them would have made CI green by deleting the only honest reporting of the defect.
- **Unresolved.** Four `ReviewBulkBacklogReadinessTests` failures read `-1.0`, meaning the backlog
  gauge was absent from the registry rather than stale. They pass on Linux now and I did not
  establish why they failed. The suspect is `meterRegistry.clear()` at
  `PaymentIntentConfirmContractTests:89` against gauges registered once in a constructor, but those
  two classes have different Spring context keys, so the link is unproven. Recorded here rather
  than claimed as fixed.

## 8. Open Questions

- Why was the backlog gauge missing from the registry in CI? If the cause is test-class execution
  order, GitHub's runner could order differently than the local container did and it will return.
- Surefire's default `runOrder` is `filesystem`, which is arbitrary on ext4 and roughly sorted on
  APFS. Should the suite pin an explicit order so CI and local runs are comparable at all?
- Are the roughly thirty ad-hoc `.truncatedTo(ChronoUnit.MICROS)` calls now redundant? They are
  harmless, but leaving them implies the source is not trusted.
