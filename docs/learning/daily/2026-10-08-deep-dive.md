# 2026-10-08 — Git History And Publication Authority

The original change remains an ancestor of develop after a revert. A revert adds
an inverse patch; it does not remove the original commit. Merely pointing a feature
branch at the original commit would therefore not reintroduce its changes through
a meaningful new PR. Creating a feature branch from the reverted develop and
cherry-picking the original patch produces a new descendant and the intended diff.

Two exact-tree comparisons protect preservation: reverted develop against the
pre-change base, and the restored feature commit against the original research
commit. The repair journal and branch instruction then add explicit documentation
on the feature branch. Payment lifecycle, tenant isolation, ML lineage, schema and
runtime behavior remain unchanged; historical implementation proof stays historical.

The failure was an authorization/workflow judgment error. A green pre-push gate
does not establish that the target branch is permitted. Before every publication,
inspect the branch, intended remote target, owner's authorization and required
review path. Ordinary commit/push requests must use a feature branch and PR.
