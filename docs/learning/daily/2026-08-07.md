## Three things worth remembering

### 1. A proof field is a promise that something exists, and nothing checked it

The gate validated the *shape* of a row — required fields present, `Status: PASS`, no
unfinished-work marker. That is exactly the check a well-formed obsolete claim passes.
Every Phase 5 matrix is `PRE_IMPLEMENTATION`, so its `Proof` fields are written in future
tense as obligations. Implementation then consolidated each domain into one contract
class plus a `*PostgreSqlTests` subclass, and `Status` flipped to `PASS` without anyone
rewriting `Proof`. Chapter 50 planned eleven suites and shipped seven test methods.
Chapter 46 planned ten and shipped 302 lines across two classes.

The consolidation was sound engineering. The defect was that the durable traceability
artifact was never updated to say so, so it points at names that resolve to nothing.

### 2. `ER-0098`'s own correction was never enforced

`ER-0098` states that removing `openapi-contract-check.py` from the readiness run would
fail a test. It would not have. The readiness tests stubbed each checker and asserted
only the exit code — an unreferenced stub is simply never executed, and the run still
exits zero. The correction was recorded, believed, and inert for a chapter.

The fix is a marker-file test that asserts *invocation*, verified by deleting a gate line
and watching it fail, then restoring it and watching it pass. The wider lesson: when a
process correction is written, its enforcement must be executed against the failure it
claims to prevent. Nobody had ever deleted the line to check.

### 3. A matrix with only one status cannot describe reality

Every gap row was `PASS` while naming a suite that did not exist, because `PASS` was the
only value the gate accepted. A reviewer who noticed a thin row had nowhere to record it
short of blocking a merged phase — which is not a move anyone makes at the end of a
closure pass. The vocabulary shortage was not cosmetic; it was the reason the condition
survived review.

Adding `PARTIAL` cost about thirty lines because only one line in the whole repository
enforced row status. The absence was never load-bearing, only unexamined.

## Where production turned out to be short

Writing the tests is how we learned production did not keep three promises:

- `ProjectionRebuildMetrics` emitted no duration and no lease-recovery signal, though
  `ProjectionRebuildStore` had recorded `LEASED` versus `LEASE_RECOVERED` as durable
  events all along. Added both, plus a `recovered` flag on `ProjectionRebuildLease` so
  the distinction is carried rather than inferred from the fencing epoch — the epoch
  increments on every claim, so inferring it would have been wrong.
- `TransactionalDomainEventWriter` emitted nothing at all. Added
  `DomainEventWriterMetrics`. Its rejection counter fires immediately rather than after
  commit, because the rejecting transaction is about to roll back and a deferred counter
  would make an integrity failure indistinguishable from an ordinary rollback.

## Two things that looked like findings and were not

- I reported the replay execution probe as having zero call sites. Wrong: my grep was

## Second pass: an artifact gap that was really a testability gap

The two rebuild concurrency rows and the replay non-interference row had been sitting in
the same bucket, described as three missing test suites. They were not three of a kind.
Replay's row was payable in an afternoon and rebuild's was not, and the reason was one
class: `OfflineReplayDatasetExecutionProbe`, a seam replay had from the day its worker was
written and rebuild never got. A rebuild's lease invariants are only observable at instants
inside a Spring Batch chunk. Without a seam there, a test can assert the outcome of an
uninterrupted run and nothing else — so the audit's per-row verdict was accurate but its
grouping hid the actual blocker. **An unwritten test suite is sometimes a missing test
seam wearing a costume.**

`ProjectionRebuildExecutionProbe` is now wired at four instants: before a chunk takes its
lease, after chunk evidence and before its checkpoint, after the checkpoint statement, and
before the generation switch commits. Picking the first one was the whole design problem.
Every point inside the writer sits inside a chunk transaction that opened by locking the
rebuild row `FOR UPDATE`, so a takeover staged from any of them blocks on the victim
instead of racing it. The only instant a worker intends to write and holds no lock is
before it takes the lease, which is exactly where a real stale worker gets overtaken.

### Two places the row's prose was wrong about production

Both are now written down as what happens, not what was expected.

A live projection write racing a generation switch is **not** parked and applied to the
winner. It blocks on the definition pointer, and when the lock releases, read-committed
re-evaluation means the generation row it locked no longer satisfies
`generation.id = definition.active_generation_id` — so it fails with
`ProjectionGenerationUnavailableException`. That looks like a defect and is the opposite.
The exception is deliberately not caught by `process`, so the event is not quarantined; it
is refused and applied on redelivery. Quarantining a valid event because a switch happened
underneath it would convert a transient race into permanent operator work. The dangerous
outcome — landing in the generation being retired — is the one ruled out.

An incompatible-handler rollback target cannot be built at all.
`protect_projection_generation` makes a generation's handler version immutable, and a
generation is created carrying its definition's version, so a retained target cannot drift
from the definition that owns it. The test asserts unconstructibility instead of refusal,
which is the stronger claim.

### Three things the tests taught, none of them about the code under test

- A lease takeover staged with a plain `JdbcTemplate` call from inside the victim's chunk
  transaction **joins that transaction** and is rolled back with the chunk it was supposed
  to fence. The test passes and asserts nothing. Another worker is another transaction, so
  the fixture now uses `PROPAGATION_REQUIRES_NEW`. This is the second time this session a
  test looked green while measuring nothing.
- `ck_projection_rebuilds_time` enforces `lease_expires_at > updated_at`, so a lease cannot
  be back-dated — expiry is only reachable by winding `updated_at` back with it. Identical
  constraint shape to the replay table, and the same trap.
- `md5(string_agg(row_to_json(t)))` over a table silently digests one column instead of the
  row if the alias collides with a column name. `fraud_labels` has a column called
  `source`, and `source` was the alias. Twenty-one families were being compared and one of
  them was comparing a varchar to itself.

### An exception whose supertype was load-bearing and wrong

`ProjectionRebuildFenceException` extended `IllegalStateException`. Spring's Hibernate
translator maps that to `InvalidDataAccessApiUsageException`, because the JPA specification
treats `IllegalStateException` as API misuse — so every throw out of
`ProjectionRebuildStore`, a `@Repository`, came back rewrapped. The same type surfaced raw
from the applier, control service and reconciliation engine, which are not repositories.
One exception type, two observable behaviors, decided by an annotation on the thrower.

There was no live defect: nothing catches it. The writer lets it fail the Spring Batch
chunk and `ProjectionRebuildJobListener` fences on token and epoch, not on type. But
`catch (ProjectionRebuildFenceException)` would have compiled, read correctly, and never
fired — the kind of trap that is only cheap to fix before someone relies on it.

It now extends `RuntimeException`, matching `StaleReplayDatasetWorkerException` on the
replay side, which had the same shape for the same reason all along. Deliberately **not** a
`DataAccessException`: losing a fence is a domain ownership decision, not a database access
failure, and that hierarchy splits on transient versus non-transient — a retry
classification that is actively wrong when the fenced loser must stop rather than retry.

**The generalisation: an exception's supertype is part of its contract when a framework
inspects types.** `@Repository`, `@Transactional` rollback rules and retry policies all
branch on it, so "which RuntimeException do I extend" is an interface decision, not a
formality. The test now asserts the exact type through the real repository proxy, because
the only thing that would catch a regression here is an assertion that the wrapping is
absent.

### The technique worth keeping: assert the invariant over the class, not the methods

Two assertions in this pass make claims that cannot rot. `C46-OPS-001` asserts
`RiskOperationsEventProducer` has exactly one constructor parameter and one THAAP-typed
field, both `DomainEventWriter` — so the chapter's "no Kafka, projection, rebuild or dataset
behavior" claim now fails a test the moment a dependency is added, instead of surviving
until a reviewer happens to look. `C46-AUTH-001` asserts by reflection that **every** public
producer method takes authority from a typed authenticated context or is an explicit system
fact, so a method added next year cannot quietly opt out.

**A structural invariant asserted over a whole class is worth more than the same invariant
sampled on the methods that existed the day it was written.** Both of these would have been
much weaker as "here are three methods, and they look right".

leaves the row `RUNNING` exactly as JVM death would; whether that is enough for the restart
