## 2. Payment Processing Concepts Learned

- Weekly public writing should still start from payment truth: lifecycle state,
  idempotency behavior, processor boundaries, authorization outcomes, and
  ledger deferrals.
- A good payment-system post explains what the system can prove, not only what
  the feature appears to do.

## 3. Fraud Detection Concepts Learned

- Fraud explainability can be taught publicly through generic architecture:
  decision-time evidence, feature snapshots, reason codes, model/rule versions,
  audit records, and analyst review.
- Blog topics should be concept-led and useful to a reader who knows nothing
  about the private codebase.

## 4. Security Concepts Learned

- Public writing should avoid implying sensitive data is stored or exposed.
- The template now asks writers to name raw, hashed, tokenized, masked, or
  omitted values where security and privacy matter.

## 5. Architecture / Design Notes

- The blog system is intentionally a public-writing workflow. Private learning
  artifacts can inspire topic choice, but the article body should not mention
  product names, repository paths, files, commits, or weekly build status.
- The title should usually be public and concept-led, such as "Why Fraud
  Systems Need Explainable Intelligence."
- The publishing rule is to teach concepts deeply without leaking private
  implementation context.
