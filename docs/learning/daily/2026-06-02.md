## 2. Payment Processing Concepts Learned

- Payment schemas need explicit migration history because retries,
  idempotency, ledger entries, webhooks, and reviews all depend on stable
  persisted state.
- Composite tenant ownership foreign keys are stronger than checking only
  globally unique IDs. They prevent a payment intent or payment method from
  pointing at a customer owned by another merchant.
- The idempotency uniqueness invariant belongs in the database, not only in
  service code: `(merchant_id, idempotency_key)` is the durable boundary.
- `capture_method` belongs on `payment_intents` before capture behavior grows,
  because it changes later authorization/capture lifecycle semantics.

## 3. Fraud Detection Concepts Learned

- Fraud tables are still scaffold-level, but they now have durable
  tenant-scoped storage and merchant hot-lookup indexes.
- Fraud decision, rule, and review list endpoints currently query by
  `merchant_id` ordered by `created_at`, so the migration added matching
  composite indexes for analyst-facing read paths.
- Fraud and review tables remain intentionally scaffold-level until
  `payment_attempts` exists, so fraud lineage can use real foreign keys instead
  of nullable orphan identifiers.

## 4. Security Concepts Learned

- Foreign keys from every tenant-owned table back to `merchants` make tenant
  ownership a storage invariant, not only an API convention.
- Composite foreign keys on `(merchant_id, customer_id)` and
  `(merchant_id, webhook_endpoint_id)` prevent cross-merchant object
  attachment even if application code regresses later.
- Merchant API keys and webhook signing secrets are not persisted raw; lookup
  and later signing flows use stored hashes plus non-secret prefixes.
- Payment method storage keeps safe card metadata such as BIN, last4, funding,
  and country, but still does not persist full PAN or CVV.
- Existing local PostgreSQL volumes created by temporary Hibernate scaffolding
  should be reset before first Flyway startup because the Day 4 migration is
  the first authoritative schema.

## 5. Architecture / Design Notes

- Flyway owns schema creation from `src/main/resources/db/migration`.
- Hibernate now runs with `ddl-auto: validate` in both local and test profiles.
- The first migration mirrors the current intentionally slim domain model
  rather than adding future payment-attempt, ledger, audit, or ML fields early.
- The schema uses globally unique UUID primary keys plus composite
  `(merchant_id, id)` unique constraints where child tables need tenant-safe
  foreign keys.
- The schema pulls forward stable payment/security columns, but still defers
  payment-attempt-linked fraud decision fields until the attempt table lands.
- Future implementation days now require a readiness review, review-disposition
  decision, and post-implementation self-review before being marked complete.

## 7. Bugs, Surprises, Or Tradeoffs

- The first sandboxed Maven run could not resolve new Flyway artifacts because
  network access was restricted; rerunning with approved network access
  downloaded the dependencies into the workspace-local Maven cache.
- H2 appends suffixes to backing indexes for some unique constraints, so
  migration metadata tests assert the expected prefix instead of exact H2
  backing-index names.
- Constraint tests intentionally log SQL constraint violations while asserting
  that those violations are raised correctly.
- Testcontainers correctly skipped the PostgreSQL migration test when Docker
  was not available in the current runtime.
- The default local `thaap_payments` PostgreSQL database still contains
  pre-Flyway Hibernate-created tables from earlier scaffolding. Because that
  schema is non-empty and has no `flyway_schema_history`, normal
  `scripts/payments-api-run.sh` fails until the local volume/database is reset
  or replaced with a clean database.
