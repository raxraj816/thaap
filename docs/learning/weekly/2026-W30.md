## Engineering lessons

- Product risk metrics require explicit durable denominators, coverage, time,
  traffic-origin, and label-availability semantics; operational telemetry
  cannot substitute for them.
- A bounded historical policy simulator can precede the general Phase 5 event
  replay platform only if it reads immutable decision-time facts and does not
  claim Kafka, current Redis, or model semantics.
- Pulling forward a thin UI is safe when it operates proven APIs and retains an
  honest local/test credential boundary; hosted identity remains separate.
- Roadmap coordinates belong in plans and review packets; product capabilities
  belong in executable identity.
- Applied Flyway history is deployment truth. Improve an uncommitted migration
  before release, but repair and validate an already-applied local identity
  without rewriting shared history or deleting data.
- Comments inside exact-byte Redis scripts are protocol bytes. A naming-only
  comment change still requires a new verified digest and reconciled evidence.
- Java file renames require a clean build because incremental output can retain
  the old class and create false duplicate proof.
- Automated policy must model legitimate exceptions narrowly. A global chapter
  ban would break the required matrix/dossier workflow; exact scope is safer.
- HMAC privacy is not enough: rotation must preserve the fraud decision made
  from still-live evidence, including nested inner/outer pseudonyms.
- Cross-resource rollback needs ownership, not just identity. Stable retry
  identity makes deduplication possible but makes unconditional cleanup unsafe.
- Authorization must execute conceptually before replay; principal-scoped
  idempotency prevents a lower-role actor from borrowing a stored success.

## Next review focus

Chapter 38 must freeze historical cohort, `asOf`, traffic-origin, label-
availability, candidate digest, checkpoint/restart, cancellation/finalization,
and report-integrity boundaries before simulation production changes.

Keep capability naming as part of every future design and closure review. When a
new artifact is introduced, ask what payment, fraud, security, data, or
operational truth it owns; never derive its durable name from delivery order.
For every future rotatable pseudonym, draw the retention-window and nested-key
cross-product; for every compensation path, force resource reuse before cleanup;
for every idempotent authenticated API, cross replay with another actor.
