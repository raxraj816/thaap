# Daily Deep Dive: 2026-07-27

## 1. System Goal

Chapter 40 turns an ingested chargeback into an operable dispute workflow without inventing network truth. A risk manager appends safe evidence facts, server-side rules decide readiness, that manager submits one exact version, and only a trusted simulator can record `WON` or `LOST`. VIEWER and ANALYST roles can inspect tenant workflows but cannot mutate them.

## 2. Plain-English Design Brief

Think of the workflow row as a table of contents and the version/event rows as the signed pages. The table of contents may advance, but old pages cannot be edited. Without this split, a later evidence edit could silently change what THAAP claims was submitted. Real document upload, network representment, and settlement reversal are intentionally excluded because their trust and storage boundaries do not yet exist.

## 3. Code Map

- `DisputeWorkflowInitializer` derives the deadline during chargeback creation.

## 4. Request/Data Flow

1. Chargeback creation commits money/fraud truth and initializes one DRAFT workflow from `receivedAt + catalogue.responseDays`.
2. An authenticated risk manager first locks and revalidates the live operator and credential, then locks that merchant's workflow and appends a closed, canonical evidence version plus digest.
3. The server derives missing requirement codes from the reason definition and updates the projection.
4. A manager locks the same row, verifies READY and the exact latest version, then binds it as submitted.
5. A separately authenticated synthetic runner appends one deduplicated terminal outcome; events and audits retain the transition.

## 5. Database Invariants

- Composite foreign keys prevent cross-merchant workflow, evidence, actor, and outcome linkage.
- Unique `(merchant_id, chargeback_id)`, evidence version number, external outcome key, and workflow outcome keys enforce one legal lineage.
- Evidence/outcome/event/catalogue triggers reject UPDATE and DELETE; the projection trigger permits only legal transitions with `projection_version + 1`.
- The due index makes scheduler work bounded; exact timestamp checks preserve occurred/received ordering.

## 6. Security And Privacy Invariants

No arbitrary evidence text is accepted. Verification results come from immutable authorization truth; the operator supplies only delivery, communication, and device-continuity booleans. Credentials, event keys, tenant IDs, evidence values, and digests are excluded from metric tags and safe API errors.

## 7. Fraud/ML Relevance

The submitted evidence version and synthetic outcome form explainable training/operations lineage. They can later support dispute-win reporting, feature engineering, and policy feedback without contaminating genuine network labels. No model update is performed in this chapter.

## 14. Chapter 41 System Goal

Chapter 41 gives a merchant developer a believable way to exercise THAAP's
payment-risk loop without adding a second, privileged payment implementation.
The console or executable client performs ordinary customer, payment-method,
intent, and confirm calls. A separately authenticated scenario API supplies a

## 15. Scenario Mental Model

A scenario run is a tamper-evident checklist, not a background job. The client
is the pair of hands doing each public API operation; the server is the
inspector that verifies the resulting resource before checking off a step. If
the client dies, a later worker can resume from the durable unchecked step. A
lease epoch is a fencing token: once PostgreSQL grants a newer epoch, an old
worker cannot report success even if it wakes up with stale credentials.

## 22. Verification And Generation Mental Model

Verification is a signed challenge-response, not a generic health check. THAAP
creates a short-lived random challenge, stores only its digest, sends it in a
canonical payload signed by the endpoint's current secret generation, and
accepts only the exact token returned in one final successful response field.
URL change, secret rotation, disable, expiry, or a newer challenge fences the
old response even if the network call eventually returns.

A delivery generation is an operational recovery epoch. Automatic retries share
one generation-local budget. Manual redelivery appends the actor and reason,
increments the generation, and starts that local budget at zero while retaining
the global attempt count and exact immutable event identity.

A lease token and an idempotency key answer different questions. A lease says
which worker may advance a run at one epoch; transport idempotency says whether

## 32. Post-Closure Review Remediation

The second Staff-level review found ten genuine truth gaps. The five backend
monitoring, simulation, dispute, note, and scenario gaps are described first;
webhook lifecycle/authorization and cockpit integration/resilience follow. None
was cosmetic. Each came from proving one nearby property and then generalizing
it across a boundary family with a different clock, identity, authorization
point, external side effect, or accountability obligation.

### Point-in-time truth includes association time

`ER-0064` showed that an incident can occur before `asOf` but become associated
with a payment only later. Event time answers when something happened;
`linked_at` answers when THAAP could first know that this evidence belonged to
this attempt. Enumeration summary and cohort queries now both require
`linked_at <= asOf`. The focused monitoring contract passes all seven tests and
proves replay before the link plus inclusion exactly at and after the link. The
inherited PostgreSQL contract also passes all seven tests on PostgreSQL 16.14,
closing `ER-0064`.

The prior review missed this because chargeback and fraud-label availability
tests were treated as representative of all late evidence. The durable lesson
is to inventory the availability column of every joined table, including link
tables, rather than borrowing another evidence family's proof.

### A counterfactual is original stack minus one family plus one candidate

`ER-0065` showed why an isolated candidate is not a production fraud decision.
The original decision may combine static rules, fraud lists, velocity,
merchant-policy thresholds, authored rules, and safety exceptions. A valid
simulation preserves that decision-time stack and replaces only the candidate
family:

- policy simulation replaces policy-threshold evidence but preserves authored
  rules;
- authored-rule simulation replaces every historical version with the same
  immutable `rule_code`, not merely one version UUID, while preserving policy
  and unrelated rules; and
- safety-exception simulation can suppress only historical evidence for its
  exact `sourceRuleVersionId`; it preserves nullable `effective_action`, cannot
  silence an active successor, and cannot invent a never-active source.

The focused H2 contract
`everyCandidateFamilyPreservesUnrelatedHistoricalControlEvidence` passes the
mixed-control, same-family replacement, retired-source/successor, historically
suppressed, and approved-never-active partitions. Independent review and all 8
inherited PostgreSQL tests pass because production query semantics—not an
isolated in-memory evaluation—own this claim.

### Authentication is a snapshot; authorization must survive until commit

`ER-0067` exposed a classic time-of-check/time-of-use race. A valid
`RiskOperatorContext` proves the credential passed request authentication; it
does not prove the actor remained enabled before the workflow mutation. Dispute
revision, submission, and completed-replay authorization now lock the live
operator and credential, verify current status and role, require RISK_MANAGER,
and only then lock the workflow. VIEWER and ANALYST retain read-only dispute
access.

`forcedOperatorDisableBeforeEvidenceRevisionRejectsInFlightAndFutureMutations`
forces disable to own the actor lock, observes the revision wait, and proves
zero evidence/event/audit writes after disable wins. The expanded 19-test
PostgreSQL contract passes disable-before-submit and completed revise/submit
replay-after-disable. The prior suite tested actors disabled before a request,
but never disable after authentication and before the resource lock.

### Privacy requires both non-disclosure and accountability

`ER-0069` found that note encryption and plaintext-sink scans were necessary but
not sufficient. Every authorized plaintext read now creates one
metadata-only `review_note.accessed` audit in the read transaction, recording
only total note count and returned-content count. Denied reads create no event;
redacted rows increase the total but not the content-return count; plaintext
never enters the audit.

The focused workspace contract passes all seven tests and proves manager `2/2`,
assigned-analyst post-redaction `2/1`, and zero events for denied reads. The
review miss came from testing only the negative privacy claim—where plaintext
must not appear—without testing the positive accountability event that must
appear.

### Tenant scope is not report ownership

`ER-0070` showed that a merchant-qualified query can still be wrong for a
run-owned report. A scenario report must traverse the target run's completed
`CONFIRM_PAYMENT_INTENT` step resources to its attempts; it cannot count every
attempt in the tenant. The focused developer-scenario contract passes all nine
tests and proves that unrelated runs before and after a target neither change
its one-attempt origin breakdown nor its canonical report digest.

The earlier demo used one merchant reference attempt and one scenario, so its
mixed tenant total looked like reconciliation rather than contamination. The
durable review rule is that every terminal aggregate needs an explicit
ownership path from report to source rows; `merchant_id` alone proves isolation,
not provenance.

### External I/O needs a final locked permit

`ER-0066` showed why a database precheck cannot authorize a later network send.
A terminal challenge could win after the caller's clock check while the caller
still signed and dispatched. Verification now signs the exact endpoint
generation, then acquires one short locked dispatch permit that revalidates the
challenge, endpoint, URL, secret generation, expiry, and supersession state and
records the dispatch lease. Only that permit allows transport I/O.

The H2 spy contract proves signing occurred, injects a terminal winner at the
permit boundary, and observes `dispatch_started_at IS NULL` plus zero transport
calls. The same deterministic contract exists in
`WebhookDeliveryPostgreSqlConcurrencyTests` and passes on PostgreSQL 16.14,
closing `ER-0066` at the actual lock boundary.

### Actor fencing and authorization prose are one boundary

`ER-0068` found the same authentication-snapshot race in webhook redelivery.
Execution and completed replay now lock and revalidate the live operator and
credential before endpoint and delivery state. The forced PostgreSQL
disable-versus-redelivery ordering passes with no new generation or external
work, so the finding is resolved.

`ER-0071` was not merely a documentation typo. Chapter-local service/tests had
granted ANALYST while the founder-confirmed phase matrix and cockpit required

### Browser safety includes routing and partial failure

`ER-0072` found that mocked fetch tests cannot prove a real Vite proxy. The
cockpit now proxies both webhook route families and tests the configuration.
`ER-0073` found that one optional dependency failure discarded every successful

## 34. Phase 5 Planning Goal

Phase 5 turns the completed transaction-local payment-risk product into a
durable internal data platform. Its success condition is not that Kafka runs.
Its success condition is that a committed payment or fraud fact can reach a
merchant-visible projection, survive duplicates and restarts, and rebuild from
immutable evidence without changing source truth.

The execution plan is deliberately ordered semantic-contract first:

```text
Chapter 44 event + transaction contract
  -> Chapters 45–46 domain producer families
  -> Chapter 47 Kafka transport
  -> Chapter 48 consumer/inbox substrate
  -> Chapter 49 analytics product
  -> Chapter 50 rebuild/activation
  -> Chapter 51 offline replay dataset
  -> Chapter 52 integrated closure
```

Starting with Kafka would harden transport decisions before THAAP knows which
facts, privacy rules, ordering roots, and compatibility commitments the
transport must preserve.

## 35. Dual-Write And Duplicate Mental Model

PostgreSQL and Kafka cannot share one normal atomic commit. Direct publication
therefore admits either a committed payment with no event or an event for a
rolled-back payment. The planned outbox stores domain state and immutable event
in one PostgreSQL transaction, then publishes after commit.

The outbox closes event loss but does not remove duplicates. Kafka may
acknowledge and the publisher may crash before recording success. Retrying the
same event is required. A consumer inbox keyed by consumer and event ID commits
with the projection effect, so redelivery converges without double-counting.

The honest promise is at-least-once transport plus one durable application
effect, not cross-system exactly once.

## 36. Event, Audit, And Webhook Boundaries

- Domain event: which committed fact internal consumers may project.
- Audit log: which live actor performed a sensitive action and why.
- Webhook event: which exact signed payload a merchant receiver may deduplicate.

Replaying a domain event cannot call the processor, rebuild ledger entries,
send a webhook, or invent an actor. Existing `AuditLog` and webhook
infrastructure are extended or referenced, not recreated under Phase 5 names.

## 37. Projection Generation Mental Model

A projection is a disposable, optimized view—not payment or fraud authority.
Rebuilding the active table in place exposes partial data. Phase 5 therefore
keeps generation A serving while generation B replays immutable events,
catches up, and proves event counts, stream coverage, row counts, content
digests, and business invariants. One locked pointer change activates B only
after reconciliation. A remains a bounded rollback target.

Freshness is product data. An analytics response must expose generation,
source cutoff, last applied occurrence/processing time, coverage, and traffic-
origin policy so “missing,” “stale,” and “zero” cannot collapse into one visual
state.

## 38. Phase 5 Design Tradeoffs

- PostgreSQL projections precede ClickHouse because scale evidence does not yet
  justify a second analytics store and reconciliation boundary.
- Versioned canonical JSON precedes Schema Registry because Phase 5 has one
  first-party Java producer/consumer; external compatibility remains unclaimed.
- One internal topic keyed by tenant-qualified domain stream preserves the
  useful per-stream order without fabricating global commit order.
- Repeated publication failure becomes durable `BLOCKED` work rather than
  event deletion; unrelated streams continue.
- A quarantined Kafka record is durably acknowledged without advancing its
  domain-stream position, allowing unrelated streams in the same partition to
  continue while successors from the affected stream remain held.
- Pre-Phase-5 history uses immutable, digest-bound projection bootstrap facts
  from an explicitly labelled source snapshot at a cutoff, not invented
  historical domain-event IDs and timestamps.
- The Phase 4.5 historical simulator remains the activation authority. Phase 5
  may supply an event-derived cohort only after exact point-in-time equivalence.

## 44. Founder-Confirmed Destination And Production-Validation Boundary

The founder confirmed that THAAP must become a real merchant-facing fraud/risk
platform that initially integrates with existing PSPs. This does not invalidate
V1. The deterministic simulator remains the safest place to learn payment
mechanics, prove hostile failure sequences, generate controlled scenarios, and
regress decisions without risking merchant traffic. The correction is that the
simulator is now explicitly a stage and permanent test environment, not the
definition of the finished product.

Four new immutable promises close the strategic gap:

- `VP-020` owns authenticated PSP integration, reconciliation, and source
  provenance.
- `VP-021` owns the hosted merchant lifecycle and risk control plane.
- `VP-022` forces real traffic to progress from `SHADOW` through separately
  approved advisory or bounded enforcement with safe fallback and kill switch.
- `VP-023` requires denominator-correct merchant outcome evidence and a
  governed feedback flywheel with explicit causal limitations.

Phase 9 remains the production-readiness gate. Phase 10 is separate because a
secure hosted system is not yet a useful customer product, and a working
adapter is not yet fraud-reduction evidence. Phase 10 closes only through a
real merchant path from PSP event to decision, analyst action, mature outcome,
reproducible impact report, and governed improvement candidate. A negative or
inconclusive pilot result must remain visible; it may close an experiment but
cannot be rewritten into product success.
