# Daily Deep Dive: 2026-06-26

This note is for end-to-end understanding of a Staff-level implementation slice.
It should make the code explainable, not merely documented.

## 1. System Goal

- We corrected the weekly public blog system so posts teach concepts directly
  instead of referencing the product, repo, source files, or implementation
  status.
- This matters because the founder wants public technical credibility through
  detailed essays on payment-risk systems, not private build summaries.
- The future capability is a repeatable weekly writing loop for Senior
  Staff-style educational posts with diagrams, invariants, failure modes,
  tradeoffs, and operational review questions.

## 2. Plain-English Design Brief

- Simplest mental model: each post teaches one public concept in depth.
- Without this correction, posts would sound like product updates or internal
  implementation notes.
- We chose to rewrite the blog workflow, template, backlog, checklist, seed
  draft, add an editorial rubric, and add a public-draft checker script.
- We then replaced the post template with a two-layer structure: private
  editorial brief plus public article draft.
- We intentionally deferred web publishing, visual styling, and platform choice.

## 3. Code Map

- `docs/blog/README.md` defines the public concept blog workflow.
- `docs/blog/POST_TEMPLATE.md` provides the public essay structure.
- `docs/blog/POST_TEMPLATE.md` separates private planning from public prose.
- `docs/blog/TOPIC_BACKLOG.md` lists concept-first post ideas.
- `docs/blog/WEEKLY_BLOG_CHECKLIST.md` gates public readiness.
- `docs/blog/EDITORIAL_RUBRIC.md` scores whether the article earns public
  attention and trust, not just whether it has sections.
- `docs/blog/drafts/2026-W25-why-fraud-systems-need-explainable-intelligence.md`
  is the rewritten first seed public draft.
- `scripts/blog-week-start.sh` creates weekly drafts.
- `scripts/blog-public-check.sh` scans drafts for blocked private/project-status
  terms.

## 4. Request/Data Flow

Describe the flow step by step:

1. Pick a public concept such as idempotency, audit replay, real-time scoring,
   rule engines, or explainable fraud intelligence.
2. Create a draft with `scripts/blog-week-start.sh YYYY-WNN short-slug`.
3. Fill the private editorial brief.
4. Write for a public reader: problem, first principles, diagram, walkthrough,
   invariants, failure modes, tradeoffs, and review questions.
5. Remove the private brief and template prompt text.
6. Run the checklist.
7. Score the draft with `docs/blog/EDITORIAL_RUBRIC.md`.
8. Run `scripts/blog-public-check.sh`.
9. Move the draft to `published/` only after it reads like a public technical
   essay.

## 5. Database Invariants

- No database schema changed.
- The documentation invariant is that published posts must not include private
  product names, repo paths, branches, commits, source files, or build status.
- If the invariant disappears, the public essay becomes private project
  narration rather than reusable technical education.

## 6. Security And Privacy Invariants

- No secrets or sensitive payment data were introduced.
- The public checker protects against accidental leakage of private project
  context.
- The writing template asks each post to explain privacy and security
  implications of the concept itself.

## 7. Fraud/ML Relevance

  evidence, and privacy-safe explanations.

## 9. Staff Engineer Review Notes

- Tradeoff: enforce public/private separation with a simple grep-based checker
  rather than a full publication pipeline.
- Risk reduced: accidental public articles that mention product internals or
  sound like weekly status updates.
- Additional risk reduced: drafts that look organized but are too generic for
  LinkedIn or Medium.
- Reversible: the Markdown drafts can later move to any publishing platform.
- Dangerous to overbuild now: CMS, SEO tooling, analytics, or full website work
  before the writing loop is proven.
