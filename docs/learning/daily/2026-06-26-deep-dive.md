## 1. System Goal

- We corrected the weekly public blog system so posts teach concepts directly
  instead of referencing the product, repo, source files, or implementation
  status.
- This matters because the founder wants public technical credibility through
  detailed essays on payment-risk systems, not private build summaries.
- The future capability is a repeatable weekly writing loop for Senior
  Staff-style educational posts with diagrams, invariants, failure modes,
  tradeoffs, and operational review questions.

## 2. Plain-English Design Brief

- Simplest mental model: each post teaches one public concept in depth.
- Without this correction, posts would sound like product updates or internal
  implementation notes.
- We chose to rewrite the blog workflow, template, backlog, checklist, seed
  draft, add an editorial rubric, and add a public-draft checker script.
- We then replaced the post template with a two-layer structure: private
  editorial brief plus public article draft.
- We intentionally deferred web publishing, visual styling, and platform choice.

# Chapter 15 Deep Dive: Capture With Balanced Ledger

## 1. System Goal

- We implemented the first real post-authorization money-truth chapter: capture
  with balanced ledger evidence.
- This matters because authorization only says funds may be captured. Capture
  changes the platform's accounting story and must not be represented by status
  alone.
- The future capability is refund, fee, dispute, payout, and analyst reporting
  built from append-only money movement records.

## 2. Plain-English Design Brief

- Simplest mental model: capture is valid only when the platform can write the
  accounting entries that explain it.
- Without this design, THAAP could show a `CAPTURED` payment while having no
  durable accounting proof of where the money went.
- We chose full capture only: debit `CUSTOMER_RECEIVABLE`, credit
  `MERCHANT_PAYABLE`, same amount and currency, same transaction group.
- We intentionally deferred partial capture, refund ledger groups, fee entries,
  disputes, reserves, and payout settlement.

## 3. Code Map

- `V5__add_ledger_entries.sql` creates append-only ledger storage with
  same-merchant PaymentIntent source integrity, allowed capture account/direction
  checks, and duplicate capture account protection.
- `ledger/LedgerEntry`, `LedgerAccount`, `LedgerDirection`, and
  `LedgerSourceType` model ledger rows.
- `ledger/LedgerService` writes and validates balanced capture groups.
- `ledger/LedgerEntryController` exposes safe bounded merchant-scoped ledger
  reads.
- `PaymentIntentController` now requires approved authorization before capture,
  writes ledger entries, changes state, creates webhook delivery records, and
  records capture audit truth in one idempotent mutation.
- `PaymentIntentCaptureLedgerContractTests` and
  `PaymentIntentCaptureLedgerRollbackTests` prove the main behavior and
  rollback boundaries.

## 4. Request/Data Flow

1. Merchant calls `POST /payment_intents/{id}/capture` with `X-Api-Key` and
   `Idempotency-Key`.
2. Tenant context resolves the merchant and idempotency reserves the mutation.
3. The PaymentIntent is loaded with a tenant-scoped pessimistic lock.
4. The controller requires status `REQUIRES_CAPTURE` and a tenant-scoped
   approved Authorization from an authorized PaymentAttempt.
5. `LedgerService.recordCapture` writes a balanced two-entry transaction group.
6. PaymentIntent moves to `CAPTURED`.
7. Webhook delivery records and a safe audit log are created.
8. Idempotency stores the response only if the whole mutation commits.

## 5. Database Invariants

- `ledger_entries` rows include `merchant_id`, `transaction_group_id`,
  `source_type`, `source_id`, `account`, `direction`, amount, currency, and
  creation time.
- For Chapter 15, capture ledger rows must reference a same-merchant
  PaymentIntent source.
- The schema allows only the two Chapter 15 capture account/direction pairs and
  blocks duplicate account rows for the same capture source.
- Capture ledger groups must balance: debits equal credits.
- Capture entries for this chapter use source type `PAYMENT_INTENT_CAPTURE`.
- `GET /ledger/entries` scopes reads by current merchant and bounds result size.
- If ledger persistence fails, capture state, webhook rows, audit rows, and
  idempotency completion roll back.

## 6. Security And Privacy Invariants

- No raw PAN, CVV, API keys, idempotency hashes, card fingerprints, or raw PII
  are written to ledger or capture audit payloads.
- Ledger rows are merchant financial history and must never be readable across
  tenant boundaries.
- Ledger reads are bounded because tenant isolation prevents cross-tenant leaks,
  while pagination prevents one tenant from accidentally or maliciously pulling
  unbounded financial history in one request.
- Capture audit payloads contain safe IDs and amounts that support
  reconstruction without exposing sensitive payment input.

## 7. Fraud/ML Relevance

- Fraud and analyst workflows now have post-authorization money truth: whether
  an approved payment was actually captured.
- Future fraud metrics such as fraud dollars captured, refund abuse, dispute
  loss, and false-positive cost need ledger-backed capture state.
- We avoided changing the original FraudDecision after capture; post-authorization
  signals must become separate labels, recommendations, or case events later.

## 8. Tests As Proof

- Migration tests prove V5, ledger indexes, source integrity, duplicate capture
  account protection, and allowed account/direction checks exist.
- Capture contract tests prove approved capture, balanced entries, replay,
  double-capture rejection, invalid declined/3DS states, tenant isolation, and
  bounded ledger reads.
- Rollback tests prove ledger persistence failure does not leave captured state,
  partial ledger rows, capture webhook truth, capture audit truth, or completed
  idempotency.
- Missing next Staff-level tests: refund ledger balancing, void/cancel
  accounting, and fee/dispute ledger groups when those chapters exist.

## 9. Staff Engineer Review Notes

- Tradeoff: no separate `captures` table yet. For this chapter, PaymentIntent
  captured state plus ledger transaction group is enough durable capture truth.
- Risk reduced: a payment cannot be marked captured unless accounting evidence
  is created in the same transaction, and the database rejects impossible
  capture ledger source truth.
- Reversible: a future `captures` table can reference the existing ledger
  transaction group without changing the ledger invariant.
- Dangerous to overbuild now: fees, reserves, partial capture, partial refunds,
  and payout settlement before the basic full-capture invariant is proven.
