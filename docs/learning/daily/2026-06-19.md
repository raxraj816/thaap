## 2. Payment Processing Concepts Learned

- Confirm is the bridge between a customer-visible payment container and the
  processor-facing authorization path.
- A PaymentAttempt should move into a processor-ready state before Chapter 11
  attaches real processor authorization results.
- Once confirm moves a PaymentIntent to `PROCESSING`, a new distinct confirm
  key should not create another attempt until a later processor outcome creates
  a retryable state.
- Teaching payment systems well means defining the domain object, the
  production invariant, the failure mode, and the test proof before expecting a
  new engineer to reason about the implementation.
- Authorization is the processor/issuer decision to reserve funds; it is not
  capture or settlement.
- Persisting processor truth is necessary because capture, refunds, disputes,
  fraud labels, analyst timelines, and ML datasets need more than a response
  string on the attempt.
- Retryable declines should reopen the PaymentIntent for another confirm
  attempt instead of making the payment terminal.

## 3. Fraud Detection Concepts Learned

- A fraud decision interface can shape the real-time path before durable fraud
  lineage exists.
- Persisting a thin `FraudDecision` too early would create misleading product
  truth because Chapter 12 still owns risk score, risk level, reason codes,
  latency, feature snapshots, and feature freshness proof.
- Processor declines are future fraud and card-testing signals, but Chapter 11
  still correctly avoids writing durable fraud lineage until Chapter 12 can
  attach feature snapshots and reason-code truth.

## 4. Security Concepts Learned

- The confirm plan preserves the existing tenant and payment-method ownership
  checks before adding any processor or fraud side effects.
- Logs for Chapter 10 should carry request IDs and trace-ready operation names
  without leaking card fingerprints, API keys, idempotency hashes, or merchant
  secrets.
- Chapter 11 preserves the tokenized simulator boundary: the processor adapter
  derives deterministic outcomes from stored safe metadata, not raw PAN.

## 5. Architecture / Design Notes

- Chapter 10 is now an orchestration bridge, not a thin fraud implementation.
- The successful confirm path should move the PaymentIntent from
  `REQUIRES_CONFIRMATION` to `PROCESSING` and the PaymentAttempt from
  `CREATED` to `READY_FOR_PROCESSOR`.
- Chapter 12 remains the owner of durable fraud lineage and feature freshness
  metadata.
- Chapter 11 remains the owner of real processor authorization and final
  authorization/decline mapping.
- The founder escalation warning is now part of the operating contract: win by
  moving fast toward a defensible payment-risk loop without creating false
  product truth.
- Chapter 11 makes `authorizations` the source of truth for processor outcomes;
  `payment_attempts.processor_authorization_id` is response correlation, not
  the full processor record.
- Unknown simulator cards default to approved so older local happy-path cards
  remain useful while the Chapter 11 catalog introduces deterministic edge
  cases.
- Confirm's all-or-nothing boundary comes from `IdempotencyService`, which runs
  the operation supplier and idempotency response storage inside one
  `TransactionTemplate`.
- Review hardening clarified the exact processor boundary: non-`ALLOW` fraud
  decisions must fail before processor authorization, and processor exceptions
  must roll the whole confirm operation back out of `PROCESSING`.
- Authorization now stores both requested and authorized amounts, with non-null
  3DS result, so later partial authorization and capture rules have the facts
  they need.
- Review follow-up fixed two Staff-level misses: authorizations now land in a
  forward-only Flyway `V2`, and non-approved simulator outcomes persist
  `authorized_amount = 0`.

## 7. Bugs, Surprises, Or Tradeoffs

- The existing Chapter 10 text left the target PaymentIntent status half-open:
  "`PROCESSING` or authorization-ready status agreed for Chapter 11." The plan
  now resolves that ambiguity before implementation.
- The current `fraud_decisions` table is intentionally too thin for the
  product vision. The implementation uses an interface boundary instead of
  writing that placeholder row.
- Moving the PaymentIntent to `PROCESSING` invalidated the old Chapter 9
  monotonic-success test for separate confirm keys. The Chapter 10 behavior is
  now one successful confirm, with replay for the same idempotency key and
  conflict for a different key while processing.
- The founder warning clarified the difference between disciplined deferral and
  over-cautious deferral. The former protects product truth; the latter loses
  momentum.
- The teaching standard needed one more explicit constraint: explain like the
  founder is a capable new intern, not like a domain expert who already knows
  the hidden assumptions.
- Automatic capture remains intentionally deferred even when the PaymentIntent
  uses `AUTOMATIC` capture method. Chapter 11 proves authorization; capture and
  ledger correctness need their own side-effect boundary.
- The simulator catalog uses `card_bin` + `card_last4` because raw card numbers
  are intentionally discarded at PaymentMethod creation.
- Review hardening changed that catalog to an explicit `card_bin:card_last4`
  key so the simulator-specific lookup cannot be confused with full-card-number
  matching.
- A controller-level `@Transactional` annotation on `confirmPaymentIntentOnce`
  would be misleading because that helper is invoked inside the same controller
  instance. The real transaction boundary is the existing idempotency service
  transaction template, proven by the processor-failure rollback test.
- Editing an already-applied Flyway migration is unsafe even when fresh-schema
  tests pass. Fresh H2 confidence is not the same as production upgrade safety.
- The existing local `thaap_payments` Docker volume has an older applied `V1`
  checksum than the current repo. That database needs a local reset or Flyway
  repair before normal startup, but a clean PostgreSQL database proves the
  current `V1 + V2` path works.
- Money fields need outcome-by-outcome assertions. Merely adding
  `requested_amount` and `authorized_amount` was not enough; declined and
  action-required outcomes must prove no funds were authorized.
