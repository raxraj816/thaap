# Daily Deep Dive: 2026-07-28

This note is for end-to-end understanding of a Staff-level implementation slice.
It should make the code explainable, not merely documented.

## 1. System Goal

- We built THAAP's durable event and analytics plane: 42 atomic domain facts,
  exact-byte Kafka delivery, an inbox-idempotent consumer, generation-aware
  payment/merchant projections, rebuild/reconciliation/activation, and an
  immutable point-in-time replay dataset.
- A fraud platform needs to answer both “what is true now?” and “what did the
  system know when it made this decision?” Source tables answer the first;
  immutable event/feature/control/label lineage makes the second reproducible.
- This closes the production risks of lost database/Kafka dual writes,
  duplicate money-like analytics effects, cross-tenant stream confusion,
  silently stale dashboards, non-reproducible model cohorts, and invasive
  projection repair.

## 2. Plain-English Design Brief

- The simplest mental model is “authoritative facts plus replaceable views.” A
  payment mutation and its event commit once in PostgreSQL. Kafka may deliver
  that fact more than once. The inbox ensures each projection generation sees
  one effect, while immutable events let a new view be rebuilt later.
- Without the outbox, a payment could commit while its Kafka send fails and
  disappear from analytics. Without exact byte identity, a duplicate ID could
  carry changed meaning. Without generation/cutoff evidence, a dashboard could
  mix old and new projection logic. Without availability-time labels, offline
  evaluation would train on future information.
- Phase 5 chooses one narrow, real product loop: payment/risk mutations produce
  42 closed facts, one six-partition topic delivers them, one consumer builds
  payment and merchant views, five APIs and the cockpit explain them, a shadow
  rebuild changes handler generations safely, and a dataset creates stable ML
  evidence.
- Model fitting/promotion, ClickHouse, arbitrary event download, arbitrary SQL,
  raw Kafka access, event editing, automated break-glass abandonment, and
  historical event fabrication are intentionally excluded. Those would either
  widen the trust boundary or claim lineage Phase 5 does not own.

## 3. Code Map

- `event/` owns the exact catalogue, envelope, JCS codec, stream head, immutable
  event, outbox row, and mandatory transaction writer.
- `PaymentDomainEventService` and `RiskOperationsEventProducer` map source-owned
  entities to closed allowlisted payloads at the mutation seam.
- `eventpublication/` owns due claiming, tenant/stream budgets, leases/fencing,
  exact Kafka bytes/key/headers, retry/block state, health, metrics, and audited

- `projection/` owns transport validation, inbox/quarantine, deterministic
  handlers, payment/merchant generation positions/checkpoints, readiness, and
  operator recovery.
- `analytics/` owns bounded tenant queries, cursor binding, freshness/coverage,
  five read endpoints, and safe DTOs. `apps/analyst-dashboard-ui` renders those
  states and keeps credentials in memory.
- `projection/rebuild/` owns cutoff manifests, Spring Batch execution, leased
  rebuild state, five-family reconciliation, activation, cancellation, and
  rollback.
- `replay/` owns immutable replay manifests, decision-time source reads,
  availability-bounded labels, chunk evidence, stable digests, compatibility,
  worker health, and two tenant APIs.
- V65–V79 build the event, publication, consumer, projection, rebuild, replay,
  label-cohort, and tenant-free transport-poison boundaries. PostgreSQL
  triggers protect immutable or monotonic history; H2 remains a fast structural

- The critical tests live beside those capability packages. Real PostgreSQL /
  Kafka suites certify locks, migrations, bytes, topology, retries, consumer
  commit/ack behavior, rebuild fences, and point-in-time results.

## 4. Request/Data Flow

Describe the flow step by step:

1. A merchant/risk request authenticates a live tenant actor and reserves its
   operation-scoped idempotency identity.
2. The domain service locks and validates the authoritative aggregate, invokes
   the processor/ledger/risk logic once where applicable, and persists the
   source mutation.
3. In that same transaction, the producer builds a closed payload and the
   writer locks the tenant-qualified stream head, allocates the next version,
   canonicalizes exact bytes, and inserts one immutable event plus one pending
   publication.
4. After commit, a fenced publisher claims due rows under batch/tenant/stream
   budgets and sends the stored bytes outside the database transaction. It
   appends safe attempt evidence and records acknowledged, retryable, unknown,
   permanent, blocked, or stale-fence outcome.
5. Spring Kafka delivers the record. The consumer recomputes byte identity,
   validates envelope/key/source agreement, locks payment then merchant active
   generations, reserves inbox identity, requires exact next stream version,
   applies both views, advances generation-local position/checkpoint evidence,
   and commits before manual acknowledgement.
6. Analytics resolve the authenticated tenant and active generation, execute
   bounded/indexed queries, bind cursors to tenant/generation/query shape, and
   return data plus explicit cutoff, coverage, origin, and freshness.
7. A data operator may build a hidden shadow generation from immutable cutoff
   membership. It catches up, reconciles at one watermark, and atomically
   switches only the active pointer; rollback selects a compatible retained
   generation.
8. A tenant risk manager may create an immutable dataset using the same cutoff,
   bounded cohort and label availability. A fenced worker resumes from keyset
   chunks and records compatibility only after exact overlap proof.

## 5. Database Invariants

- `(merchant, stream_type, stream_id, stream_version)` is unique and positive;
  a locked `event_stream_heads` row makes versions gap-free under concurrency.
- A domain event is immutable, has one tenant-qualified publication, exact lower
  hex payload/record digests, bounded bytes, microsecond time order, an exact
  type/version/stream catalogue, and no cross-tenant causation foreign key.
- Publication identity never changes. Lifecycle transitions, retry count,
  fencing token/lease, broker acknowledgement, blocked time, and append-only
  attempts are constrained. A stale finalizer cannot overwrite a new owner.
- Inbox identity is `(consumer_name,event_id)`, while altered or untrusted
  transport deliveries have separate immutable position/digest evidence. One
  invalid header can never reserve a victim tenant's inbox row.
- Projection rows, checkpoints, stream positions, and aggregate/cohort state
  are tenant and generation qualified. Positions/checkpoints never regress.
  Projection-definition ownership is explicit so a merchant generation cannot
  masquerade as a payment generation.
- Rebuild cutoff membership, events, reconciliation attempts, five family
  results, source watermark, activation/retained links, and source digests are
  immutable or monotonically fenced. Only the current complete reconciliation
  may activate.
- Dataset creator/tenant/cutoff/generation lineage, query/output digests,
  checkpoints, chunks, item digests, classification counts, and compatibility
  families are immutable or monotonic. A terminal dataset cannot be rewritten.
- Removing these constraints would turn an application bug or stale worker into
  false payment, fraud, or ML history—precisely where Java-only validation is
  weakest during concurrency and deployment skew.

## 6. Security And Privacy Invariants

- Merchant, risk-operator, platform-operator, bootstrap, scenario, webhook, and
  encryption secrets exist at API/config boundaries. Credentials are verified
  through hashes/HMAC keyrings; only safe prefixes and versioned identity
  digests persist where needed. The UI retains supplied credentials only in
  memory.
- Event schemas prohibit PAN/CVV, email/phone, API keys, secrets/passwords,
  tokens, idempotency keys, notes, unrestricted metadata, IP/device/session IDs,
  and raw RiskContext. Projections/datasets use explicit allowlists rather than
  copying payload JSON.
- Kafka failure, quarantine, metrics, logs, audit, APIs, runbooks, fixtures, and
  demos expose closed codes and safe classes—not payloads, exception messages,
  broker credentials, or high-cardinality tenant/event/resource labels.
- Tenant identity comes from the authenticated actor or cryptographically
  verified event/source agreement, never a request query parameter or untrusted
  Kafka header alone.
- This is payment-security defense in depth: least privilege, data minimization,
  strong tenant boundaries, immutable evidence, constant-time digest/credential
  comparison, and fail-closed behavior at every ambiguous identity boundary.

## 7. Fraud/ML Relevance

- Analysts can search a risky payment, see lifecycle/money/decision/review/label
  summaries, inspect merchant trends, and know exactly which generation/cutoff
  and origin policy produced them.
- Data/ML work can build a stable cohort from immutable decision-time feature
  values, controls, outcomes, and label availability, then reproduce the query
  and output digests after a restart.
- Explicit unlabeled, contradictory, superseded, unsupported, missing-feature,
  synthetic, corrupt, included, and excluded partitions stop silent sample
  selection bias.
- Exact compatibility evidence allows an approved event cohort to enter the
  existing governed rule-simulation boundary without silently changing its
  population or metric semantics.
- Model training, inference promotion, drift policy, feature registry expansion,
  and automated control activation remain later work because Phase 5 proves the
  data plane and replay contract, not a complete ML lifecycle.

## 8. Tests As Proof

- Canonical codec tests prove golden JCS bytes, exact envelope/schema fields,
  Unicode/null/number/timestamp/size partitions, nested/full digests, and the
  exact 42-type catalogue.
- Real PostgreSQL event tests prove fresh/retained migrations, immutability, one
  source/event/publication transaction, rollback, and forced actual-writer
  ordering with event/outbox postconditions.
- Producer tests prove all payment and risk seams, rollback, no forbidden data,
  stable lineage, and after-commit metrics rather than “method returned” metrics.
- Real Kafka/publication tests prove stored bytes/key/headers, fixed topology,
  acknowledgement/finalization ambiguity, `SKIP LOCKED`, broker outage recovery,
  source non-interference, and configuration-drift readiness.
- Consumer proof must cover exact duplicate versus altered bytes, missing/mutated
  headers, tenant-free poison, dependency rollback, manual ack after commit,
  concurrent duplicate, same-stream gaps, unrelated progress, recovery order,
  and active-generation races on real Kafka/PostgreSQL.
- Analytics/UI proof covers lifecycle/money totals, label cohorts, origin,
  cursor substitution, two tenants, indexes, exact freshness boundaries,
  no-zero missing states, memory-only credentials, loading/denied/dependency
  states, and production build output scans.
- Rebuild proof must force chunk crash/resume, stale lease takeover, live cutoff
  race, mismatch rejection, activate/rollback orderings, and exact source
  non-interference. Dataset proof must force before/exact/after labels, restart,
  digest stability, mixed classifications, tenant isolation, and exact
  simulation overlap.
- Happy-path API checks alone certify none of the concurrency, migration,
  broker, browser, or point-in-time claims. The final Staff question is always:
  “Did this test run at the real enforcement boundary and force both orders?”

## 9. Staff Engineer Review Notes

- We accept at-least-once transport and make its duplicate consequences
  harmless. This is simpler and more honest than distributed exactly-once
  claims across PostgreSQL, Kafka, and payment processors.
- We reduced loss, duplication, stale-data, tenant-substitution, future-label,
  stale-worker, and invasive-repair risk at the boundaries where they become
  production incidents.
- Projections, generations, handler versions, origin policies, feature/query
  digests, and datasets remain reversible or comparable. Source facts and
  audit history intentionally do not.
- It would be dangerous to add arbitrary payload tooling, raw topic/SQL access,
  auto-abandon poison, automatic source backfill, model training/promotion, or
  ClickHouse before THAAP has the governance and operational proof those
  boundaries require.

## 10. Explain-Back Questions

Answer these without looking at the code:

1. It made committed payment/fraud facts durable, deliverable, explainable,
   rebuildable, and usable as point-in-time evaluation evidence.
2. It separates one-time source mutation from at-least-once fact delivery and
   makes all derived state generation/cutoff/digest qualified.
3. It reduces lost facts, duplicate projection effects, cross-tenant poisoning,
   false freshness, unsafe rebuild activation, and future-data leakage.
4. It defers arbitrary tooling and ML promotion because those require a wider
   security/governance boundary than the proven data plane.
5. Exact-byte tests, forced PostgreSQL/Kafka interleavings, fresh/retained
   migrations, source non-interference, tenant/privacy partitions, browser
   states, rebuild races, and point-in-time replay equivalence prove them.
6. “PostgreSQL owns immutable business facts, Kafka provides at-least-once
   delivery, inboxes provide one projection effect, generations make read models
   replaceable, and cutoff/availability/digest evidence makes analytics and ML
   claims reproducible without ever replaying payment commands.”

## 13. Interview Narrative

Practice saying this out loud:

- The tradeoff I made was accepting duplicate delivery while prohibiting
  duplicate business mutation and projection effect.
- The invariant I enforced was exact immutable fact identity from source commit
  through Kafka, inbox, generation, analytics, rebuild, and dataset lineage.
- The production risk I reduced was losing, changing, duplicating, leaking, or
  mis-timing payment/fraud evidence under failure and concurrency.
- I deferred arbitrary data access and model promotion because Phase 5 owns a
  safe reproducible data plane, not an unrestricted data/ML control plane.
- The tests prove the claim at PostgreSQL, Kafka, browser, migration, and
  point-in-time boundaries with forced failures and durable postconditions.
