# Daily Deep Dive: 2026-06-09

This note is for end-to-end understanding of a Staff-level implementation slice.
It should make the code explainable, not merely documented.

## 1. System Goal

Chapter 6 makes `POST /payment_intents` production-shaped enough to be a safe base
for later confirm, authorization, fraud, and ledger work.

In payment terms, this slice creates the customer-visible payment container. It
does not move money. It records that a merchant intends to collect a specific
amount from one of its own customers, under a stable object ID that later
attempts and decisions can reference.

The production risk reduced here is duplicate or cross-tenant object creation.
If retries create multiple payment containers, merchants lose trust. If one
merchant can attach another merchant's customer to a PaymentIntent, tenant
isolation is broken before fraud scoring even begins.

## 2. Plain-English Design Brief

The simplest model is:

1. Authenticate the merchant through `X-Api-Key`.
2. Require an `Idempotency-Key`.
3. Validate the create request.
4. Prove the customer belongs to that merchant.
5. Create one PaymentIntent in `REQUIRES_CONFIRMATION`.
6. Create webhook delivery intent for active merchant endpoints.
7. Store and replay the response for safe retries.

Without this design, a network retry could create duplicate PaymentIntents or a
client could point at another merchant's customer ID. Both failures corrupt the
payment lifecycle and future fraud labels.

We built the create boundary and test proof. We intentionally deferred confirm,
PaymentAttempt creation, fraud decisions, processor authorization, ledgering,
and idempotency race hardening because those are separate side-effect
boundaries in the master plan.

## 3. Code Map

- `PaymentIntentController` owns the HTTP contract, validation annotations,
  tenant-scoped customer check, PaymentIntent creation, and webhook delivery
  creation call.
- `PaymentIntent` owns the domain state: ID, merchant, customer, amount,
  uppercase currency, capture method, status, and timestamps.
- `IdempotencyService` owns required-key enforcement, request hashing,
  merchant-scoped replay, changed-body conflict detection, and stored response
  replay.
- `WebhookDeliveryService` creates `payment_intent.created` delivery rows for
  active merchant endpoints.
- `PaymentIntentCreateContractTests` proves the Chapter 6 contract directly.

The tables involved are `payment_intents`, `idempotency_records`,
`customers`, `webhook_endpoints`, and `webhook_deliveries`.

## 4. Request/Data Flow

1. `POST /payment_intents` enters `PaymentIntentController`.
2. `MerchantContext` resolves the tenant from `X-Api-Key`.
3. Bean validation checks `customerId`, positive `amount`, and three-letter
   `currency`.
4. `IdempotencyService.execute` rejects a missing key, computes the internal
   request hash, checks existing records by `(merchant_id, key)`, and either
   replays, conflicts, or runs the create supplier.
5. `CustomerRepository.existsByIdAndMerchantId` proves the customer belongs to
   the merchant.
6. `PaymentIntentRepository.save` persists the new object with uppercase
   currency and status `REQUIRES_CONFIRMATION`.
7. `WebhookDeliveryService.createDeliveries` writes
   `payment_intent.created` delivery records for active endpoints.
8. The idempotency record stores the response body and HTTP status for replay.
9. The API returns the public PaymentIntent response.

## 5. Database Invariants

- `payment_intents.merchant_id` is required and references `merchants`.
- `(merchant_id, id)` is unique for tenant-scoped object addressing.
- `(merchant_id, customer_id)` references `customers(merchant_id, id)`, so a
  PaymentIntent cannot point to another merchant's customer.
- `idempotency_records` are unique by `(merchant_id, idempotency_key)`.
- `webhook_deliveries` reference webhook endpoints by `(merchant_id,
  webhook_endpoint_id)`, preventing cross-merchant delivery rows.
- Hot lookup indexes exist for merchant, customer, and idempotency access.

If the tenant-scoped foreign keys disappeared, application bugs could silently
create cross-merchant payment lineage. If the idempotency unique key
disappeared, retries could diverge into duplicate objects.

## 6. Security And Privacy Invariants

The request contains a customer ID, amount, currency, optional capture method,
`X-Api-Key`, and `Idempotency-Key`. The API key is authenticated by hash/prefix
storage from prior days. The idempotency request hash is internal, keyed through
`SensitiveValueHasher`, and not returned.

The response returns public PaymentIntent state only. It does not return
idempotency hashes, stored response bodies, API-key hashes, webhook signing
secret hashes, customer PII hashes, or card fingerprints.

The payment-security principle is least exposure plus tenant isolation: the
merchant can see its payment container, not internal controls or another
merchant's graph.

## 7. Fraud/ML Relevance

PaymentIntent create provides stable context for future PaymentAttempts,
fraud decisions, feature snapshots, review cases, and processor outcomes. It
also establishes customer linkage, amount, currency, and capture method as
payment facts that later features can reference.

We avoided adding fraud rules, model scores, feature snapshots, graph signals,
and analyst explanations because no PaymentAttempt exists yet. Scoring a
PaymentIntent directly would collapse the planned distinction between payment
container and scoring/audit unit.

## 8. Tests As Proof

`PaymentIntentCreateContractTests` proves:

- successful create returns the public response and persists normalized state
- `Idempotency-Key` is required and errors use the standard shape
- replay returns the original response
- replay does not create duplicate PaymentIntent or webhook delivery rows
- changed-body reuse returns `409`
- invalid request fields return validation errors
- missing `captureMethod` defaults to `AUTOMATIC`
- another merchant's customer is rejected

Existing migration tests also prove the schema-level tenant constraints and
indexes exist. Existing tenant tests still cover broad cross-merchant payment
read and mutation behavior.

The missing test a Staff engineer would ask for next is a concurrent duplicate
idempotency-key race test. That belongs to Chapter 8, where the master plan calls
for atomic duplicate-key race handling.

## 9. Staff Engineer Review Notes

The tradeoff was to harden a narrow object-creation boundary without pulling in
confirm or authorization behavior. That keeps each side effect auditable:
creation creates a container, confirm creates an attempt, fraud creates a
decision, and processor authorization creates a result.

The risk reduced was accidental duplicate or cross-tenant PaymentIntent
creation. The design stays reversible because no extra fraud, ML, ledger, or
processor schema was added.

It would be dangerous to overbuild by adding synthetic fraud scores here. The
platform needs lineage before intelligence; otherwise explanations become
storytelling instead of evidence.

Practice saying this out loud:

- The tradeoff I made was keeping Chapter 6 limited to object creation.

  PaymentIntent per idempotent create request for its own customer.

  cross-tenant object linkage.
