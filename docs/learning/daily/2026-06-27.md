## 2. Payment Processing Concepts Learned

- A verification artifact is trustworthy only when invariant violations make
  the run fail. Reporting false ledger truth as a boolean is weaker than
  rejecting the run.
- Requested amount, authorized amount, authorization status, and network status
  are separate claims and should be verified independently.
- Authorization says funds may be reserved; capture says the merchant finalized
  the charge; void says an uncaptured authorization must no longer be captured.
  They are separate lifecycle facts and must not overwrite one another.
- Capture method is executable product behavior, not decorative request
  metadata: `AUTOMATIC` and `MANUAL` must end an approved confirm differently.
- Refund is a later append-only money event, not deletion or mutation of the
  original authorization/capture history.
- `CAPTURED` status alone is insufficient refund eligibility; authorization and
  the balanced capture ledger group are the evidence that money truth exists to
  reverse.

## 3. Fraud Detection Concepts Learned

- A scenario is not fraud lineage merely because it has a decision ID. The
  decision and feature snapshot must both point to the same PaymentAttempt.
- Local `syntheticRunId` metadata supports debugging, but it is not a trusted
  training-data classification because merchants control PaymentIntent
  metadata.
- A post-decision cancel or void must not rewrite the original FraudDecision.
  Later analyst/ML workflows need to distinguish decision-time truth from a
  later payment operation.
- Refund likewise preserves the original FraudDecision and FeatureSnapshot;
  future labels must treat refund as an outcome signal, not retroactive
  decision-time fraud truth.

## 4. Security Concepts Learned

- Secrets passed as command arguments may be visible through process inspection
  or command tracing. Environment lookup avoids that exposure path.
- A local-only generator needs an enforced loopback boundary, not only
  documentation saying it is local.
- Composite foreign keys on authorization voids prevent a same-tenant mix-up
  from linking the authorization for one PaymentAttempt to another
  PaymentIntent; tenant filtering alone would not prove object lineage.
- Refund and ledger composite keys prove the Refund, PaymentIntent,
  PaymentAttempt, and Authorization belong to one tenant-bound object chain.

## 5. Architecture / Design Notes

- Merchant-facing authorization evidence now returns processor-neutral fields;
  the internal simulator outcome remains durable but is not a public contract.
- Run identity is unique even for concurrent same-seed runs, is attached to
  generated PaymentIntents, and names an atomic summary artifact.
- Authoritative synthetic-origin classification is intentionally not inferred
  from merchant metadata.
- Automatic capture reuses the Chapter 15 capture primitive inside confirm so
  manual and automatic paths cannot drift in ledger, webhook, or audit behavior.
- V6 converts legacy approved automatic rows waiting in `REQUIRES_CAPTURE`;
  forward-only V7 completes the compatibility boundary for every other
  non-terminal automatic row that could still progress toward capture. This
  preserves the old explicit-capture contract for existing confirms, retries,
  action flows, processing recovery, and approved payments instead of moving
  money as a deployment side effect. Terminal rows remain untouched as
  historical truth.
- `Authorization.status` remains `APPROVED` after void. The new void row is the
  append-only later fact and the authorization read exposes both.
- Refund ledger rows use the Refund as source while retaining the original
  PaymentIntent ID. Capture and refund transaction groups remain separately
  balanced and queryable.
- V8 refuses legacy thin-refund rows instead of inventing missing identifiers,
  authorization lineage, or ledger evidence during deployment.

## 7. Bugs, Surprises, Or Tradeoffs

- The prior phone suffix used hexadecimal characters, producing values such as
  `+1555016c49`; decimal derivation now creates valid `+1` E.164-shaped values.
- Timestamp-only run IDs could collide within one second. The run ID now combines
  microseconds, seed digest, and random entropy.
- Atomic output prevents partial summary files, but interrupted multi-request
  generation is not resumable yet. That debt belongs to the future generator
  reliability/volume slice before scheduled, high-volume, or automatically
  retried runs.
- Existing tests relied on the old accidental behavior where default
  `AUTOMATIC` meant "wait for manual capture." Tests whose subject is manual
  authorization now request `MANUAL` explicitly; Chapter 17 tests own the new
  automatic behavior.
- `RECORDED` void status deliberately means local simulator invalidation, not a
  claim that a real network reversal succeeded.
- `RECORDED` Refund status uses the same honesty rule: THAAP recorded the local
  reversal but did not claim an external acquirer completed a refund.
- The V8 migration guard intentionally makes a local database with legacy thin
  refunds reset or remediate explicitly; silent synthetic backfill would create
  false accounting evidence.
