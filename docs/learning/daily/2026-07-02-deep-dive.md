# Daily Deep Dive: 2026-07-02

## 1. System Goal

This recovery makes Chapter 19's final merge claim true at five overlooked
boundaries: HTTP request-target representation, legacy migration input
validation, executable readiness behavior, merchant-consumer deduplication,
and worker-disabled observability.

These matter in a payment-risk platform because an event must reach the exact
merchant route, historical rows must not become invented lineage, and a release
gate must actually execute the proof it advertises.

## 2. Plain-English Design Brief

The mental model is:

1. A Java `URI` may contain Unicode characters.
2. HTTP/1.1 request lines are ASCII wire representations.
3. Converting by replacement changes the destination; converting through the
   URI ASCII form preserves meaning with percent escapes.
4. A migration must validate every legacy value it needs before changing schema.
5. A readiness flag is only trustworthy if its behavior test observes the
   commands it promises to run.
6. A parsed event ID is only a deduplication candidate; a replay-safe consumer
   must atomically persist it with the business effect before acknowledgement.
7. Disabling side effects must not disable the operational signal that explains
   the resulting backlog.

No new webhook product surface was added. Existing secret-rotation grace,
fairness, and endpoint-creation idempotency deferrals remain under `TD-0003`
through `TD-0005`.

## 4. Request/Data Flow

1. A merchant-configured endpoint URL is persisted.
2. Target policy validates scheme, host, DNS answers, and address safety.
3. Transport calls `URI.toASCIIString()` and extracts its raw ASCII path/query.
4. The exact ASCII request line, original Host identity, signatures, and payload
   bytes are written to the pinned address.
5. Response grammar and final acknowledgement are validated before durable
   delivery finalization.

For the merchant consumer:

1. Verify the timestamp and exact-body HMAC before parsing.
2. Parse the signed body ID and require header agreement.
3. Insert event ID plus payload hash in the same durable transaction as the
   representative business effect.
4. Return success only after commit.
5. On crash/restart or concurrent redelivery, acknowledge matching durable
   state without applying the effect again; reject changed bytes under one ID.

For migration:

1. Flyway enters V9 against V8 state.
2. V9 rejects unsupported execution evidence.
3. V9 rejects event types outside the five canonical values.
4. Only then may V9 create tables, columns, subscriptions, and event lineage.

## 5. Database Invariants

- Unknown V8 event types never reach schema creation or payload backfill.
- A rejected migration leaves `webhook_events` absent and does not add
  `webhook_endpoints.operational_status`.
- Canonical event/resource mapping remains the only lineage V9 can serialize.
- The existing composite tenant and event/delivery/attempt constraints remain
  unchanged.
- The reference consumer's event ID is a SQLite primary key and the stored
  payload hash prevents a conflicting message from masquerading as a duplicate.

## 6. Security And Privacy Invariants

- Unicode route characters cannot be replaced with `?` and redirect a signed
  callback to another handler on the same authority.
- Existing percent escapes remain unchanged, preventing double-encoding.
- Host, TLS identity, address pinning, payload signing, secret encryption, and
  sensitive-data boundaries are unchanged.
- Consumer deduplication happens only after authentication, so an unsigned
  correlation header cannot reserve a deduplication key.

## 7. Fraud/ML Relevance

Reliable event routing is the integration bridge from payment and fraud truth
to merchant automation and future analyst feedback. This change preserves that
bridge without adding new model features or pretending that unsupported legacy
event types have known resource semantics.

## 9. Staff Engineer Review Notes

The tradeoff is retaining the narrow custom socket transport while expanding
its proof surface to the request line. The code change is small because the JDK
already owns correct URI ASCII serialization.

The migration guard deliberately rejects rather than guesses. An unknown legacy
event cannot safely choose a resource type, payload contract, or merchant
meaning.

Readiness now optimizes for truth over speed: non-trivial work always pays the
full test cost.

SQLite is intentionally fixture-local, not THAAP server infrastructure. It
demonstrates the merchant transaction shape with a mature embedded database:
durable uniqueness and the representative effect share one commit. Real
merchants should use the equivalent transaction in their own datastore.

The worker-disabled fix deliberately reuses the same database count as enabled
processing. It changes observation only; the scheduler still cannot claim or
send while the kill switch is off.

## 14. Chapter 20 Phase 2 Closure Addendum

### System goal

Chapter 20 turns the existing processor fixture behavior into one immutable,
documented, executable contract and uses that contract to close the complete
Phase 2 simulator boundary. The goal is not more payment surface area. It is
proof that processor, lifecycle, accounting, fraud lineage, audit, and webhook
truth agree before Phase 3 begins changing fraud decisions.

### First-principles model

There are two independent decisions during confirm:

1. THAAP decides whether fraud policy allows processor execution.
2. The processor or issuer decides whether authorization succeeds.

The current fraud engine always records `ALLOW` / `RULES_NOT_ENABLED`. A
processor response such as `SUSPECTED_FRAUD` is downstream network evidence; it
must not be rewritten into a THAAP `BLOCK`. Phase 3 will activate real
fraud-policy actions while retaining this separation.

### Design

- `SimulatorProcessorCatalog` owns eight mapped BIN-plus-last4 fixtures and one
  explicit unknown-card default.
- `SimulatorProcessorAdapter` converts the selected immutable outcome into a
  new authorization reference and amount truth.
- The public API contract does not change.
- The Chapter 20 runner submits simulator-only card fixtures at the transient
  tokenization boundary, then records only safe fixture labels and IDs.
- Read-only PostgreSQL inspection supplies audit proof because audit logs are
  intentionally not exposed as a merchant API.

### Phase 2 invariants

- Approved automatic capture cannot exist without balanced capture entries.
- Approved manual authorization remains captureable or voidable, never both.
- Decline and 3DS-required authorize zero and create no capture ledger truth.
- Full refund requires capture evidence and exactly reverses its account
  directions.
- FraudDecision and FeatureSnapshot remain immutable across processor, money,
  and webhook outcomes.
- Webhook failure and retry cannot mutate originating payment or ledger truth.
- Every boundary remains tenant scoped and idempotent.

## 15. Chapter 20 Redirect-Boundary Recovery

### Escaped finding

The post-closure merge review reproduced a P1 credential-boundary failure.
`require_loopback_origin` validated the initial API URL, but Python's default
HTTP redirect handler created a follow-up request and retained custom
`X-Api-Key` and `X-Admin-Bootstrap-Token` headers. A loopback response could
therefore redirect those credentials to another origin.

This is `ER-0021`, category `MISSING_FAILURE_SEQUENCE`. The product promise was
frozen and the dossier already recommended merge, so the finding cannot be
relabelled as pre-closure review.

### First-principles model

An origin restriction has two separate questions:

1. Where does the caller ask the client to connect?
2. Where can protocol behavior cause the client to connect next?

Validating only the first answer leaves redirects outside the security model.
Authentication headers are capabilities: whoever receives them can act with
their authority. The safe local proof policy is therefore simpler than trying
to classify redirect destinations—reject every redirect before constructing a
second request.

### Implementation and proof

- `ApiClient` uses a dedicated `RejectRedirectHandler`.
- Every redirect raises `DemoFailure` before a follow-up request is created.
- A real source server returns 301, 302, 303, 307, and 308 to a credential-
  bearing POST.
- A separate target server records all requests and proves it receives zero
  across every redirect partition.
- A fresh PostgreSQL V1-to-V9 runtime demo then proves the hardened client still
  completes all nine legitimate public-API paths and emits reconciled
  owner-only evidence.
- The Chapter 20 security matrix, dossier, escaped register, service/script
  documentation, and learning trail now describe the effective-destination
  boundary.

### Design-review explanation

The defense is intentionally fail-closed. Chapter 20 does not need redirect
convenience, so same-origin and cross-origin redirects share one prohibited
class. This removes header-retention, method-rewrite, body-forwarding, and
redirect-chain ambiguity from the demo credential boundary.
