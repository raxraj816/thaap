## 2. Payment Processing Concepts Learned

- A Redis observation is fraud evidence, not payment truth. Processor and ledger
  work begins only after the complete action set has been aggregated.
- A negative list is never an ALLOW override. It can only add BLOCK, REVIEW, or
  REQUEST_3DS, so a lower-severity entry cannot weaken a stronger base rule.
- A merchant policy is another negative decision candidate, not permission to
  bypass platform safety. Approval establishes governance truth; only activation
  changes the configuration observed by future confirms.

## 3. Fraud Detection Concepts Learned

- Velocity counts prior logical attempts, excluding the current stable attempt
  member. This makes first execution, retry, and rollback recovery explainable.
- Fraud-list evaluation stores both matched and non-matched active-list evidence,
  preserving which immutable version was consulted at decision time.
- List deactivation is append-only lifecycle truth; it changes future decisions
  without rewriting historical entries or evaluations.
- Policy evaluation stores every matched and non-matched threshold with its exact
  typed operand and feature value. This makes a past decision reproducible after
  newer policy versions activate or retire.

## 4. Security Concepts Learned

- Redis and list identity storage uses purpose-separated HMACs. Raw PAN, email,
  IP, device, session, and customer identity never appears in Redis keys or list
  rows. BIN and country remain canonical because they are validated control
  categories, not unique customer secrets.
- Composite tenant foreign keys bind lists, versions, entries, lifecycle events,
  decisions, attempts, operators, and traffic origin. Cross-tenant substitution
  is rejected even through direct SQL.
- Profile/policy creator and approver must be distinct active same-tenant
  RISK_MANAGER operators, revalidated while the configuration lock is held.

## 5. Architecture / Design Notes

- PostgreSQL remains authoritative for list configuration and decision lineage;
  Redis is bounded ephemeral coordination only.
- List mutation locks the merchant before the operator and list, serializing the
  per-tenant 64-list/1,000-entry bounds and lifecycle transitions.
- Confirm now takes a shared merchant risk-control lock while list mutations take
  the exclusive form. Concurrent confirms still coexist, but a decision cannot
  straddle a committed lifecycle transition.
- Email-domain correlation required a new purpose-specific customer digest.
  Existing retained customers remain null because reconstructing a domain from a
  one-way email digest would violate both mathematics and privacy.
- Confirm takes the existing shared merchant risk-control lock; policy activation
  takes the exclusive form. Therefore a decision sees either the old committed
  configuration or the new committed configuration, never mixed bytes.

  label rolled-back work as success. Emission now occurs after completion with
  an exact `transaction=committed|rolled_back` tag.

  preview attempted a locking read inside a read-only transaction. Preview now
  uses a tenant-qualified non-locking read, while lifecycle mutations retain
  their locking path. The defect was found and fixed before closure.
