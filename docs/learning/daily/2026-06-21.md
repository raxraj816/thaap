## 2. Payment Processing Concepts Learned

- Confirm is now both a payment lifecycle bridge and a fraud-lineage boundary.
- Processor authorization should happen only after the fraud decision is known
  and durably attached to the attempt.
- Idempotent replay must return the same attempt response without duplicating
  fraud decisions, feature snapshots, authorizations, or webhook deliveries.
- Audit logs are operational history, not current payment state. They explain
  how a confirm reached its final status.

## 3. Fraud Detection Concepts Learned

- A fraud decision is not complete unless it records what was decided, why, how
  long it took, and what feature facts existed at decision time.
- Honest stub lineage is better than fake intelligence: `RULES_NOT_ENABLED` and
  nullable `modelVersion` are truthful.
- FeatureSnapshot is the bridge between real-time decisions and future offline
  replay, rules simulation, and ML training.

## 4. Security Concepts Learned

- Feature payloads must use safe decision-time values only.
- Chapter 12 stores BIN and last4 but not raw PAN, CVV, raw PII, API keys,
  idempotency hashes, or merchant secrets.
- Fraud decision detail remains tenant-scoped through `X-Api-Key` resolution.
- Chapter 13 audit payloads include safe IDs, statuses, amounts, fraud reasons,
  and processor outcomes, but not raw PAN, CVV, raw PII, API keys, card
  fingerprints, merchant secrets, or idempotency hashes.
- Audit redaction belongs in `AuditLogService` because audit evidence is
  permanent and future callers should not be trusted to remember every
  forbidden field name.

## 5. Architecture / Design Notes

- `PaymentAttempt` remains the scoring and audit unit.
- `FraudDecision` owns action, score, reason, ruleset/model, timing, and freshness
  summary.
- `FeatureSnapshot` owns immutable feature values and freshness proof.
- The first `features_v1` set is intentionally small: amount, currency, capture
  method, attempt number, safe card metadata, and lineage IDs.
- Lineage IDs remain in `features_v1` for portable replay/export, while the
  dedicated columns remain canonical for database integrity.
- Legacy placeholder FraudDecision rows are marked with
  `legacy_placeholder_v1` and `MISSING` freshness instead of fake attempt
  lineage. They are not ML-valid training examples.
- Clarified the boundary between fraud reasons and processor outcomes:
  `RULES_NOT_ENABLED` is the Chapter 12 fraud decision reason, while simulator
  outcome codes remain on `Authorization` because they are produced after the
  fraud decision.
- Real rules, velocity counters, model scoring, review case creation, and ledger
  effects remain deferred to their owner chapters.
- Audit logs are no longer deferred for confirm. Capture/refund/ledger audit
  coverage remains deferred to the chapters that implement those side effects.
- Audit actor identity now separates tenant ownership from credential
  traceability: `merchant_id` remains the tenant boundary, while
  `actor_id` stores the API-key prefix for `MERCHANT_API_KEY` events.
- Confirm-specific audit payload construction now lives outside
  `PaymentIntentController`, keeping the controller focused on orchestration and
  making audit event shape reviewable in isolation.
- Feature snapshot size is no longer hard-coded at the controller boundary; it
  defaults to `16384` bytes and is configurable through
  `thaap.fraud.feature-snapshot.max-json-bytes`.
- Added Micrometer counters for audit writes and feature snapshot guard errors
  so production can observe when evidence creation or snapshot storage safety is
  failing.
- Chapter 13 intentionally keeps audit persistence inside the confirm
  idempotency transaction. For the simulator, audit evidence is part of local
  payment-risk truth; before a real external processor is integrated, this
  boundary must be revisited with an outbox/reconciliation design.

## 7. Bugs, Surprises, Or Tradeoffs

- The old tenant-isolation test manually inserted placeholder FraudDecision rows.
  Chapter 12 replaced that with real confirm-generated decisions because
  decisions now require PaymentAttempt lineage.
- Adding a foreign key from PaymentAttempt back to FraudDecision would create a
  circular delete path in tests. The durable ownership direction is
  FraudDecision -> PaymentAttempt; `payment_attempts.fraud_decision_id` remains
  the public correlation pointer.
- The stub score is `0.00` and risk level is `LOW`; this is intentionally modest
  because no real rules or model have run.
- The V3 migration is now upgrade-safe for long-lived dev databases with old
  placeholder decisions, but it is not a full production zero-downtime migration
  strategy. That belongs with deployment mechanics and live data contracts.
- Verification tools can fail for infrastructure-version reasons even when the
  underlying service is healthy. The correct Staff move was to test Docker
  directly, isolate Testcontainers as the failing boundary, and pin the
  dependency version that restores the production-database proof.
- Request IDs and idempotency keys must stay separate. A test briefly used the
  idempotency key as part of `X-Request-Id`, which made the audit payload
  privacy assertion impossible. The corrected test uses a neutral request ID.
- A review correctly pointed out that "current callers are careful" is not a
  durable security boundary. The safer design is to sanitize inside
  `AuditLogService` and test hostile payloads directly.
- The V4 migration creates a new table, so its index-lock risk is lower than a
  migration that indexes an existing hot table. The production rollout note is
  still necessary because later migrations will touch live payment, fraud, and
  ledger tables.
- Audit writes currently fail closed inside the confirm transaction. This is a
  defensible simulator/product-learning tradeoff because a local success without
  audit evidence weakens replayability, but it would be dangerous to carry
  unchanged into an irreversible external processor integration.
- A flat SQL string test helper made audit privacy assertions too coarse. The
  contract test now reads structured audit rows so positive assertions target the
  actual actor, action, before payload, and after payload fields.
- Audit payload mapping inside a controller is easy to accept at first and hard
  to defend as capture, refund, review, and label flows arrive. Extracting the
  mapper now keeps confirm orchestration readable and gives future audit event
  shapes a natural test boundary.
- Staff-level audit review has to be adversarial. Redaction, actor identity,
  transaction evidence, and metric semantics are evidence boundaries, not polish
  details.
- `repository.save(...)` is not the same as durable commit. For JPA-backed
  audit evidence, created/failed counters need transaction-completion semantics
  so rollback or deferred database failures do not produce misleading metrics.
- A Staff role statement is weaker than a repeatable gate. THAAP now treats
  adversarial review as part of commit readiness, with review findings
  classified as fixed now, accepted risk, deferred, or rejected as not
  applicable.
