# Daily Deep Dive: 2026-07-04

## 1. System Goal

Chapter 21 retires every implementation debt inherited from Phases 1 and 2
before fraud policy begins trusting payment lineage. It closes five gaps:
synthetic classification, generator recovery, endpoint-create retries, secret
rotation overlap, and shared-worker fairness.

The first-principles rule is simple: a debt is resolved only when the missing
enforcement boundary exists and the dangerous sequence has executable proof.
Changing the word `OPEN` to `RESOLVED` is the last step, not the first.

## 2. Plain-English Design Brief

Trusted origin answers “who is allowed to classify this traffic?” The server
authenticates a dedicated runner credential; merchant metadata remains ordinary
data.

Generator recovery answers “what happened if the other system committed but we
did not checkpoint?” Stable public-API idempotency makes payment mutations safe
to retry. Merchant/customer creation is not idempotent, so ambiguity stops the
run for an explicit cleanup disposition instead of guessing.

Endpoint creation applies the same lost-response principle to a reveal-once
secret. THAAP stores an encrypted copy of the original authorized response,
keyed by a tenant-scoped HMAC of the external idempotency key.

Rotation gives every secret a generation. A claim remembers its generation;
the endpoint retains the previous encrypted generation until an exact expiry.

Fairness chooses who gets the next worker slot. A durable cursor rotates across
merchants and endpoints; per-poll budgets cap burst consumption while each
delivery is still claimed immediately before its HTTP operation.

## 4. Request/Data Flow

Synthetic payment flow:

1. Runner sends API key plus the dedicated runner credential.
2. Merchant authentication resolves the tenant; runner authentication assigns
   origin.
3. PaymentIntent stores origin.
4. Confirm copies origin to PaymentAttempt, FraudDecision, and FeatureSnapshot.
5. Immutable webhook events and generated evidence expose the same origin.

Endpoint-create flow:

1. Controller requires `Idempotency-Key`.
2. Service HMACs the key and canonical request, then reserves it in a
   `REQUIRES_NEW` transaction.
3. The operation transaction creates one endpoint, subscriptions, audit record,
   and encrypted response material.
4. Same-request retry decrypts the original response; changed or rotated state
   conflicts.

Delivery flow:

1. Claim transaction locks the singleton cursor.
2. It rotates to an eligible merchant and endpoint, locks one delivery, creates
   one attempt, and records the current secret generation.
3. Executor enforces merchant/endpoint poll budgets.
4. Secret service loads current or still-valid previous material.
5. Existing dispatch preparation, signing, HTTP, and finalization continue
   unchanged.

## 5. Database Invariants

- Origin columns are non-null and legacy rows default to `MERCHANT_API`.
- Endpoint-create identity is unique per merchant and plaintext external keys
  are not stored.
- A creation record is either wholly `IN_PROGRESS` or wholly `COMPLETED`.
- The same tenant and exact URL have one endpoint identity.
- Previous secret fields are all null or all populated.
- One dispatch cursor records the last merchant and endpoint.
- Existing delivery row locks and unique attempt numbers still prevent double
  claims.
- V13 maps only already-known sends to a conservative dispatch timestamp.

## 6. Security And Privacy Invariants

Runner and API credentials remain environment-only and absent from reports.
Webhook secrets are raw only in the authorized response and process memory;
durable copies use AES-GCM with merchant/endpoint AAD. Idempotency identity uses
HMAC rather than plaintext. The generator journal temporarily needs API keys
to resume, so the file is owner-only and completed/abandoned runs erase step
response payloads. Rollback journaling avoids long-lived WAL sidecars and
SQLite secure deletion overwrites removed secret-bearing checkpoint content.

Metrics use bounded scope tags, never merchant IDs, endpoint IDs, URLs, or
secrets. Endpoint audit state uses safe prefixes and omits URLs/ciphertext.

## 7. Fraud/ML Relevance

Phase 3 can now distinguish synthetic from ordinary payment and decision rows
without trusting merchant metadata or reconstructing classification later.
Later dataset builders can filter the immutable origin column. Stable generator
runs also prevent duplicate payment/decision examples from silently biasing
training or evaluation distributions.

No Phase 3 rule execution, label model, or analyst workflow was added. Those
features now inherit a cleaner substrate.

## 9. Staff Engineer Review Notes

Two design choices matter in review.

First, the generator journal is operator-local rather than falsely
tenant-owned: one run deliberately creates several merchants. Tenant
isolation remains at every public product object, while the local journal owns
cross-tenant orchestration references.

Second, fairness did not pre-claim a batch. Pre-claiming would let slow earlier
HTTP calls consume later leases. Round-robin one-at-a-time claims preserve the
stronger lease invariant at the cost of a serialized cursor, which is
appropriate for the current bounded database worker.

## 13. Interview Narrative

I retired five cross-cutting debts before fraud policy work. The key tradeoff
was a serialized durable fairness cursor and operator-local run journal, which
fit the current bounded product while preserving lease and tenant truth. The
largest surprise was a shipped V9 schema shape that clean migration tests could
not reproduce; I added V13, an immutable-shape PostgreSQL fixture, and ER-0022.
The final hostile pass also found that Chapter 20's redirect correction had not
been applied to the older generator, so ER-0023 now pairs loopback validation
with fail-closed effective-destination proof. The result is zero non-resolved
debt with full backend/Python suites and a real crash-after-commit recovery
demo.
