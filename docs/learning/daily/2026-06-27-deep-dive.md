# Daily Deep Dive: 2026-06-27

## 1. System Goal

Chapter 16 needed to become a trustworthy local payment-risk evidence producer,
not merely a script that happened to print expected values. The hardening slice
makes success mean that payment lifecycle, authorization, fraud lineage,
tenant isolation, privacy, and zero-ledger claims all agree.

## 2. Plain-English Design Brief

The mental model is a fail-closed test harness that also produces durable local
data. If THAAP creates money truth where no capture occurred, links fraud
evidence to the wrong attempt, targets a shared environment, or leaks a secret,
the generator must stop rather than publish a passing artifact.

We built local safety and operational lineage now. Trusted server-side
synthetic-origin classification remains deferred because the necessary schema
and dataset-consumer boundary do not exist. Resumable interrupted runs remain a
separate generator-reliability deferral because there is no durable run-state,
cleanup, or safe resume protocol yet.

The destination ownership is explicit:

- `TD-0001`, Phase 4.5, **Developer Scenario Runner And Traffic-Origin Governance**:
  Payments Core owns the trusted schema/API boundary; Risk Operations owns
  scenario-runner policy and analytics exclusion behavior.
- `TD-0002`, Phase 7, **Synthetic Generator V2 Run Orchestration**: ML/Data Platform owns
  durable run state, checkpointing, retry, resume, and cleanup; Payments Core
  remains responsible for idempotent mutation APIs and origin propagation.

These debts now live in the canonical technical debt register. The readiness
gate validates required fields, immutable IDs, non-vague owners/targets,
resolution evidence rules, and bidirectional master-plan registration so their
survival no longer depends on conversational memory.

## 3. Code Map

- `scripts/generate-synthetic-scenarios.py`: scenario plan, API execution,
  invariant assertions, target validation, run identity, privacy scan, and
  atomic artifact writing.
- `scripts/generate_synthetic_scenarios_tests.py`: deterministic data,
  environment, collision, ledger, privacy, and output tests.
- `PaymentAttemptController`: processor-neutral merchant authorization evidence.
- `PaymentAttemptAuthorizationContractTests`: tenant scope, safe response, and
  simulator-field omission.

## 4. Request/Data Flow

1. The CLI reads the bootstrap token from the environment and validates that the
   API origin is loopback.
2. A collision-resistant run ID is created before merchant mutations.
3. Public APIs create merchants, customers, PaymentMethods, PaymentIntents, and
   confirms; each PaymentIntent carries the run ID and generator version.
4. Merchant reads retrieve PaymentIntent, PaymentAttempt, FraudDecision,
   FeatureSnapshot, Authorization, and ledger evidence.
5. Exact cross-object and money-truth assertions run before the sanitized
   summary is atomically published.

## 5. Database Invariants

- This slice adds no schema migration.
- Existing foreign keys and tenant constraints remain the durable source of
  payment and fraud linkage.
- `syntheticRunId` metadata is operational traceability, not a database-enforced
  origin claim.

## 6. Security And Privacy Invariants

- The admin bootstrap token never appears in CLI arguments or summary output.
- Only loopback HTTP(S) origins without credentials, paths, queries, or
  fragments are accepted.
- Raw card, buyer contact data, API keys, and generated idempotency keys are
  forbidden in the summary scan.
- Authorization reads remain tenant-scoped and omit simulator-specific public
  contract fields.

## 7. Fraud/ML Relevance

Every generated confirm must have a FraudDecision and FeatureSnapshot linked to
the same PaymentAttempt. This gives future replay and label work honest local
examples. It does not yet make the records safe for training: trusted origin,
label provenance, sampling policy, and dataset versioning are still missing.

## 8. Tests As Proof

- Unit tests prove stable scenario plans, valid deterministic phones, safe card
  labels, privacy scanning, loopback enforcement, environment-secret loading,
  run-ID uniqueness, ledger fail-closed behavior, and atomic output.
- Contract tests prove same-merchant authorization reads, cross-merchant
  concealment, safe fields, and omission of `simulatorOutcomeCode`.
- The live smoke test proves the complete public API path; the full backend
  suite protects existing payment, ledger, tenant, audit, and rollback behavior.

## 9. Staff Engineer Review Notes

- The central tradeoff is enforcing local-only generation until a trusted
  synthetic-origin boundary exists, while keeping bounded local runs
  non-resumable until durable orchestration is justified.
- The reduced risks are false ledger proof, shared-data contamination,
  credential exposure, malformed synthetic identity data, artifact collisions,
  and simulator-specific API lock-in.
- The design stays reversible because a future authoritative origin column can
  replace metadata-based local traceability without changing scenario semantics.

## 13. Interview Narrative

- The tradeoff I made was local-only generation before trusted origin lineage.
- The invariant I enforced was no successful synthetic run with false payment,
  fraud, tenant, privacy, or ledger truth.
- The production risk I reduced was contaminating risk evidence while publishing
  a misleading passing artifact.
- I deferred authoritative origin classification to the dataset/ML-lineage
  slice because its trusted schema and consumer boundaries do not exist yet.
- I separately deferred resumability to the generator reliability/volume slice
  until scheduled, high-volume, automatically retried, or long-running jobs
  require durable run state.
- The tests prove deterministic data quality, security boundaries, exact
  lineage, zero-ledger truth, safe output, and public API neutrality.
