# Daily Deep Dive: 2026-07-13 — Deterministic Fraud Decision MVP

## 1. System Goal

We converted the honest allow-only fraud stub into a real, explainable payment-
risk loop. A confirm now evaluates a fixed ruleset, persists exact decision-time
features and every rule outcome, applies one coherent payment action, and only
then—if the action is ALLOW—calls the processor. REVIEW creates a durable queue
item that merchants can inspect and cancel without inventing analyst resolution.

This matters because a fraud platform is credible only when its explanation,
payment state, processor history, and future label data all describe the same
event. A clever score with contradictory money truth is worse than no score.

## 2. Plain-English Design Brief

Think of confirm as a guarded fork:

```text
locked payment + governed features
  -> evaluate every immutable rule
  -> persist decision evidence
  -> BLOCK | REVIEW | REQUEST_3DS | ALLOW
                                  -> processor only here
```

The V1 policies are intentionally narrow: extreme USD amount blocks, a third
attempt enters review, and elevated USD amount requests 3DS. We did not add a
general JSON rules language, Redis velocity, merchant editing, analyst approval,
or an ML score because each expands authorization, failure, lineage, and
operational boundaries that Phase 3 did not freeze.

## 3. Code Map

- `DeterministicConfirmDecisionEngine`: typed predicates, complete evaluation,
  precedence, stable reasons, and exact severity mapping.
- `FraudRule` / `RuleCatalogueValidator`: immutable seeded definition and
  fail-before-traffic catalogue contract.
- `RuleExecutionResult`: append-only per-rule evidence.
- `PaymentIntentController`: locked transaction, pre-processor flush, four
  branches, review cancellation, audit/webhook/idempotency integration.
- `ManualReviewCaseController`: tenant-owned bounded list/detail reads.
- V20–V25: tables, seeds, immutability, forward type repair, semantic lineage,
  and conservative webhook subscription-consent repair.
- Contract, rollback, migration, metric, tenant, and PostgreSQL concurrency
  tests provide the proof ladder.

## 4. Request/Data Flow

1. API key and idempotency key establish tenant and retry identity.
2. Confirm locks PaymentIntent, validates owned PaymentMethod, and assigns the
   next attempt number.
3. Seven feature values and one snapshot are materialized from allowlisted data.
4. All three rules evaluate; the engine returns results and one aggregate action.
5. Decision, features, results, and optional review case are persisted and
   flushed through SQL constraints.
6. BLOCK, REVIEW, and fraud step-up finish without processor/money rows. ALLOW
   invokes the simulator and records Authorization/lifecycle truth.
7. Audit, webhook, idempotent response, and after-commit metrics reconcile the
   same branch.
8. Review cancellation locks intent before case, cancels intent/attempt/case,
   preserves the original decision, and creates no void or ledger entry.

## 5. Database Invariants

- One attempt owns one decision; each `rules_v1` decision owns three unique
  results, one per definition/version.
- Feature definition ID/code/version/type agrees with every typed value.
- Rule result ID/code/version/priority/action/reason agrees with the immutable
  rule definition.
- A review case agrees with the same tenant, intent, attempt, REVIEW decision,
  reason bytes, and traffic origin.
- Rule definitions/results and decision-time feature evidence are append-only.
- Review case lifecycle allows only a coherent OPEN shape or a coherent
  MERCHANT_CANCELED shape.

Without these constraints, a direct SQL error could make an explanation look
valid while attaching the wrong rule meaning or an ALLOW decision to a review.

## 6. Security And Privacy Invariants

The engine never receives PAN, CVV, fingerprint, BIN, last4, customer PII,
metadata, description, credentials, or raw idempotency material. Public DTOs
expose IDs, closed status/reason codes, timestamps, and safe governed evidence.
Metrics use finite action/rule/outcome/stage/cause/origin dimensions. Tenant and
traffic origin are database identities, not optional filters.

## 7. Fraud/ML Relevance

The stored feature/result/decision bundle is future training and replay
infrastructure: later labels can point to what the engine actually saw and did.
But the current `0.9500` BLOCK value is not calibrated probability. Phase 4/5
must add label provenance, time-safe datasets, model version, calibration, and
deployment lineage before making ML claims.

## 8. Tests As Proof

- Unit vectors cover numeric edges, all eight rule match subsets, and input
  permutations.
- Contract tests prove all actions, exact replay, historical compatibility,
  bounded review pages, tenant ownership, and zero forbidden artifacts.
- Rollback tests fail every rule-result position and review-case persistence.
- PostgreSQL tests force real lock waits for same/distinct confirm and cancel
  keys, fail the production rule-result flush constraint before processor work,
  and prove equal-timestamp cursor pagination on the production dialect.
- Migration tests prove clean and retained upgrades, immutable catalogues,
  copied-semantic foreign keys, and historical byte preservation.
- The loopback demo proves the complete public path and reconciles durable rows
  through read-only SQL.

## 14. Phase 4 Planning Goal

The next system goal is to convert the review queue from a merchant-visible work
item into a trustworthy operational feedback loop. The shortest useful slice
is not “add an approve button.” It is:

```text
dedicated operator identity
  -> role and assignment authorization
  -> immutable resolution
  -> coherent payment cancellation
  -> immutable, time-safe fraud label
```

Approval, refunds, Redis velocity, policy, authentication, chargebacks, and
incidents then build on that actor and evidence foundation in separate chapters.

## 15. Why Outcome And Label Are Separate

A payment action answers what THAAP did. A label answers what later evidence
says about fraud. Plain refund may be customer service, and plain cancellation
may be caution without proof. The Phase 4 plan therefore carries an explicit
classification separate from the action and creates labels only for confirmed
legitimate/fraud classifications or fraud-coded chargebacks. This avoids
silently training future models on business actions misrepresented as truth.

## 16. Label Time And Future Leakage

Every label records both when evidence occurred and when THAAP learned it. A
chargeback raised weeks later cannot be joined into a historical training row
as if it existed at authorization time. Dataset builders must filter by
`available_at`, and corrections append superseding labels rather than rewriting
history.

## 17. Redis Consistency Model

Redis cannot participate atomically in the PostgreSQL payment transaction. The
plan uses a stable logical-attempt member and one atomic versioned operation so
retry excludes the current attempt even if an earlier database transaction
rolled back. A leaked reservation expires and can only raise risk
conservatively. Timeout never becomes zero: risk decisioning receives an
explicit unavailable feature and REVIEW floor, while rate-limit ambiguity
returns 503 rather than a false 429 or silent acceptance.

## 21. Chapter 26 Enforcement Model

Authentication is deliberately two-stage. The request resolver treats the
operator secret as a candidate credential and constructs a tenant/actor
context. Every mutation then reloads and locks the operator row before touching
the review. That second check is what makes disable-versus-action serialization
real; a filter-only role check would be stale by the time payment or label truth
changes.

Assignment is split into a mutable projection and immutable events. The case
row answers “who owns this now?” efficiently, while assignment events answer
“how did ownership get here?” PostgreSQL uses tenant-safe foreign keys and a
deferred projection trigger so a projection cannot commit without the matching
event even though ORM flush order may write them in either order.

Resolution uses the existing lock hierarchy: operator authorization, then
PaymentIntent, PaymentAttempt, and ManualReviewCase. CANCEL and
CANCEL_AND_REPORT_FRAUD share the same local cancellation boundary. The latter
adds a typed FRAUD label with separate evidence and availability times; plain
CANCEL remains INCONCLUSIVE and cannot create training truth.

The first hostile implementation review found that a naive “self-assign” rule
would let an analyst steal an already-assigned case. The corrected rule permits
self-assignment only from OPEN; reassignment requires RISK_MANAGER and locks the
target operator so target-disable cannot race into a stale assignment.

## 22. Chapter 26 Hostile Closure Lessons

The most important lesson was that a locally plausible invariant can still be
false at the framework or upgrade boundary. The code configured a Jackson 2
`ObjectMapper`, but Spring Boot 4's HTTP converter uses Jackson 3; unknown
fields therefore remained open until a `JsonMapperBuilderCustomizer` closed
the actual transport boundary. Similarly, a migration that looked safe on an
empty database failed against a retained V25 cohort because the V24 history
trigger correctly rejected an UPDATE. Default-backed non-rewriting columns
were the truthful repair.

Lock ordering also needs fresh reads, not just correct locks. A JPA entity read
before waiting on PaymentIntent could retain stale case state in the persistence
context. Fetching only payment lineage first and then loading the case under its
lock makes the post-wait authorization and terminal decision observe committed
truth. Transaction metrics have the same timing requirement: register the
after-completion observer before any fallible write, or early rollbacks become
invisible.

Finally, enums are not a taxonomy. `CARD_TESTING` and
`ACCOUNT_TAKEOVER_CONFIRMED` were each valid values but an invalid pair. V28
and service validation now bind each fraud type to its exact reason. This is
why fraud data review must prove relationships, not merely column domains.

## 23. Chapter 27 — Override Before Processor

An analyst approval is not permission to rewrite the fraud engine. The engine's
REVIEW decision remains the historical fact describing what the machine knew at
confirm time. APPROVE is a later human fact: “an authorized operator accepted
this reviewed attempt.” Keeping both facts is essential for model evaluation,
appeals, and audit. Otherwise every human override would corrupt the very
training data needed to improve the original decision.

The transaction therefore has a deliberate order. It locks actor and payment
lineage, validates assignment, writes the immutable resolution and optional
classification label, and flushes that evidence before the processor call. A
constraint failure at this flush proves the processor is never invoked without
durable override intent. Later failures still roll back local authorization,
ledger, audit, webhook, and idempotency state together.

The processor call itself cannot be rolled back. The simulator consequently
uses the reviewed PaymentAttempt UUID as its operation identity. A retry after
local rollback addresses the same operation, while a genuinely different
attempt produces a different reference. This is the core payments distinction
between transactional atomicity and idempotent reconciliation across an
external boundary.

The hostile race review also clarified outcome truth. Approval that reaches
automatic capture makes a waiting merchant cancellation lose because captured
funds are terminal for this API. Cancellation that owns the PaymentIntent lock
first makes approval revalidate and fail before a third processor call. Two
approvals converge to the first committed resolution, authorization, and
capture even when the follower submits a different classification.

Explain-back: why must REVIEW, APPROVE, processor authorization, and LEGITIMATE
label remain four separate facts, and which one supplies the external operation
identity after rollback?

## 24. Chapter 28 — Authentication Is Evidence, Not Authorization

A challenge is not money authorization. It is a pending proof obligation
attached to one attempt. That distinction is why fraud-requested authentication
has no Authorization row before success, while processor-requested
authentication may retain a `REQUIRES_ACTION` Authorization whose authorized
amount is still zero. Only authenticated processor approval can create approved
funds, and only the existing capture boundary can create ledger value.

The completion transaction locks PaymentIntent, PaymentAttempt, and challenge
in that order, revalidates the tenant-bound secret even for terminal reads, and
compares the server clock using `now < expiresAt`. It then calls the simulator
with an authenticated continuation marker and the same attempt-derived
operation identity. A second `REQUIRES_ACTION` is not converted into an
unbounded loop: it returns conflict and rolls back every local transition.

Reveal-once behavior and exact idempotent replay create a storage tension. The
raw secret must be returned for the original confirm replay, but must not exist
as plaintext durable data. The solution is AES-GCM protected response material
with merchant and idempotency-record identity as additional authenticated data.
The challenge itself stores both a SHA-256 verifier and a purpose-separated
HMAC identity, and startup inventories every still-required HMAC and replay key
version before accepting traffic.

V31 captures the historical lesson: table constraints validate a row shape but
cannot alone prove the row belongs to the correct fraud decision or processor
authorization, nor prevent later rewriting. PostgreSQL triggers now validate
those source-specific edges and permit exactly one PENDING-to-terminal
transition. The retained migration had to be forward-only because V30 had
already run on the local product database.

Explain-back: why can a processor-source challenge have an Authorization row
while still having zero authorized funds, and why must terminal replay validate
the client secret again?

## 25. Chapter 29 — Identity Inputs Are Not Model Features

An IP address, device ID, session ID, and user agent can help correlate events,
but exposing their hashes as feature values would create both privacy leakage
and an unstable model contract. Chapter 29 therefore stores tenant-bound,
purpose-separated HMAC identities only as restricted lineage. The explainable
feature surface contains safe classifications and bounded values such as
country, channel, account age, bot score, CAPTCHA outcome, and country-match
booleans.

Missing evidence must remain missing. A missing bot score is not zero, and a
missing country comparison is not false. The materializer always records
`risk.context_present`, persists only optional values actually observed, and
lists absent feature codes in snapshot lineage. That preserves the distinction
between a real low-risk observation and merchant data that was never supplied.

Explain-back: why would replacing a missing bot score with zero corrupt both
fraud decisions and future model training, and why are HMAC correlation values
kept outside the public FeatureSnapshot?

## 26. Chapter 29 — Deferred Trigger Events Are Historical Images

A PostgreSQL deferred constraint trigger runs at commit, but its `NEW` record is
the image captured when that triggering statement ran. RiskContext is inserted
before the FraudDecision exists and receives its decision ID later in the same
transaction. Therefore, the deferred INSERT event still carries a null decision
even though the committed row is complete.

The correct enforcement split is:

- a BEFORE INSERT trigger validates the already-existing payment-attempt edge;
- a BEFORE UPDATE/DELETE trigger permits only one null-to-decision attachment
  and rejects every safe-value or history rewrite;
- a DEFERRABLE constraint trigger re-reads the current RiskContext row by ID at
  commit and validates the final decision/attempt/origin edge.

This is stronger than relaxing the constraint for ORM convenience: incomplete
direct SQL still fails at commit, while legitimate ORM flush ordering remains
supported. The hostile PostgreSQL tests forced both successful and rolled-back
paths and caught the stale-event-image mistake before the first completion
claim.

## 27. Chapter 29 — Input Grammar Includes Numeric Conversion

An integer field is not strict merely because its Java type is `Integer` and it
has `@Min`/`@Max`. Jackson may coerce `1.5` to `1` before Bean Validation sees
the value, erasing evidence that the client sent an invalid representation.
Chapter 29 disables float-to-integer coercion on the Spring HTTP mapper and the
standalone mapper, then proves fractional, overflow, enum, country, IP,
control-character, unknown-field, and future-time partitions.

In a payment-risk API this matters because conversion changes product truth:
silently rounded account age, login age, or bot score becomes durable feature
evidence and later training data. Rejecting the representation before any
PaymentAttempt is created preserves both API honesty and ML lineage.
