## Three things worth remembering

### 1. A well-formed claim and a true claim are different things

The old gate checked the *shape* of an invariant row: required fields present,
`Status: PASS`, no `TBD`/`TODO`/`FIXME` marker. That is precisely the check a
well-formed obsolete claim passes with room to spare.

Every Phase 5 matrix is `PRE_IMPLEMENTATION`. Its `Proof` fields were written in
future tense as obligations — "`ProjectionRebuildObservabilityTests` will inspect
Micrometer meters." Implementation then consolidated each domain into one contract
class plus a `*PostgreSqlTests` subclass re-running the same bodies against real
PostgreSQL. That consolidation is good engineering: one body proven against both H2
and real PostgreSQL beats two suites that drift apart. Then `Status` was flipped to
`PASS` and nobody rewrote `Proof` to say what had been built.

Chapter 50 planned eleven suites and shipped seven test methods. Chapter 46 planned
ten and shipped 302 lines across two classes. Nothing in the process forced the
document written *before* implementation to agree with the code written *after* it,
and the gate could not tell the difference, because a sentence naming a class that
does not exist is shaped exactly like a sentence naming one that does.

### 2. A process correction is not real until it has been executed against the failure

`ER-0098` recorded that removing `openapi-contract-check.py` from the readiness run
would fail a test. It would not have. The readiness tests stubbed every checker and
asserted only the final exit code — an unreferenced stub is simply never called, and
the run still exits 0. The correction was written down, believed, and toothless.

It was found by doing the obvious thing nobody had done: delete the line and watch
for a red test. Nothing went red.

The new test writes a marker file from each stub and asserts every marker exists.
I verified it the same way rather than trusting it: stripping the
`python-sdk-package-check.py` line into a scratchpad copy of the readiness script
makes the test fail with `['python-sdk-package-check.py']`. The mutant dies. That
mutation check costs about four seconds and is the only thing separating an
enforcement from a claim about an enforcement.

### 3. A gate that cries wolf is a gate someone switches off

The resolver has to fail closed on a missing artifact while staying silent on the
backticked prose the matrices are full of — `AUDIT` and `LIMIT` are SQL keywords the
rows quote, `ER-0096` is a register coordinate, `PASS` is a status. Flagging those as
missing files would bury 511 real rows in noise, and a noisy gate gets bypassed,
which is the exact mechanism that let the first unrun gate survive.

So the match is deliberately narrow: something shaped like a test class
(`^[A-Z][A-Za-z0-9]*Tests?$`) or like a source file with a known extension. Anything
else in backticks is prose and is ignored. Path references fall back to basename,
because Chapter 58 names SDK suites as `tests/test_secure_client.py`, relative to the
client package rather than to the repository.

The same instinct shaped the escape hatch. A row whose proof was planned and never
built cites a `TD-NNNN` coordinate, and the gate accepts that — but the exemption is
not silent. It costs an author a register entry with an owner, a trigger and done
criteria, which `technical-debt-check.py` then enforces. The gap moves somewhere it
has a name, instead of living invisibly inside a `PASS` row.

## What I got wrong

Two things, both recorded rather than quietly fixed.

The larger one is that 23 rows now read `Status: PASS` while their own `Proof` field
admits the suite was never written. That is incoherent on its face, and it is the
honest description of where the repository stands. The cause is structural:
`invariant-proof-check.py` requires every row to be `PASS`, so a matrix has no way to
express "held on the ordinary path, unproven adversarially." The fix is a `PARTIAL`
status that mandates a debt reference and is rejected at phase closure rather than
chapter closure. I did not make it here because it changes the meaning of all 511
invariant rows in the repository, and that belongs in its own chapter with its own
migration — not inside an audit. It is written down in the audit document so the next
person does not have to rediscover the reasoning.

The smaller one I found while writing this note. The debt exemption is *field-wide*: a
`Proof` field citing `TD-0007` is skipped entirely, so a genuinely fabricated class
name sitting in the same sentence would ride through unchecked. I confirmed the hole
exists — a field naming `CompletelyInventedTests` alongside a `TD-0007` citation
returns no errors — and then confirmed it is currently latent: across all 23
debt-exempt rows, re-running the resolver with the exemption disabled surfaces zero
additional unresolved artifacts. Nothing is being masked today. The right shape is to
exempt only the artifacts the debt entry names, not the whole field.
