## 2. Payment Processing Concepts Learned

- Confirm is now both a payment lifecycle bridge and a fraud-lineage boundary.
- Processor authorization should happen only after the fraud decision is known
  and durably attached to the attempt.
- Idempotent replay must return the same attempt response without duplicating
  fraud decisions, feature snapshots, authorizations, or webhook deliveries.

## 3. Fraud Detection Concepts Learned

- A fraud decision is not complete unless it records what was decided, why, how
  long it took, and what feature facts existed at decision time.
- Honest stub lineage is better than fake intelligence: `RULES_NOT_ENABLED` and
  nullable `modelVersion` are truthful.
- FeatureSnapshot is the bridge between real-time decisions and future offline
  replay, rules simulation, and ML training.

## 4. Security Concepts Learned

- Feature payloads must use safe decision-time values only.
- Chapter 12 stores BIN and last4 but not raw PAN, CVV, raw PII, API keys,
  idempotency hashes, or merchant secrets.
- Fraud decision detail remains tenant-scoped through `X-Api-Key` resolution.

## 5. Architecture / Design Notes

- `PaymentAttempt` remains the scoring and audit unit.
- `FraudDecision` owns action, score, reason, ruleset/model, timing, and freshness
  summary.
- `FeatureSnapshot` owns immutable feature values and freshness proof.
- The first `features_v1` set is intentionally small: amount, currency, capture
  method, attempt number, safe card metadata, and lineage IDs.
- Lineage IDs remain in `features_v1` for portable replay/export, while the
  dedicated columns remain canonical for database integrity.
- Legacy placeholder FraudDecision rows are marked with
  `legacy_placeholder_v1` and `MISSING` freshness instead of fake attempt
  lineage. They are not ML-valid training examples.
- Clarified the boundary between fraud reasons and processor outcomes:
  `RULES_NOT_ENABLED` is the Chapter 12 fraud decision reason, while simulator
  outcome codes remain on `Authorization` because they are produced after the
  fraud decision.
- Real rules, velocity counters, model scoring, review case creation, audit logs,
  and ledger effects remain deferred to their owner chapters.

## 7. Bugs, Surprises, Or Tradeoffs

- The old tenant-isolation test manually inserted placeholder FraudDecision rows.
  Chapter 12 replaced that with real confirm-generated decisions because
  decisions now require PaymentAttempt lineage.
- Adding a foreign key from PaymentAttempt back to FraudDecision would create a
  circular delete path in tests. The durable ownership direction is
  FraudDecision -> PaymentAttempt; `payment_attempts.fraud_decision_id` remains
  the public correlation pointer.
- The stub score is `0.00` and risk level is `LOW`; this is intentionally modest
  because no real rules or model have run.
- The V3 migration is now upgrade-safe for long-lived dev databases with old
  placeholder decisions, but it is not a full production zero-downtime migration
  strategy. That belongs with deployment mechanics and live data contracts.
- Verification tools can fail for infrastructure-version reasons even when the
  underlying service is healthy. The correct Staff move was to test Docker
  directly, isolate Testcontainers as the failing boundary, and pin the
  dependency version that restores the production-database proof.
