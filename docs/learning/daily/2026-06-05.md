## 2. Payment Processing Concepts Learned

- Merchant onboarding is a payment-system trust boundary, even in a simulator.
- Customer and payment method APIs should minimize stored data before
  PaymentIntent creation grows more state transitions.
- Test card input is transient input. The durable payment method should be a
  token plus safe card metadata.

## 3. Fraud Detection Concepts Learned

- Safe card metadata such as BIN, funding type, country, last4, and fingerprint
  can support future rules and analyst investigation without storing raw PAN.
- Customer hashes can support future velocity and linkage features, but raw PII
  should not be needed for the first fraud MVP.
- Fraud lineage fields remain deferred until `PaymentAttempt` exists.

## 4. Security Concepts Learned

- API keys are bearer credentials. Raw keys should be revealed once and not
  persisted.
- Public merchant creation must require a bootstrap token, even in a simulator.
- Prefix/hash storage lets the system authenticate and debug credentials without
  turning database reads into credential access.
- Low-entropy PII and card-derived values need keyed HMAC/pepper domains so a
  database leak is not trivially offline-enumerable.
- Contract tests should prove non-leakage in both API responses and database
  rows.

## 5. Architecture / Design Notes

- `SecretHasher` owns exact SHA-256 hashing for high-entropy generated secrets.
- `SensitiveValueHasher` owns keyed HMACs for customer PII, card fingerprints,
  and idempotency request hashes.
- Day 5 did not require a database migration because Day 4 already added the
  required hashed secret and safe metadata columns.
- Merchant admin remains bootstrap setup, not full production admin identity,
  RBAC, audit, or key rotation.
- Payment method validation remains intentionally simple simulator validation.
